# ADR-0010: 診断ログは実値をマスキングせず出力し、`logs` フォルダの管理は利用者・導入組織の責任とする

- 状態: 採用済み（Accepted）
- 日付: 2026-08-11
- 管理責任者: リポジトリメンテナー

本 ADR は、初期仕様 版 1.10 で確定済みの `DIAG-003`・`DIAG-004`・`DIAG-005`・`SEC-005`・`SEC-007` と、P01 で実装済みの挙動を、設計判断として記録するものです。実装はすでに完了しており、本 ADR が追加するのは判断の経緯そのものの記録です。

## 背景

`DIAG-003`・`DIAG-004` は、診断に必要な場合はログ本文、DB セル値、DICOM タグ値、DICOM 画素、認証情報、クリップボード内容その他の実値を、機密性を理由とするマスキング・省略・伏字を必須とせず、また追加設定や警告なしで診断ログへ出力してよいと定めています。`SEC-005` は、その結果として診断ログに個人情報等の機密データ、認証情報、フルパスその他の実値が平文で含まれ得ること、`logs` フォルダの閲覧制限・持ち出し・保管・削除が利用者または導入組織の責任範囲であることを定めています。`SEC-007` は、初期リリースでは DICOM 匿名化、機密データのマスキング表示、操作監査ログを提供せず、利用可否と端末管理を導入組織の責任範囲とすると定めています。

これらは初期仕様 版 1.10 に明記され、P01 では、診断ログファイル冒頭にマスキングしない方針と管理責任を明記する見出しを出力する実装、および [`docs/security/data-handling.md`](../../security/data-handling.md) への具体値の追記まで完了しています。しかし、「なぜマスキングしないのか」「マスキング必須化・暗号化・アクセス制御という代替案を検討したうえで、なぜ採らなかったのか」という判断の経緯そのものは、要件表と実装記録には残っていても、ADR という判断記録の形では記録されていませんでした。これは意図的な設計判断ですが、方針を知らずに診断ログを目にした読者が「情報漏えい」や実装の不備と誤認する危険があります。本 ADR はその誤認を防ぐために、判断の経緯を残すものです。

## 判断の基準

- Hakutaku は運用先の対象端末の管理されたローカル環境で使う開発・調査ツールであり、その端末で起きた不具合の原因究明に必要な情報を欠落させないこと（診断性の優先）
- 版 1.10 の確定要件（`DIAG-003`〜`005`、`SEC-005`、`SEC-007`）を変更せず、その意図を判断として明文化すること
- `SEC-001`（参照内容をネットワークへ送信しない）、`SEC-009`（実行時の書き込み先を実行ファイル直下に限定する）など、他の不変条件と矛盾しないこと
- 初期リリースの対象範囲を超えて、DICOM 匿名化や操作監査ログなど `SEC-007` が後続リリース扱いとする機能を先取りしないこと

## 検討した選択肢

1. 実値を診断ログへそのまま出力し、`logs` フォルダの管理を利用者・導入組織の責任とする（版 1.10 の確定要件、P01 実装済み）
2. 既知のパターン（DICOM タグ、DB セル値、認証情報など）を自動検出してマスキングを必須化する
3. 診断ログファイルを暗号化する
4. `logs` フォルダやログ閲覧機能に対して、Hakutaku 自身が認証・認可によるアクセス制御をかける

## 決定

選択肢1を採用する。適用範囲は次のとおり。

- `DIAG-003`・`DIAG-004` のとおり、診断に必要な場合はログ本文、DB セル値、DICOM タグ値、DICOM 画素、認証情報、クリップボード内容、参照元のフルパスその他の実値を、マスキング・省略・伏字なしで診断ログへ出力してよいものとする。追加設定や警告も必須にしない。
- `DIAG-005` のとおり、時刻、重要度、モジュール、操作種別、ソース ID、エラーコード、スタックまたは内部位置を記録できるようにする。
- `SEC-005` のとおり、診断ログに個人情報等の機密データ、認証情報、フルパスその他の実値が平文で含まれ得ることを前提とし、マスキング・暗号化・アクセス制御を Hakutaku の機能要件とはしない。`logs` フォルダの閲覧制限、持ち出し、保管、削除は利用者または導入組織の責任範囲とする。
- `SEC-007` のとおり、初期リリースでは DICOM 匿名化、機密データのマスキング表示、操作監査ログを提供しない。利用可否と端末管理は導入組織の責任範囲とする。
- P01 の実装（[`docs/security/data-handling.md`](../../security/data-handling.md)「実装で確定した具体値（P01）」）のとおり、診断ログファイルの冒頭（新規作成時とローテーション後の新しいファイルの両方）に、実値をマスキングしない方針と、管理責任が利用者・導入組織にあることを明記した見出しを出力し、ログを開いた読者がその場で方針を確認できるようにする。

選択肢2（マスキング必須化）を退ける理由: DICOM タグ、DB セル値、パス、認証情報などは運用先ごとに書式や意味が異なり、汎用的な検出規則では過剰検出（診断に必要な値まで隠してしまう）と過小検出（機密値の見落とし）を避けられない。誤ったマスキングは不具合の原因究明そのものを妨げ、`DIAG-003` が優先する診断性と正面から矛盾する。検出規則の実装・保守コストに見合う効果も見込めない。

選択肢3（暗号化）を退ける理由: Hakutaku は対象端末のローカル環境で動く単体の調査ツールであり、鍵の生成・配布・保管を安全に行う基盤を持たない。復号鍵の管理が新たな責任と攻撃対象を生むだけで、平文のアクセス制御を導入組織の端末管理（OS のフォルダ権限、設置場所の隔離など）に委ねる方針と比べて実効性が高まらない。

選択肢4（アクセス制御）を退ける理由: Hakutaku 自身が認証・認可の仕組みを持つことは、「導入フォルダごと退避・削除すればよい」という単体ツールとしての設計（`SEC-009`）から外れ、対象範囲を大きく広げる。OS のフォルダ権限や導入組織の端末管理に委ねる方が、運用先の既存の管理体制と整合し、追加の実装・保守コストも生まない。

いずれの代替案も、「診断に必要な情報を欠落させない」という最上位の要件（`DIAG-003`）と両立させるだけの効果が、追加コストに見合わないと判断し、版 1.10 の確定要件どおり選択肢1を採用した。

## 結果

### 良い影響

- 対象端末で起きた不具合の原因究明に必要な実値（ログ本文、DB セル値、DICOM タグ値、認証情報など）が、マスキングによる欠落なく記録される
- マスキング機構の誤検出・見落としという新たなリスクを持ち込まない
- 診断ログファイル冒頭の見出し（P01 で実装済み）により、ログを開いた読者がその場でマスキングなしの方針と管理責任の所在を確認できる

### 悪い影響とトレードオフ

- 診断ログおよびその閲覧・共有経路（ログの提供、画面共有、バグ報告への添付など）を通じて個人情報等の機密データが平文のまま外部へ渡り得る。その防止は Hakutaku の機能ではなく、利用者・導入組織の運用（`logs` フォルダの閲覧制限、持ち出し管理、保管、削除）に依存する
- 方針を知らない利用者が診断ログを不用意に共有すると、情報漏えいにつながり得る。導入手順書等での周知が前提になる（後続課題）

## セキュリティとプライバシーへの影響

診断ログには個人情報等の機密データ、認証情報、フルパスその他の実値が平文で含まれ得る（`SEC-005`）。Hakutaku 自身はマスキング・暗号化・アクセス制御を行わず、`logs` フォルダの閲覧制限、持ち出し、保管、削除は利用者または導入組織の責任範囲とする。この境界は [`docs/security/data-handling.md`](../../security/data-handling.md)「機密情報の確定要件」「データ領域と責任」と同一であり、本 ADR はこれを変更せず、判断の経緯を記録するものである。

診断ログ自体はネットワークへ送信されず（`SEC-001`）、書き込み先も実行ファイル直下の `logs` に限定される（`SEC-009`）。これらの不変条件は本判断でも維持する。

## 移行または切り戻し

本判断はすでに版 1.10 の確定要件および P01 の実装として適用済みであり、新たな移行作業はない。

方針を変える場合（例えば後続リリースでマスキング機能、機密データのマスキング表示、操作監査ログを追加する場合）は、`SEC-007` を含む関連要件を改定したうえで、本 ADR を `Superseded` とする新しい ADR を作成する。既存の診断ログファイルへ遡って適用することはしない。

## 検証

- 診断ログと画面表示がフルパス等の実値をマスキングしないこと（`DIAG-003`、`DIAG-004`）、`logs` 以外のユーザープロファイル配下に何も作られないこと（`SEC-009`）は、[`docs/verification/manual-check.md`](../../verification/manual-check.md)「4.16 実行時フォルダと診断ログ」で確認済み
- 参照内容がネットワークへ送信されないこと（`SEC-001`）は、[`docs/verification/stage0-results.md`](../../verification/stage0-results.md)「3. `SEC-001` 送信監視」で確認済み
- 診断ログファイルの冒頭（新規作成時・ローテーション後）に、マスキングしない方針と管理責任の所在を明記した見出しが出力されることは、P01 の実装記録（[`docs/security/data-handling.md`](../../security/data-handling.md)「実装で確定した具体値（P01）」）で確定済み。段階0検証記録・手動確認手順には見出し文言そのものを対象とした確認項目はまだない（後続課題）

本 ADR は採用済みのため本文を書き換えず、上の3点目が「後続課題」とした事項の現在の状態を追記として記録します。

見出し文言そのものを対象とした確認項目は、[`docs/verification/manual-check.md`](../../verification/manual-check.md)「4.16 実行時フォルダと診断ログ」の手順4・手順5として追加済みです。手順4は新規作成直後の `logs\hakutaku.log` の冒頭を対象に、マスキングしない方針（「マスキングせずそのまま記録します」）と、`logs` フォルダの閲覧制限・持ち出し・保管・削除が利用者・導入組織の責任範囲であること（「利用者・導入組織の責任範囲です」「SEC-005」）が明記されていることを確認します。手順5はローテーション後の新しい `hakutaku.log` の冒頭についても同じ内容を確認します（退避済みファイルを含む見出し内容の自動検証は `crates/diagnostics/tests/diagnostics.rs` の `rotated_files_all_start_with_required_header` にあります）。

## 見直す条件

- 導入組織から、マスキング・暗号化・アクセス制御を Hakutaku 自身の機能として求める要求が確認され、版 1.10 の確定要件（`DIAG-003`〜`005`、`SEC-005`、`SEC-007`）を改定する場合
- DICOM ビューア等の後続リリースで、`SEC-007` が対象とする機密データのマスキング表示や操作監査ログを提供する判断をした場合
