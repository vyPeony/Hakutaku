# ADR-0002: エラーコード体系は最小限の分散採番とする

- 状態: 採用済み（Accepted）
- 日付: 2026-08-01
- 管理責任者: リポジトリメンテナー

本 ADR の状態は、この変更が `main` へマージされた時点で採用済みになります。

## 背景

P01 で診断ログへエラーコードを記録できるようにしたが（`DIAG-005`）、リポジトリ全体の採番方針がなく、`src-tauri/src/bootstrap/runtime.rs` が `HKT-W2-0001`〜`0007` を暫定的に採番している。各モジュールが独自に採番すると番号が重複し、ログから発生源を特定できなくなる。本 ADR は、この採番方針を定めるものである。

一方で、「エラーコードを設けない」選択肢もある。Hakutaku の診断ログは実値をマスキングせず（`DIAG-003`／`DIAG-004`）、本文と内部位置（`at=ファイル:行`）を毎レコード記録する。利用者向けエラーも `ERR-002` により対象・理由・次操作を文章で示す。エラーの内容は既に利用者とログへ残っており、コードがなくても原因調査はできる、という指摘である。

## 判断の基準

- ログから発生源と原因を特定できること（背景で示した問題設定）
- 導入組織の手順書・問い合わせ対応が、失敗を版をまたいで安定した名前で参照できること
- 採番・保守のコストが小さく、開発者が文書だけを見て重複なく採番できること
- 既存の P01 実装と診断ログとの互換を保つこと

## 検討した選択肢

1. エラーコードを設けない。本文と `at=` に依拠する
2. `crates/diagnostics` へ全コードの定数と台帳を中央集約する
3. 中央文書は領域表だけとし、コードは領域ごとの台帳モジュールで分散採番する（最小限の体系）

## 決定

選択肢3を採用する。書式（`HKT-<領域>-<番号4桁>`）、領域の割り当て、採番手順は[エラーコード体系](../../development/error-codes.md)を正本とする。

選択肢1の核心である「エラーの内容が利用者とログに残れば足りる」は、要件（`DIAG-003`〜`005`、`ERR-002`）のとおり正しい。そのため、エラーコードを全エラーへ義務付けず、「起動不能・継続不能」「利用者・導入組織側の対処が必要」「手順書から参照される見込みがある」失敗にだけ割り当てる。それ以外は `code=-` のままでよい。

選択肢1を全面採用しない理由は次の2点である。

- 本文の文言も `at=ファイル:行` も、版をまたいで安定しない。文言の改善やリファクタリングのたびに、導入組織の手順書・過去の診断ログとの対応が壊れる。これは採番方針で防ごうとしている事故そのものである
- `DIAG-005` は採用済み要件として `code=` 欄を要求しており、欄を恒久的に空へ保つ選択は、既存の P01 実装とテストを外す手戻りを生む。エラーコードが後から必要になってから導入すると、過去版・過去ログと体系が揃わない

選択肢2は、全領域のエラーの意味が診断クレートへ集まって依存の向きが崩れ、コード追加のたびに横断変更とマージ競合の単一点が生まれるため退ける。

## 結果

### 良い影響

- 領域接頭辞により、モジュール間のコード重複が構造的に起きない
- 領域内の重複は、1ファイル（採番台帳モジュール）のレビューで確認できる
- 既存の `HKT-W2-0001`〜`0007` は新しい体系へそのまま適合し、移行はコメントの更新だけで済む（診断ログの互換を維持）
- コードを必須にしないため、些細なエラーに採番の手間が発生しない

### 悪い影響とトレードオフ

- 全コードの一覧が1箇所にない（必要になれば台帳モジュールから生成する。利用者向け一覧表は本 ADR の対象外とし、別途扱う）
- 割り当て基準の判断が実装者に委ねられる（PR レビューで補う）

## セキュリティとプライバシーへの影響

なし。エラーコードは固定文字列であり、実値や個人情報等の機密データを含まない。診断ログの記録内容、保存先、ローテーションは変更しない。

## 移行または切り戻し

- 移行: `src-tauri/src/bootstrap/runtime.rs` の暫定採番コメントを、正本（エラーコード体系）への参照と領域 `W2` の台帳宣言へ差し替える。コードの値は変更しないため、既存の診断ログとの対応は崩れない
- 切り戻し: エラーコードを廃止する場合、各台帳の定数と `error_code =` の指定を削除する。`code=` 欄自体は `DIAG-005` により残る

## 検証

- 新しい領域・コードを追加する PR が、エラーコード体系の文書だけを根拠に、重複なく採番できること
- 診断ログの `code=` を手掛かりに、発生源のモジュールと原因へたどれること

## 見直す条件

- 利用者向けエラーコード一覧表を作るとき（表示や翻訳の要件が加わる場合）
- 領域数・コード数が増え、台帳の分散が重複や検索性の問題を起こしたとき
