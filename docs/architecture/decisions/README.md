# アーキテクチャ判断記録

設計判断記録（Architecture Decision Record: ADR）は、重要な設計判断と、その時点の背景、代替案、影響を残すための文書です。

## ADR を使う判断

- 複数の構成要素やコネクターに影響する
- 後戻りや移行のコストが高い
- 公開 API、保存形式、互換性、バージョン管理に影響する
- 認証情報、データ保持、外部通信などの信頼境界を変える
- 主要な実装技術、配布形態、プロセスモデルを選ぶ

局所的で容易に変更できる実装詳細や、単純な依存更新に ADR は不要です。

## ファイル名

`NNNN-short-kebab-title.md` の形式で、連番を使用します。

例: `0001-application-delivery-model.md`

番号 `0000` は [テンプレート](0000-template.md) のために予約します。

## 状態

- 提案中（`Proposed`）: まだ実装判断の根拠にしない
- 採用済み（`Accepted`）: レビューされ、現在の判断として採用した
- 暫定決定（`Provisional`）: 明示した確定条件（例: 段階1検証の完了）を満たすまで暫定として扱う採用。段階0から実装判断の根拠にできる点で「提案中」とは異なり、確定条件を満たした時点で採用済み（`Accepted`）へ更新する
- `Deprecated`: 現在は推奨しないが、置き換え先がない
- `Superseded`: 新しい ADR に置き換えられた

## 運用

1. テンプレートをコピーし、次の番号と短い題名を付ける
2. 背景、判断の基準、比較する選択肢を記載して PR を作る
3. 通常の PR レビューで合意し、採用済み（`Accepted`）にする
4. 採用後は履歴の正確さを保つため、誤字やリンク以外を原則書き換えない
5. 判断を変える場合は新しい ADR を作り、相互に `Superseded` 関係を記載する
