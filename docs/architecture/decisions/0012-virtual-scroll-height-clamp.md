# ADR-0012: 巨大な表示集合ではスクロール高さをクランプし、区分一次写像で行位置へ対応付ける

- 状態: 採用済み（Accepted）
- 判断日: 2026-08-12 以前（[段階0検証記録](../../verification/stage0-results.md)の [10.1](../../verification/stage0-results.md#101-採用した修正方針)節が記録した再検証セッション。同節に日付の記録がないため、実装がすでに含まれていた公開リポジトリの初期コミットの日付を上限として示す）
- 文書化日: 2026-08-25
- 管理責任者: リポジトリメンテナー

本 ADR は、すでに実装・検証済みの設計判断を後から記録するものです。状態は、この変更が `main` へマージされた時点で採用済みになります。本文は**現在の実装（[`src/virtual_scroll.js`](../../../src/virtual_scroll.js)・[`src/log_view.js`](../../../src/log_view.js)）を正**とし、経緯は[段階0検証記録](../../verification/stage0-results.md)の 10 節を参照します。

## 背景

`PERF-007` は10万行を超えるログを、`PERF-012` は可視範囲と前後バッファだけを保持する仮想スクロールを求めます。仮想スクロールは「総行数 × 固定行高」の高さを持つスペーサでスクロールバーを成立させますが、2000万行規模ではこの理論高さが 440,000,000px（20,000,000行 × 22px）になります。

段階0検証（[stage0-results.md](../../verification/stage0-results.md) 2.3節・7節）で、次の2つの不成立が実測されました。

1. **末尾へ到達できない。** WebView2（Chromium）が実際にレイアウトへ反映した `scrollHeight` は 26,843,546px にクランプされ、スクロールバー操作でファイル末尾付近へ到達できませんでした。要求した高さがブラウザ側で黙って切り詰められるため、スクロール位置と行位置の対応そのものが成立しません
2. **保持上限を一時的に超える。** 1回のスクロール処理は「不足チャンクの取得を開始する（非同期・完了を待たない）→ その時点のキャッシュだけで破棄判定を行う」順で動くため、多数の取得が次々に完了する規模では、次の破棄判定までの窓で `CFG-022` の保持行数・保持バイト数を超えました（241サンプル中18件、最大 +12.6%）

どちらも、ブラウザ側の制約と非同期取得のタイミングに由来する規模依存の問題であり、`PERF-012` の成立可否と行番号ジャンプ（`LOG-013` 系の操作）に直結します。判断を残さないと、後から「なぜ高さを実際の行数どおりにしないのか」「なぜ取得完了ごとに破棄判定を二重に走らせるのか」が読み取れません。

## 判断の基準

- `PERF-012`（可視範囲＋一定バッファのみ保持し、上限超過時は遠い範囲を破棄して再取得する）と `CFG-022` の上限を、規模によらず常に満たすこと
- スクロールバー操作・`Ctrl+End`・行番号ジャンプのいずれでも、表示集合の末尾へ確実に到達できること
- クランプ未満の通常規模（大多数のログ）で、既存の挙動を一切変えないこと（回帰を作らない）
- ブラウザの内部実装（実際のクランプ位置、コンポジタの同期タイミング）へ依存しないこと
- 実行環境なしで回帰を検知できること（2000万行の試験データと WebView2 を必要としない検査に落とせること）

## 検討した選択肢

1. **スクロール高さに上限を設け、超過時だけスクロール座標と行インデックスを別の写像で対応付ける**（採用）
2. 可変行高の仮想スクロール（前置和の推定と実測差分の吸収）へ作り替え、取得済み範囲の実高さでスクロール高さを構成する
3. 総行数を分割してページ送りにし、1ページあたりの高さをブラウザのクランプ未満に抑える
4. 破棄判定については、取得中（in-flight）チャンクの予定行数・概算バイト数を破棄予算へ前もって算入する

選択肢2は、取得完了のたびに前置和を再計算してスクロール位置を補正する非同期の状態機械になり、誤差の蓄積とスクロール位置の飛びを作り込みやすくなります（[`src/virtual_scroll.js`](../../../src/virtual_scroll.js) 冒頭の「可変行高ではなく折りたたみ方式を採用した理由」と同じ判断です）。しかもブラウザのクランプ自体は解消しないため、規模が大きければ結局この ADR と同じ写像が要ります。

選択肢3は、`LOG-006`・`LOG-007` が求める「1つの表示集合を通しで見る」体験を壊し、時系列統合表示のページ境界という新しい仕様判断を持ち込みます。

選択肢4は、`raw_text` の実バイト数が応答到着まで判明しないため、見積もり方法自体に新しい仕様判断を要し、見積もり誤差が残ります。

## 決定

### 1. スクロール高さのクランプ

- [`src/virtual_scroll.js`](../../../src/virtual_scroll.js) に `MAX_TOTAL_HEIGHT_PX = 24_000_000`（px）を置き、総理論高さ（`totalItems × rowHeightPx`）がこれを超える場合だけ、スペーサが構成する「実効総高さ」をこの値に固定する（`computeEffectiveTotalHeightPx`）
- 値は、実測クランプ値 26,843,546px を**安全側に下回る**丸めた値とする。実測値ちょうどに合わせないのは、WebView2 の版や実行環境でクランプ位置が変動しても、指定した高さがブラウザに再度クランプされないようにするため
- クランプが効いているかどうかの判定は `isHeightScalingActive` に閉じ、呼び出し側は規模で分岐しない
- **クランプ未満の通常規模では、従来の1:1の関数（`computeVisibleRange`・`computeSpacerHeights`・`computeScrollTopForRowIndex`）へそのまま委譲し、挙動を変えない。** 既存関数は書き換えず、超過時だけ切り替わる別関数（`computeVisibleRangeForScroll`・`computeSpacerHeightsForScroll`・`computeScrollTopForRowIndexScaled`）を追加する

### 2. クランプ時のスクロール位置と行位置の対応

- **対応の唯一の基準は `computeSpacerHeightsForScroll` が構成するレイアウトとする。** 上下スペーサの高さの**合計**を、可視範囲の位置・大きさによらず常に厳密に「実効総高さ − 実描画行の高さ」に固定し、その残り高さを未描画の先頭側・末尾側の行数比で配分する。上スペーサの高さは、そのまま描画ブロックの document 座標（先頭の描画行の上端）になる
- スクロール位置 → 先頭行インデックス（`computeVisibleRangeForScroll`）と、行インデックス → スクロール位置（`computeScrollTopForRowIndexScaled`）は、どちらもこのレイアウトから導いた**3領域の区分一次写像**の逆写像・順写像として実装し、独自の一次式を持たない。3領域は、上スペーサが0pxでクリップされる頭部、両側ともクリップされない内側（圧縮が効く区間）、下スペーサが0pxでクリップされる末尾であり、境界で連続する
- **末尾到達性を最優先する。** `scrollTop >= maxScrollTopPx`（スクロールバーが末尾に到達した状態）では式を経由せず、先頭行インデックスを上限（`totalItems − visibleRowCount`）へ固定して必ず `endIndex === totalItems` になるようにする。ブラウザが実際に反映した `scrollHeight` が実効総高さと厳密に一致しない環境でも、末尾到達性を環境依存にしないため
- **行番号ジャンプは、目標行そのものではなく `JUMP_CONTEXT_ROWS`（= 2）行手前を先頭行として順写像へ通す。** 実機（WebView2）が 10^7 px 級の座標を単精度相当（±10px 程度）へ量子化するため、目標行をちょうど上端に置く計算では丸めだけで目標行が画面外へ出る
- 1行未満の厳密な画素対応は求めない。優先するのは、可視範囲の連続性（表示行が飛ばない・逆行しない）と末尾到達性である

> [!NOTE]
> [段階0検証記録](../../verification/stage0-results.md)の [10.1](../../verification/stage0-results.md#101-採用した修正方針)節は、この写像を「スクロール位置の比例（0〜1）を総行数に掛けて先頭行インデックスを決める」と記録しています。これは当時の実装であり、**現在の実装とは異なります**。その後 [Issue #33](https://github.com/vyPeony/Hakutaku/issues/33) で、単純比例の一次式とスペーサ配分の一次式は傾きがわずかに違い、2000万行規模で両者が最大46行ずれること（行番号ジャンプの目標行が画面外へ出る）が判明したため、上記の3領域の区分一次写像へ置き換えました。10.1 節は当時の記録として残し、本 ADR が現在の判断を示します。

### 3. 破棄判定の再実行順序

- `renderVisibleRows` の順序（`ensureChunksLoaded` → `evictFarChunks` → `renderRows`）は変えない
- **チャンク取得が完了しキャッシュへ格納した直後に、破棄判定を再実行する。** [`src/log_view.js`](../../../src/log_view.js) の `fetchChunk` 内、`state.chunkCache.set(...)` の直後に `runPostFetchEvictionPass()`（内部で `computeCurrentRenderTargets()` → `evictFarChunks(...)` を呼ぶだけ）を置く
- 判定には見積もりを使わず、**その時点の実測の保持行数・保持バイト数だけ**を使う。`selectChunksToEvict`・`evictFarChunks` は変更せず、そのまま追加で1回呼ぶ

## 結果

### 良い影響

- 2000万行規模でも `CFG-022` の保持上限を全サンプルで順守し（241サンプル中0件の超過。修正前は18件）、スクロールの末尾へ到達できる（[10.4](../../verification/stage0-results.md#104-200万行の再検証)・[10.5](../../verification/stage0-results.md#105-2000万行の再検証)節）
- スクロール位置・スペーサ配分・行番号ジャンプが単一のレイアウト定義から導かれるため、三者の整合が構造的に保たれる
- `viewport.scrollHeight` が可視範囲の移動でふらつかなくなり、末尾到達判定が決定的になる
- クランプ未満の通常規模は従来経路のままで、回帰の対象にならない
- 破棄判定が実測値だけに基づくため決定的で、追加コストは軽量な純粋関数呼び出し1回（DOM 操作・IPC を伴わない）

### 悪い影響とトレードオフ

- クランプが効く規模では、スクロールバーの1px が複数行に対応する。スクロールバーによる行単位の精密な位置決めはできず、行番号ジャンプが正確な移動手段になる
- 行インデックスとスクロール座標の対応に浮動小数点の丸めが入り、同じ `scrollTop` でも指す行が1行程度前後することがある
- 写像が3領域の区分一次関数になり、単純な比例より読み解く手間が増える。`computeSpacerHeightsForScroll` の配分規則を変えるときは `computeScaledScrollLayout` の3領域の式も同時に見直す必要がある
- 破棄判定が1スクロール処理内で複数回走る（取得完了ごと）

## セキュリティとプライバシーへの影響

影響はありません。対象はフロントエンドの表示計算だけで、保存形式・外部通信・認証情報・信頼境界のいずれにも触れません。むしろ保持上限を常に順守することで、フロントエンド側に滞留するログ本文の量が上限内に収まります（`PERF-012`、`SEC-004` の趣旨）。

## 移行または切り戻し

[`src/virtual_scroll.js`](../../../src/virtual_scroll.js) と [`src/log_view.js`](../../../src/log_view.js) に閉じます。Rust 側（`crates/`・`src-tauri/`）、IPC の引数・応答、設定ファイル、保存形式のいずれも変わりません。

クランプ未満の規模は従来の1:1経路へ委譲するため、切り戻しても通常規模の挙動は同じです。クランプ側だけを戻すと、2000万行規模で末尾到達不能が再発します。

## 検証

- [`scripts/check-virtual-scroll.mjs`](../../../scripts/check-virtual-scroll.mjs)（CI の `quality` ジョブ）: クランプ閾値の切り替わり、クランプ超過時の写像、行番号ジャンプと実際の描画位置の一致、保持上限に基づく破棄判定を、試験データも WebView2 も使わずに判定する。期待値は各関数の JSDoc が定める仕様から独立に導く（[回帰検査の対象と判定方法](../../verification/regression-checks.md)）
- [段階0検証記録](../../verification/stage0-results.md)の [10.2](../../verification/stage0-results.md#102-nodejs-スモークテスト)〜[10.5](../../verification/stage0-results.md#105-2000万行の再検証)節: 200万行・2000万行の実機計測モードによる再検証（保持上限の順守、`scrollHeightPx` がクランプ設計値と一致、`Ctrl+End` 相当の到達）
- [手動での動作確認手順](../../verification/manual-check.md)の「大きいファイルの表示と行番号ジャンプ」

## 見直す条件

- WebView2 の版更新で、実際にレイアウトへ反映される `scrollHeight` の上限が 24,000,000px を下回るようになったとき（`MAX_TOTAL_HEIGHT_PX` を下げる必要がある）
- 可変行高の表示（継続行を折りたたまずに行高へ反映する方式）を採用するとき。スペーサ構成の前提そのものが変わるため、新しい ADR を要する
- スクロールバーでの行単位の精密な位置決めが実運用で必要になったとき
