# ADR-0001: Rust + Tauri 2系を初期技術スタックとして暫定採用する

- 状態: 暫定決定（Provisional）
- 日付: 2026-07-29
- 管理責任者: リポジトリメンテナー

## 背景

Hakutaku の段階0を開始するには、実装言語と GUI フレームワークを選ぶ必要があります。初期仕様 版1.10 の `DEC-002` と `TECH-003` は、実装言語に Rust、GUI フレームワークに Tauri 2系を初期技術スタックとして採用し、技術試作が要件を満たさない場合は再選定できると定めています。

ただし、主対象である Windows 10 IoT Enterprise LTSC の実機を現時点では継続的に検証できません。現行の開発環境で行う段階0だけでは、最古の対象 OS、WebView2 Runtime の構成、同じ端末で稼働する他の業務ソフトウェアとの同時稼働を確認できないため、`VER-001` は P13 の段階1検証が完了するまで `DEC-002` を暫定決定に保つよう求めています。

本 ADR の「暫定決定」は、実装判断の根拠にできない「提案中」とは異なり、段階0から初期技術スタックとして使用できる判断です。一方、P13 完了後の「採用済み」とも異なり、対象実機の検証結果によって再選定できます。

## 判断の基準

- 大容量・多数のログを扱う処理性能と、Rust コアプロセスのヒープ確保量を計測できること（`TECH-001`、`TECH-006`）
- Windows 10 / 11 の64ビット版、とくに最古の Windows 10 IoT Enterprise LTSC 実機で成立すること
- Evergreen WebView2 Runtime と、オフラインで配置する Fixed Version Runtime の両経路を扱えること
- インストーラーを前提とせず、実行時にネットワークから取得しない配布を実現できること
- GUI 層とコア層の境界を保ち、Tauri 2系が成立しない場合の再選定範囲を局所化できること
- CSP、最小 Capability、Rust コア経由のファイルアクセスによって、オフライン動作と信頼境界を維持できること

## 検討した選択肢

1. Rust + Tauri 2系を初期技術スタックとして暫定採用し、段階0と段階1で検証する
2. Python と GUI フレームワークを初期候補にする
3. 技術選定を留保し、LTSC 実機を確保するまで実装を開始しない

選択肢2は、実行速度と配布の懸念から Python を第一候補にしない `TECH-002` に反するため採用しません。選択肢3は実機固有の不確実性を残さない一方、実機を確保できない期間に、OS 非依存のコア設計や検証手段も進められません。段階0で進めてよい範囲を限定し、P13で最終判断する方が、不確実性と手戻りを管理しながら実装可能性を確認できます。

## 決定

初期技術スタックとして、実装言語に Rust、GUI フレームワークに Tauri 2系を暫定採用します。この決定は初期仕様 版1.10 の `DEC-002` と `TECH-003` に対応します。

段階0ではこの構成を用いて P00 以降の実装と技術試作を進めます。ただし、段階0の完了だけでは本 ADR を確定しません。`VER-001` に従い、P13 の段階1検証の完了ゲートをすべて満たした時点で、Rust + Tauri 2系を採用済みとして確定します。

再選定に備え、解析、索引、時系列マージ、設定、メモリ会計などのコア機能を GUI に依存しない Rust 側へ置きます。Tauri コマンドは薄い境界に保ち、フロントエンド固有の状態とコアのデータ処理を分離します。

## 結果

### 良い影響

- P00 から共通の技術的前提を置き、性能、配布、WebView2、GUI の成立性を段階的に検証できる
- Rust 側でログ処理とヒープ会計を一貫して実装できる
- Tauri 2系のフロントエンドと Rust コアの境界を利用し、GUI とデータ処理の責務を分離できる
- 段階1まで最終確定を遅らせることで、開発環境だけの成功を LTSC 実機の適合性と取り違えない

### 悪い影響とトレードオフ

- Tauri 2系は WebView2 Runtime に依存し、Evergreen 未導入環境では Fixed Version Runtime の配布・検出・保守が必要になる
- Windows 10 IoT Enterprise LTSC、最古ビルド、フォルダ ACL、他の業務ソフトウェアとの同時稼働は P13 まで未検証である
- P13 で要件を満たさない場合、GUI 層の再選定と再実装が必要になる
- 段階0では性能値を参考値にしかできず、技術選定の最終的な合否を判断できない
- GUI の切り戻し可能性を保つため、Tauri 固有処理をコアへ混入させない設計上の制約を継続して負う

## セキュリティとプライバシーへの影響

Tauri 2系の採用により WebView2 を信頼境界へ含めます。リリースビルドでは開発者ツールを無効化し、CSP と必要最小限の Capability を設定します。フロントエンドへ任意パスのファイルシステム権限を与えず、ファイル・フォルダの読み取りは Rust コアのコマンド経由に限定します。

Hakutaku は実行時に参照内容や診断情報をネットワークへ送信しません。WebView2 のユーザーデータ、診断ログ、一時ファイルは、それぞれ初期仕様 版1.10の保存・削除境界に従います。本 ADR は、診断ログへ記録できる実値や導入組織の管理責任を変更しません。

## 移行または切り戻し

既存の起動確認アプリを段階0の基点とし、コア機能を GUI 非依存の Rust クレートへ分離しながら Tauri 2系で実装します。P13 の完了ゲートを満たした場合は、検証記録を関連情報へ追加し、本 ADR の状態を採用済み（Accepted）へ更新します。

P13 の完了ゲートを満たさない場合は、本 ADR を確定しません。失敗した要件と実測結果を基に代替 GUI または技術スタックを比較し、新しい ADR で再選定します。その際は GUI 層を置き換え、再利用可能な Rust コアを維持することを第一案とします。新しい判断が採用された時点で、本 ADR を置き換え済み（Superseded）へ更新します。

## 検証

段階0では、現行の Windows 10 22H2 相当環境で、起動、日本語表示、ファイル選択、ログ読み込み、時系列統合表示、仮想スクロール、ヒープ会計、クリップボードコピーの骨格を確認します。Fixed Version Runtime 経路も段階0から通し、対象最古環境を下限とするビルド構成を維持します。段階0の性能値は参考値とし、採否の判定には使用しません。

確定判定は P13 の段階1で行います。最古の LTSC 実機における Fixed Version Runtime でのオフライン起動、Evergreen と Fixed Version の両経路、必要なフォルダ ACL、他の業務ソフトウェア稼働中のログ読み取りと性能、資源抑制、メモリ推移、安全な停止を検証します。P13 の全完了ゲートを満たしたことを、`VER-001` に基づく確定条件とします。

## 見直す条件

- P13 の最古 LTSC 実機で、Fixed Version Runtime を配置しただけでは起動できない
- 対象最古ビルドで必要な OS API または依存関係が利用できない
- Evergreen と Fixed Version の両 Runtime 経路を正式に保守できない
- 他の業務ソフトウェアの稼働中に、要求されるログ読み取り、応答性、メモリ上限、安全な停止を満たせない
- CSP、Capability、オフライン動作、ファイルアクセスのセキュリティ境界を実現できない
- 段階0で主要機能の骨格が成立せず、局所的な設計変更では解消できない

これらのいずれかに該当した場合は本 ADR を確定しません。影響と代替案を記録し、再選定の ADR で判断します。
