# ADR-0003: メモリ予約の帰属は明示的な確保 API で行う

- 状態: 採用済み（Accepted）
- 日付: 2026-08-01
- 管理責任者: リポジトリメンテナー

本 ADR の状態は、この変更が `main` へマージされた時点で採用済みになります。

## 背景

P02（メモリ会計とヒープ予算の基盤）は、グローバルアロケータの計装による全確保の集計（`TECH-006`、`PERF-008`）と、大きな確保前の予約・拒否（`PERF-010`）を実装する。当時の計画正本（P02 メモリ会計）は、実確保と予約の二重計上を避けるため「実確保時に予約から振り替える」会計契約を求めるが、**グローバルアロケータは、どの確保がどの予約トークンの下で起きたかを知らない**。帰属の方式を決めないと、原子的判定と振り替えのテストが実装できないため、同計画は着手前の ADR を必須としている。本 ADR がその判断を記録する。

## 判断の基準

- `PERF-010` の予約・拒否が段階0でも機能要件として完全に成立すること
- 計装（`alloc` / `dealloc` 経路）の内部で確保・ロックの再入を起こさないこと（無限再帰・デッドロックの防止）
- 非同期ランタイムのスレッド移動、並行処理、入れ子があっても帰属が壊れないこと
- `PERF-004`〜`PERF-006` の代表入力（単一 1 GB、10 ファイル合計 2 GB）を予算 2 GB で誤拒否しないこと
- 実装と保守のコストが小さく、以降のフェーズ（P06、P08、P10）が予約 API を安全に使えること

## 検討した選択肢

1. 明示的な確保 API（予約トークンに対する明示的な振り替え操作）
2. スコープ情報の伝播（予約トークンをタスクローカルな情報として持ち、アロケータが参照する）
3. 保守的な二重計上（帰属できない確保を予約と実確保の両方に計上したままにする）

## 決定

選択肢1（明示的な確保 API）を採用する。会計契約は次のとおり。

- **グローバルアロケータの計装は、全確保を無条件に `allocated_bytes`（現在値・ピーク値）へ計上する。** ここに帰属判定を持ち込まない。アロケータ内の処理は原子的な加減算だけとし、確保、ロック取得、ログ出力を行わない
- **予約**は `reserve(要求量)` で行い、`allocated_bytes + outstanding_reserved_bytes + 要求量 <= 予算` を `outstanding_reserved_bytes` に対する CAS ループで原子的に判定する。加算は `checked_add` で行い、オーバーフローする要求は拒否する
- **帰属（振り替え）**は、予約トークンを所有するコードが、大きな確保を行うその場所で振り替え操作（`mark_allocated(量)` 相当）を明示的に呼ぶことで行う。トークンの残量と `outstanding_reserved_bytes` が減り、実確保そのものはアロケータが自動計上する。これにより二重計上が解消される
- **ソフトしきい値の検知と通知**（解放処理の呼び出し、先読み停止）は、アロケータの `alloc` / `dealloc` 経路では行わない。予約・振り替え・定期確認の各操作時に、会計サービス側で判定する。しきい値処理は確保・ロック・ログ出力を伴うため、アロケータ内で行うと再入とデッドロックの危険がある

計画正本が求める8状況の帰属は、次のとおり定義する。

| 状況 | 帰属の定義 |
| --- | --- |
| 並行処理 | トークンは所有値であり、振り替えは原子的な減算。複数スレッドが別々のトークンで振り替えても競合しない |
| 非同期タスクのスレッド移動 | トークンは future と共に移動する所有値。スレッドローカルな情報に依存しないため、`await` 前後のスレッド変更の影響を受けない |
| 入れ子の予約 | トークンは相互に独立。親子関係を持たず、それぞれが予算に対して判定される |
| 第三者クレートの内部確保 | 帰属させない。`allocated_bytes` にのみ計上され、予約は消費されない |
| `realloc` | アロケータは差分だけを `allocated_bytes` へ計上する。予約下の拡張は増加分だけを明示的に振り替える。縮小分を予約へ戻さない |
| 確保の失敗 | 振り替えは確保の成功後に行う。失敗時はトークンの残量が減っておらず、トークンの破棄で予約全量が戻る |
| `dealloc` | `allocated_bytes` から減算する。消費済みの予約は復元しない |
| 帰属できない確保 | 予約の外の確保として `allocated_bytes` にのみ計上される。これによる予算超過はソフトしきい値と予約時の再判定で検知する |

計画正本の受け入れ条件のうち「実確保時に振り替えられ、二重計上されない」「予約量より少ない確保で差分が解放される」は、本方式でそのまま適用する（差し替え不要）。

## 結果

### 良い影響

- 帰属が決定的で、全状況が単体テストで検証できる
- アロケータが原子的な加減算だけの単純な実装に保たれ、再入・デッドロックのリスクが構造的にない
- スレッド移動・並行・入れ子に対して頑健で、非同期ランタイムの選択に依存しない

### 悪い影響とトレードオフ

- 予約の下で呼んだ第三者クレートの内部確保は振り替えられず、その間 `allocated_bytes + outstanding_reserved_bytes` が実態より大きく見える。予約量の見積もりは、振り替え対象の支配的なバッファ（ログ本文、索引、デコード結果、コピー用バッファ）に限定し、内部確保分は誤差として許容する
- 大きな確保を行う各経路に、振り替え操作の呼び出し規律が必要になる。呼び忘れは「予約が消費されないまま残る」＝安全側（過大計上）の誤差として現れ、予算を静かに超える方向には壊れない

## セキュリティとプライバシーへの影響

なし。会計値はバイト数のみで、参照データの内容を含まない。予約量の計算を `checked_add` で行うことは、不正なファイル長・タグ長に由来する巨大値への防御（`ERR-004` の考え方）を兼ねる。

## 移行または切り戻し

新設のメモリ会計クレートに閉じるため、既存コードの移行はない。方式を変える場合は新しい ADR で置き換え、予約 API（`reserve` とトークン）の利用側（P06、P08、P10）への影響を評価する。

## 検証

- 計画正本の受け入れ条件のうち、並行予約、振り替え、差分解放、確保失敗、破棄による解放、`realloc`、オーバーフロー拒否のテストが、本方式ですべて実装できること
- 代表ケース（単一 1 GB、10 ファイル合計 2 GB）で誤拒否が起きないこと（読み込み経路の接続後、P06 で実測）

## 見直す条件

- 振り替えの呼び出し規律が保てず、過大計上による誤拒否が運用上の問題になったとき
- 計装のオーバーヘッドが `TECH-001` と両立しないと判明したとき（P02 の性能測定の結果）
