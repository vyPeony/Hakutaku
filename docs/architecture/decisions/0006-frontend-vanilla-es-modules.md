# ADR-0006: フロントエンドはフレームワークとバンドラーを使わない素の ES モジュールで実装する

- 状態: 採用済み（Accepted）
- 日付: 2026-08-01
- 管理責任者: リポジトリメンテナー

本 ADR の状態は、この変更が `main` へマージされた時点で採用済みになります。

## 背景

P04（最小縦断）以降、フロントエンド（WebView2 側）に仮想スクロール、保持上限の運用、通知表示などの実体が入る。着手前に、UI フレームワーク（React、Svelte など）とビルドツール（vite など）を導入するかを決める必要がある。

判断を規定する要件は次のとおり。

- `PERF-012`: フロントエンドは可視範囲と前後バッファに限って行データを保持し、**取得済みの行を累積しない**。保持行数・バイト数の上限を守り、超過分を破棄する
- P04 の受け入れ条件は、自前キャッシュだけでなく**表示ライブラリ内部の行モデル・DOM・購読が保持する行参照**まで含めて上限以下であることを内部状態で観測することを求める（旧実装計画 P04）
- `SEC-001`（参照内容を送信しない）と `VER-004`（下限環境での動作）により、依存を追加するたびに全依存の検証が必要
- 現在の構成は `frontendDist = "../src"`（ビルドなしの直接配信）であり、P01・P03 のフロントエンドは素の HTML/CSS/JS で実装済み

## 判断の基準

- `PERF-012` の保持上限を**決定的に**観測・制御できること（ブラックボックスの内部キャッシュがないこと）
- 依存追加に伴うセキュリティ検証（`SEC-001`）と保守の費用が小さいこと
- GUI 層と Rust コア層の境界を薄く保ち、GUI フレームワークの差し替えが局所的な変更で済むこと（10.6）
- 初期リリースの UI 規模（ログ表示、タブ、通知、コピー）に対して過不足がないこと

## 検討した選択肢

1. 素の ES モジュール（フレームワークなし、バンドラーなし）＋自前の仮想スクロール
2. UI フレームワーク（React / Svelte など）＋バンドラー（vite など）＋仮想スクロールライブラリ
3. バンドラーのみ導入（TypeScript / vite）でフレームワークなし

## 決定

選択肢1を採用する。

- フロントエンドは `src/` 配下の素の HTML / CSS / JS（ES モジュール）で実装し、ビルド工程を導入しない（`frontendDist = "../src"` を維持）
- 仮想スクロールは自前実装とする。行データの保持（キャッシュ）、DOM ノード、イベント購読のすべてを自前コードが所有するため、`PERF-012` が要求する「フロントエンドが保持する全行データ」の計数を、推測ではなく自コードの観測点で行える
- npm の実行時依存を追加しない（devDependencies は Tauri CLI のみを維持）。`SEC-001` の検証対象が増えない
- JSDoc コメントで型を注記し、エディタの型検査を補助する（TypeScript のビルド工程は入れない）

選択肢2を退ける理由: 仮想スクロールライブラリや框架の内部キャッシュは P04 の受け入れ条件が明示的に警戒する累積源であり、内部の行モデル保持数を外から観測する費用が自前実装より高い。実行時依存の追加は `SEC-001` の検証費用も増やす。初期リリースの UI 規模に対して導入益が費用を下回る。

選択肢3を退ける理由: ビルド工程の導入だけでも、生成物と配信物の対応確認、ソースマップ、CI への組み込みが増える。型注記は JSDoc で足り、現段階では益が薄い。

## 結果

### 良い影響

- 保持上限の観測・制御が全て自前コードに閉じ、`PERF-012` の検証が決定的になる
- npm 実行時依存ゼロを維持し、`SEC-001` / `VER-004` の検証範囲が増えない
- 配信物 = ソースであり、ビルド起因の不具合層が存在しない

### 悪い影響とトレードオフ

- 仮想スクロール、状態管理、DOM 更新を自前で書く実装費用がかかる。ただし対象は単一のログ表示が中心であり、汎用フレームワークの機能の大半は不要
- UI 規模が大きく育った場合、素の JS の保守性が下がり得る（見直す条件に記載）

## セキュリティとプライバシーへの影響

実行時依存を追加しないため、`SEC-001`（参照内容を送信しない）の検証対象が増えない。CSP（`SEC-011`）は既存のまま変更しない。

## 移行または切り戻し

GUI 層と Rust コア層の境界（範囲取得契約などの IPC 契約）を保つため、フレームワークを後から導入する場合も Rust 側の変更は不要である。フロントエンドの差し替えは `src/` 配下に閉じる。

## 検証

- P04 の受け入れ条件（保持上限・破棄・再取得の内部状態観測、DOM ノード数の制限）が自前実装で満たされること

## 見直す条件

- UI の規模・複雑性が増し、素の JS の保守費用がフレームワーク導入の費用を上回ったとき
- P13 で GUI フレームワークの再選定（`DEC-002` の見直し）が発生したとき
