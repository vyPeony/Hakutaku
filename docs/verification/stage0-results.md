#### 2.3.1 機能ゲート: 保持行数・保持バイト数（`CFG-022`）

`retentionLimits`: `maxRows=10,000`、`maxBytes=67,108,864`（既定値）。`sampleCount=241`。

**`withinRetentionLimitsForAllSamples: false`。不成立です。**

- 241サンプル中 **18件（7.5%）** で `retainedRows` が上限（10,000）を一時的に超過した。観測値: 10,240（12件）、10,752（4件）、11,264（2件）。最大超過量 **+1,264行（+12.6%）**

- 保持上限の初期値（`maxRows=10,000`）は P04-3（約30万行規模の実測）で決めた値であり、2000万行規模での再検証は今回が初めてです。今回の結果は、初期値の再検討（P13 または後続の課題）の材料になり得ます

## 3. `SEC-001` 送信監視（P12-8）

### 3.1 監視位置の定義

ネットワーク上の TLS 暗号文だけを見ても、実際に送信されていても平文のマーカーは現れません。本セッションでは、暗号化前ペイロードのプロセス単位キャプチャ（ETW/pktmon 等、管理者権限が必要なツール）は使用できないため、次の3層で代替しました。

| 層 | 内容 | 節 |
| --- | --- | --- |
| (a) 静的監査 | 依存クレートの一覧と、Hakutaku 自身のコード（`crates/`、`src-tauri/`）に外部通信の実装・呼び出しがないことの確認 | [3.2](#32-静的監査-a) |
| (b) 接続列挙 | Hakutaku の全プロセス（子孫含む）の TCP 接続を2秒間隔・60秒間、`Get-NetTCPConnection` で列挙・記録 | [3.3](#33-接続列挙-b) |
| (c) 陽性対照 | Hakutaku に送信機能を追加せず、別プロセスで同じ列挙方法により接続を検知できることを確認 | [3.4](#34-陽性対照-c) |

**この構成では「ペイロードにマーカーが現れないこと」を暗号化前の内容として直接観測できません。** これは本セッションの限界であり、ペイロード内容そのものの監視（ETW/pktmon 等）は利用者環境での実施項目として引き継ぎます。

### 3.2 静的監査 (a)

#### 3.2.1 推移的依存（`Cargo.lock`）の評価手法

`Cargo.lock` には、`tauri` 経由で解決される `reqwest`・`hyper`・`tokio` 等、ネットワーク API を持ち得るクレートが推移的依存として記録されます。**`Cargo.lock` に名前が現れることだけを根拠に、そのクレートが実際に組み込まれていると判断しません。** 評価は次の手順で行います。

1. 対象クレートが、ビルド対象である Windows ターゲット（`x86_64-pc-windows-msvc`）の依存グラフに現れるかを `cargo tree --target x86_64-pc-windows-msvc` で照合する
2. Windows ターゲットのグラフに現れないもの（Linux 等の別プラットフォーム限定の条件付き依存としてのみ解決されるもの）は、本プロダクトの配布物に含まれないため、**不使用（`not used`）** と判定する
3. Windows ターゲットのグラフに現れるものは、上記の分類（Tauri／WebView2 の IPC・カスタムプロトコル・ウィンドウ管理のための利用か）まで確認する

この手順は Dependabot のセキュリティアラート対応で実績のある評価方法であり、アラート対象が Linux 限定の推移依存だった場合は「不使用」を理由に対応を判断しています。

**結論: Hakutaku 自身のコード（`crates/`、`src-tauri/`、`src/`）は外部通信経路を実装・呼び出していません。** 依存クレートの中には HTTP/ネットワーク関連の型を持つものがありますが、いずれも WebView2/Tauri の内部処理（IPC、カスタムプロトコル、ウィンドウ管理）のために使われており、実行時通信の主体は WebView2 ランタイム自身です（3.3節参照）。

### 3.4 陽性対照 (c)

Hakutaku には送信機能を追加せず、別プロセス（PowerShell）だけで実施しました。

**(1) 開いたポートでの検知（監視方法そのものが機能することの確認）:** 別プロセスの TCP リスナー（`pwsh`、PID 12516）と別プロセスの接続側（`pwsh`、PID 2484）を起動し、3.3節と同じ列挙方法（`Get-NetTCPConnection`）で3回ポーリングしたところ、**6件すべてで検知できました**（PID・ポートの対応も正しく取得）。**同じ監視方法で、意図的に確立した接続を確実に検知できることを確認しました。**

### 10.1 採用した修正方針

#### 保持行数上限の一時超過: fetch/evict の順序競合

`src/log_view.js` の `renderVisibleRows` は、1回のスクロール処理内で「不足チャンクの取得を開始する（`ensureChunksLoaded`、非同期・完了を待たない）→ その時点でキャッシュ済みのチャンクだけを対象に破棄判定を行う（`evictFarChunks`）」の順に実行していました。大規模ファイルでは1回のスクロールステップで多数の新規チャンクが必要になり得るため、複数チャンクの非同期取得が次々と完了してキャッシュへ格納されるタイミングと、次のスクロールステップで `evictFarChunks` が呼ばれるタイミングの間に、保持行数・保持バイト数が一時的に上限を超える窓が生じていました（7節の項目1、241サンプル中18件・最大+12.6%）。

検討した2案のうち、**(b) チャンク取得完了直後（キャッシュへ格納した直後）に破棄判定を再実行する方式**を採用しました。

- (a) 取得中（in-flight）チャンクの予定行数・概算バイト数を破棄予算へ前もって算入する方式は、`raw_text` の実バイト数が応答到着まで判明しないため見積もり方法自体に新しい仕様判断を要し、実装も複雑になる
- (b) は実測値だけで判定するため見積もり誤差が生じず、既存の `selectChunksToEvict`／`evictFarChunks`（変更なし）をそのまま追加で呼ぶだけで実装できる。既存の軽量な純粋関数呼び出しを1回増やすだけで、DOM 操作・IPC 呼び出しを伴わないためスクロール応答性への悪影響もない

実装は `src/log_view.js` の `fetchChunk` 内、`state.chunkCache.set(...)` の直後に `runPostFetchEvictionPass()`（新設。内部で `computeCurrentRenderTargets()` → `evictFarChunks(...)` を呼ぶだけ）を追加しました。判断の詳細は同関数の JSDoc に記載しています。

#### 末尾到達不能: `scrollHeight` クランプ

`src/virtual_scroll.js` に、スペーサ合計高さの上限 `MAX_TOTAL_HEIGHT_PX = 24_000_000`（実測クランプ値 26,843,546px を安全側に下回る値。根拠は同定数の JSDoc）を導入し、総理論高さ（`totalItems × ROW_HEIGHT_PX`）がこれを超える場合に、スクロール座標 ↔ 行インデックスの比例写像へ切り替える3つの関数を追加しました（既存の `computeVisibleRange`／`computeSpacerHeights`／`computeScrollTopForRowIndex` は変更せず、クランプ未満の通常規模ではそれらへそのまま委譲することで回帰を避けています）。

- `computeVisibleRangeForScroll`: スクロール位置の比例（0〜1）を総行数に掛けて先頭行インデックスを決める。比例が1（末尾）のとき必ず `endIndex === totalItems` になることを保証
- `computeSpacerHeightsForScroll`: 上下スペーサの高さの**合計**が、可視範囲の位置・大きさ（バッファが境界でクリップされるか否か）によらず常に厳密に「実効総高さ − 実描画行の高さ」と一致するよう配分する
- `computeScrollTopForRowIndexScaled`: 上記の逆変換（行番号ジャンプ用）

`computeSpacerHeightsForScroll` は当初、各スペーサを個別に一律の係数（`scale`）で縮小する素朴な実装でしたが、**2000万行規模の実機検証で以下の再発見があり、実装をやり直しました**（末尾に別記）。素朴な実装では可視範囲のウィンドウ幅（バッファが境界でクリップされるか否かで73〜111行程度の幅）によって「スペーサ2つ＋実描画行の高さの合計」が数千px単位で変動し、`viewport.scrollHeight` がスクロール位置によって微小に揺れることが分かりました。この揺れが、スクロール座標→行インデックスの比例写像の分母（ブラウザの実際の最大スクロール位置）を不安定にし、末尾到達判定を僅かに外すことがありました。現在の実装は、スペーサ2つの高さの合計を可視範囲の位置によらず常に厳密な定数値に固定することで、この揺れの発生源そのものを解消しています（詳細は `computeSpacerHeightsForScroll` の JSDoc）。

`src/log_view.js` 側は、`renderRows` で `computeSpacerHeightsForScroll` を、`handleJumpRequest` で `computeScrollTopForRowIndexScaled` を使うよう置き換えました。Ctrl+Home／Ctrl+End は、比例写像でもちょうど比例0・比例1（先頭・末尾到達）に一致する境界値そのものであるため変更していません（`handleViewportKeydown` の JSDoc に理由を明記）。

### 10.6 発見事項: ラウンドトリップ走査の診断値と、Ctrl+End 相当の主判定の乖離（新規論点）

2000万行規模で、`reachedEndOfFile`（240段階のラウンドトリップ走査中に一度でも下スペーサが0pxになったか）が **false** でした。調査の結果、次のことが分かりました。

1. `computeSpacerHeightsForScroll` の修正（10.1節）により、`viewport.scrollHeight` は可視範囲の位置によらず厳密に24,000,000pxで一定になりました（スモークテストで確認済み）
2. しかし `measurement.js` のラウンドトリップ走査は、走査**開始時点で一度だけ**読み取った `maxScrollTop` を、以後240段階・数十秒にわたって固定の目標値として使い続けます。2000万行規模の実機では、この固定目標へ向けて `viewport.scrollTop` を設定しても、**実際に反映される `scrollTop` が理論値より最大で約36,500px（約0.15%、行数にして最大1万行未満）小さい値にとどまることがありました**
3. これは WebView2（Chromium）の layout 側の値（`scrollHeight`）と、実際に適用されるスクロール可能範囲（コンポジタ側が使う値と推測されます。内部機構は未確定）が、極端に大きなスクロール高さの下で、多数の連続した再描画（チャンク取得・破棄の連鎖）が発生している最中は一時的に同期しきれないことがある、という新しい観察です
4. 実際の利用者操作（Ctrl+End・`handleViewportKeydown` の `viewport.scrollTop = viewport.scrollHeight`、または OS のスクロールバーつまみを一番下までドラッグする操作）は、走査のように古い固定値を使い回すのではなく、その都度**最新の** `scrollHeight` を読み直します。`measurement.js` にこれと全く同じ式による検証（`reachedEndOfFileViaLiveJump`）を追加し、かつ一発勝負ではなく「読み直して設定→待つ」を最大8回まで再試行するようにしたところ（コンポジタ側が追いつくのを待つ）、**2000万行規模でも確実に末尾（下スペーサ0px）へ到達することを確認しました**

**この節の結論**: `reachedEndOfFile`（診断用の参考値）が false のままなのは、走査スクリプトが古い固定目標を使い続けるという**検証方法側の制約**であり、`computeSpacerHeightsForScroll` の実装自体の不具合ではありません。`reachedEndOfFileViaLiveJump`（実際の Ctrl+End と同じ式・同じ経路の検証）が true であることをもって、(b) の主判定を成立としました。

> **後日の追記（[Issue #21](https://github.com/vyPeony/Hakutaku/issues/21)）**: この節が「コンポジタ同期の遅延と推測される」と記録した現象は、その後に見つかったブラウザのスクロールアンカリング（`overflow-anchor`）による自走で説明が付きます。`src/log_view.js` の `renderRows` が行 DOM を作り直すたびにブラウザが `scrollTop` へ補正を加え、その補正が次の再描画を呼ぶ正のフィードバックになるというものです。`src/styles.css` の `.log-viewport` へ `overflow-anchor: none` を追加して解消しました。

> 根拠（`fetch_log_range` をスタブした2000万行のハーネスでの再現。実機の計測モードではありません）: 走査直後に Ctrl+End 相当（`scrollTop = scrollHeight`）を1回だけ行うと、いったんは下スペーサが0pxになった後、**操作していないのに毎秒約33,000pxずつ末尾から離れ**、2秒で下スペーサが56,162pxまで開きました。本節が記録した「理論値より最大約36,500px手前」は、この自走の途中を捉えた値と整合します。`overflow-anchor: none` を与えると `scrollTop` は末尾（下スペーサ0px）で完全に静止しました。
>
> ハーネスは実機の計測モードとは環境が異なる（IPC はスタブ、`requestAnimationFrame` をタイマーで代替、コンポジタ非稼働）ため、コンポジタ同期の遅延が併存しないことまでは確認できていません。実機の計測モードでの再確認は未実施です。以下の残存リスクの記述は、当時の記録としてそのまま残します。

**残存リスクとして正直に記録します**: 今回の再試行（最大8回・500ms間隔）は自動検証のための実装であり、**実際の製品コード（`handleViewportKeydown` の Ctrl+End ハンドラー）には再試行ロジックを追加していません**（今回のスコープはフロントエンドの計測スクリプトへの検証追加のみで、キー入力ハンドラーへ非同期の再試行を持ち込むことは、原因（コンポジタ同期の遅延）が未確定な段階では新たな複雑さ・挙動変更を招くため見送りました）。連続した高頻度の再描画（自動走査のような負荷）の直後に利用者が Ctrl+End を1回だけ押した場合、理論上はごく僅か（0.15%未満）末尾に届かない可能性が残ります。通常の利用パターン（連続スクロール走査のような負荷がない状態での単発の Ctrl+End）では発生しにくいと推測されますが、**画面実操作での確認はできていません**（本書冒頭のとおりヘッドレス環境のため）。この点は利用者による画面確認、または後続の課題として追加確認することを推奨します。

> [!NOTE]
> **後日の追記2（[Issue #23](https://github.com/vyPeony/Hakutaku/issues/23)、2026-08-17）**: #21 の修正を適用した実機の計測モードで、200万行（クランプ・比例写像が有効な最小規模。`generate-test-log.ps1 -LineCount 2000000 -Seed 42` で生成、結果ファイル `measurement-p04-1786895142.json`）を再計測し、次を確認しました。
>
> 1. Ctrl+End と同じ式のジャンプは、再試行なしの**1回目で**下スペーサ0pxへ到達した（今回 `measurement.js` へ追加した試行記録 `liveJumpEndAttemptsUsed` = 1。Ctrl+Home 側も1回目で到達）
> 2. 到達後、`scrollTop` へ一切書き込まずに約3秒間観測しても、下スペーサは0px・`scrollTop` の変位は0pxのまま保たれた（`stayedAtEndDuringIdle` = true、`scrollTopDriftPx` = 0）
> 3. ホイール相当の相対移動（120px × 16回。上スペーサが約1,320pxまで伸びる、#21 の自走が起きていた条件）を止めた後の約3秒間も、`scrollTop` は1pxも動かなかった（`scrollTopStableAfterRelativeMoves` = true、`driftPx` = 0）
>
> この結果から、上の残存リスク（連続した高頻度の再描画の直後に、単発の Ctrl+End が僅かに末尾へ届かない可能性）は実機でも解消と確認しました。当時「コンポジタ側の同期遅延と推測される」とした現象は #21 のスクロールアンカリングによる自走で説明が付き、**製品コード（`handleViewportKeydown` の Ctrl+End ハンドラー）へ再試行を追加する必要はありません**。`measurement.js` の再試行（最大8回）は、遅い環境で1回の待機（500ms）に取得・描画が収まらない場合の余裕として残し、理由のコメントを実測に合わせて更新しました。
>
> あわせて、絶対値を設定する走査では段階の合間の自走が次の代入で上書きされて構造的に観測できないため（#21 が過去の計測を2度通過した理由）、相対移動＋放置の観測（`relativeScroll`）を計測モードへ追加しました。#21 型の退行の再発検知になります。2000万行規模の再計測は行っていません（#23 の対象範囲は200万行。2000万行で当時観測した乖離は、#21 の再現ハーネスの実測で自走として説明済みです）。
