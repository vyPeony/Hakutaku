## 位置づけ

本書は、Hakutaku を実際に起動し、**画面と操作を通して実装済み機能を一通り確認する**ための手順です。手順の正本は本書、実施結果の記録は Issue / PR、段階0検証シナリオの実施結果は[段階0検証記録](stage0-results.md)が正本です。本書は結果を記録する場所ではありません。

- 対象は初期リリースの範囲（テキストログのビューア）です。検索・絞り込み、SQLite・DICOM、索引キャッシュ、ドラッグ＆ドロップは実装対象外のため、確認項目に含みません（[`PROD-009`](../requirements/functional.md)）。
- 解析ロジックそのものは自動テスト（`cargo test --workspace`）で確認済みです。本書は、自動テストでは確認できない**画面表示と実際の操作**を対象とします（[段階0検証記録](stage0-results.md)がヘッドレス環境のため「利用者確認」へ引き継いだ範囲に対応します）。
- ビルド・テスト・静的解析・整形の標準コマンドは[開発ワークフローの「段階0の標準検査」](../development/workflow.md#段階0の標準検査)にあります。本書はそれらの代わりではなく、追加で行う手動確認です。

**実施しなかった項目は「未実施」として記録してください。** 実行していない手順の結果を推測で埋めないでください。

## 2. サンプルログの生成

[`scripts/start-manual-check.ps1`](../../scripts/start-manual-check.ps1) を使うと、本章のサンプル生成から[3章](#3-アプリの起動と設定ファイルの配置)のアプリ起動までを1コマンドでまとめて済ませられます（既定で毎回ビルドします。変更が無ければ数秒で終わります）。

```powershell
./scripts/start-manual-check.ps1
```

主な引数は次のとおりです（詳細は同スクリプトのコメントベースヘルプを参照）。

| 引数 | 用途 |
| --- | --- |
| `-ConfigMode normal\|invalid\|none` | 実行ファイル直下に配置する `hakutaku.yaml` の状態を選ぶ（既定は `normal`） |
| `-SkipBuild` | ビルドを省略し、既にある実行ファイルのまま進める（既定は毎回ビルド。省略した結果、実行ファイルより新しい変更が `src/`・`crates/`・`src-tauri/` にある場合は警告します） |
| `-NoLaunch` | 準備だけ行い、アプリを起動しない |
| `-SampleDir <パス>` | サンプル一式の置き場所を変える（既定は `%TEMP%\hakutaku-samples`） |
| `-LargeLineCount <行数>` | `generate-sample-logs.ps1` の同名引数へそのまま渡す（省略時は既定 300,000）。`0` で `08-large.log` を生成しない |
| `-RegenerateSamples` | サンプルが既にあっても生成し直す |
| `-CleanUp` | 後片付けだけを行う（[5章](#5-後片付け)） |

`-SampleDir` に**古いサンプル一式**（本書のサンプルより前に生成された、`09-mixed-*.log` や `10-medium-100k.log` を含まない一式など）が残っている場合、`start-manual-check.ps1` は既存の `hakutaku.yaml` が指すファイルの存在を確認し、1件でも見つからなければ `-RegenerateSamples` を付けなくても自動で作り直します（見つからなかったファイル名と理由を表示します）。指すファイルがすべて存在すれば、従来どおり生成を省略します。

**サンプルが増えたときは、この自動判定では作り直されません。** 古い一式が指すファイルはすべて存在するため「使える状態」と判定され、新しいサンプル（例: `11-wide-line.log`）だけが無い状態のまま起動します。本書の更新でサンプルが増えた後に初めて確認を行う場合は、`-RegenerateSamples`（`start-manual-check.ps1`）または `-Force`（`generate-sample-logs.ps1`）を明示して作り直してください。左ペインに本書のサンプルが1つも欠けていないことを確認するのが確実です。

サンプル生成そのものの詳細は次のとおりです。[`scripts/generate-sample-logs.ps1`](../../scripts/generate-sample-logs.ps1) が、本書の各項目に必要なサンプルを決まった名前で一度に生成します。

```powershell
./scripts/generate-sample-logs.ps1
```

既定の生成先は `%TEMP%\hakutaku-samples` です。**リポジトリ内は生成先に指定できません**（試験データをリポジトリへ残さないため、エラーで停止します）。

| 引数 | 用途 |
| --- | --- |
| `-OutputDir <パス>` | 生成先を変える（既定は `%TEMP%\hakutaku-samples`） |
| `-LargeLineCount 0` | 大きいファイル（`08-large.log`）を作らず短時間で済ませる。[4.9](#49-大きいファイルの表示と行番号ジャンプ)・[4.10](#410-選択とクリップボードコピー)は実施できなくなる（`10-medium-100k.log` は事前定義データソースから常に開けるようにするため、この指定でも常に生成される） |
| `-Force` | 生成先に既存の内容があっても上書きする |

## 3. アプリの起動と設定ファイルの配置

設定ファイルは、**実行ファイルと同じフォルダの `hakutaku.yaml` 固定**です（`CFG-014`）。開発中の実行では実行ファイルは次の位置にあります。

| 実行方法 | 実行ファイルと設定ファイルの位置 |
| --- | --- |
| `npm run tauri dev` | `target/x86_64-pc-windows-msvc/debug/` |
| `npm run tauri build -- --no-bundle` | `target/x86_64-pc-windows-msvc/release/` |

**画面（`src/` の HTML・CSS・JS）を直した場合も、再ビルドしないと反映されません。** フロントエンド一式は `src-tauri/Tauri.toml` の `frontendDist = "../src"` により実行ファイルへ埋め込まれるためです。[`scripts/start-manual-check.ps1`](../../scripts/start-manual-check.ps1) は既定で毎回ビルドするので、通常は意識する必要はありません（変更が無ければ数秒で終わります）。`-SkipBuild` を付けた場合だけ、実行ファイルより新しい変更があると警告が出ます（[Issue #24](https://github.com/vyPeony/Hakutaku/issues/24)）。

設定を差し替えるには、生成した YAML をその位置へコピーします（アプリは `hakutaku.yaml` を自動生成・上書きしません）。

```powershell
Copy-Item "$env:TEMP\hakutaku-samples\hakutaku.yaml" target/x86_64-pc-windows-msvc/debug/hakutaku.yaml
```

設定の変更は再起動時に反映されます（`CFG-006`）。確認中は、アプリを終了してからコピーし直してください。

[`scripts/start-manual-check.ps1`](../../scripts/start-manual-check.ps1) を使っている場合は、アプリを終了してから `-ConfigMode invalid -SkipBuild -NoLaunch` のように再実行すると、同じ配置をコマンド1つで行えます（[2章](#2-サンプルログの生成)）。

## 4. 確認手順

各項目は「操作」と「期待結果」の対で書いています。期待結果が得られない場合は、そこで止めずに残りの項目も実施し、**どの項目が期待どおりでなかったか**を記録してください（`ERR-001` により、一つの失敗で他の閲覧は止まらない想定です）。

以降の項目で「ファイルを開く」から選ぶとしているファイルは、生成した `hakutaku.yaml` を配置していれば、[4.3](#43-事前定義データソース)のとおり左ペインの事前定義データソースからも同じ内容で開けます。どちらから開いても解析結果は同じであるため、各項目の手順は「ファイルを開く」からの操作で統一して記載しています。

### 4.1 3つの起動経路

設定ファイルの状態によって、起動経路が3つに分かれます（`CFG-014`〜`CFG-016`）。

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | 実行ファイル直下に `hakutaku.yaml` を**置かずに**起動する | 画面上部に「hakutaku.yaml が見つからないため、組み込み既定値で起動しました。」という通知が出る。操作はブロックされず、「ファイルを開く」は使える | `CFG-015`、`CFG-017` |
| 2 | 生成した `hakutaku.yaml` を実行ファイル直下へ置いて起動する | 通知は出ない。左ペイン「参照対象」に、設定に書いた22件（`-LargeLineCount 0` で生成した場合は21件。`08-large.log` の分が無いため）が「設定」の印付きで、設定の記載順（`01 基本のログ（2,000行）` から `10 大きめのログ（100,000行）` まで）に並ぶ | `CFG-003`、`CFG-014` |
| 3 | `hakutaku-invalid.yaml` を `hakutaku.yaml` という名前でコピーして起動する | 画面上部に安全モードの警告が出て、**ファイル名・行・列・理由**を含むエラーが3件並ぶ（`memory.budget_mib` が文字列、`clipboard.max_copy_lines` が -1、未知の設定項目 `unknown_section`）。設定由来のデータソースとプロファイルは一覧から消えるが、「ファイルを開く」は使える | `CFG-016`、`CFG-017` |

確認後は手順2の正常な `hakutaku.yaml` に戻してから先へ進みます。

### 4.2 ファイルを開く

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | 「ファイルを開く」を押し、`01-basic-utf8.log` を選ぶ | 左ペインに「アドホック」の印付きで対象が追加され、状態が「読み込み済み（2,000 行）」になる。タブが1つ増え、本文が表示される | `LOG-001`、`LOG-020`、`CFG-017` |
| 2 | 表示内容を確認する | 行番号と本文の列が並ぶ。本文列は原文（`2026/07/28 09:00:00.000 起動処理を開始しました [行番号=0]`）がそのまま表示される。**行一覧に解析済みの日時列は無い**（原文が先頭に日時を含むため、同じ日時を2度並べない。[Issue #78](https://github.com/vyPeony/Hakutaku/issues/78)） | `ERR-003` |
| 3 | 先頭行をクリックして `Ctrl+C` し、メモ帳などへ貼り付ける | 行の**原文がそのまま**貼り付けられる（[ADR-0011](../architecture/decisions/0011-copy-raw-text-only.md)。列の選択は無く、コピーは常に原文） | `COPY-001`、`COPY-002` |

### 4.3 事前定義データソース

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | 左ペインの `01 基本のログ（2,000行）` をクリックする | パスを指定せずに開ける（設定の名前だけで開く） | `CFG-003`、`SEC-012` |
| 2 | 左ペインの `10 大きめのログ（100,000行）` をクリックする | 完了後に状態が「読み込み済み（100,000 行）」になる。読み込みが速く終わる環境では、読み込み中の進捗表示と「キャンセル」は見えないことがある（[4.9](#49-大きいファイルの表示と行番号ジャンプ) 手順6も参照） | `CFG-003`、`PERF-007` |

事前定義データソースは、[2章](#2-サンプルログの生成)で生成する通常のログファイルすべて（日時書式6種、文字コード3種、継続行、未確定行、先頭の日時なし行、大きいファイル（`08-large.log` は生成した場合だけ）を含む）を指すため、左ペインだけで本章の確認項目の対象ファイルを概ね網羅して開けます。すべて正常に開けるものだけで構成しており、エラー表示の確認は [4.12](#412-共有違反と再試行) で行います。

### 4.4 日時書式と元の精度

`02-dt-001.log`〜`02-dt-006.log` を順に開いて、解析された日時を確認します。

**解析済み日時の値そのものを画面から読む手段は、現在ありません。** 行一覧の日時列は [Issue #78](https://github.com/vyPeony/Hakutaku/issues/78) で廃止し（原文が先頭に日時を含むため同じ日時を2度並べない）、残っていたコピー列も [Issue #85](https://github.com/vyPeony/Hakutaku/issues/85) で廃止しました（コピーは常に原文そのまま。[ADR-0011](../architecture/decisions/0011-copy-raw-text-only.md)）。正規化した日時の提示は、時系列統合表示の改修（[Issue #82](https://github.com/vyPeony/Hakutaku/issues/82)）で行う予定です。

**そのため、元の精度（`LOG-024`／`LOG-025`）が保たれているかの確認は自動検査が担います。** [`scripts/check-gui.mjs`](../../scripts/check-gui.mjs) のシナリオ3（日時精度）が `fetch_log_range` の応答（IPC 境界）の桁数を直接確認し、書式ごとの解析結果は Rust 側の単体テスト（`crates/parser`、`crates/core-services`）が確認します。

本節で手で確認するのは、**各書式のファイルが日時付きとして解析されるか（日時未解析の生表示にならないか）**と、書式指定の効き方（`LOG-022`、`CFG-008`）です。生表示かどうかは、行の背景色がわずかに変わり本文が斜体になることで見分けます。

| # | ファイル | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | `02-dt-001.log` | 生表示にならない（`YYYY/MM/DD HH:mm:ss.SSS` として解析される） | `LOG-009` |
| 2 | `02-dt-002.log` | 生表示にならない（ハイフン日付区切り・コロンのミリ秒区切りの `YYYY-MM-DD HH:mm:ss:SSS` も既知書式） | `LOG-009` |
| 3 | `02-dt-003.log` | 生表示にならない（1/100 秒2桁の書式） | `LOG-009`、`LOG-025` |
| 4 | `02-dt-004.log` | 生表示にならない。`hakutaku.yaml` の `datetime_format: LOG-DT-004` が使われ、自動判定を行わずに解析される（設定を外した場合は手順7のとおり生表示になる） | `CFG-008`、`LOG-022` |
| 5 | `02-dt-005.log` | 生表示にならない（秒までの書式） | `LOG-009` |
| 6 | `02-dt-006.log` | 生表示にならない（分までの書式） | `LOG-009` |

手順4は**設定の有無で結果が変わります。** `YYYY/MM/DD HH:mm:ss:SS`（`LOG-DT-004`）だけで構成されるファイルは、内容からは `LOG-DT-005`（`YYYY/MM/DD HH:mm:ss`）と区別できず、自動判定では必ず両方が同時に成立します。貪欲マッチで推測しないため（`LOG-022`。根拠は `crates/core-services/src/loader.rs` の doc コメント「日時書式の決め方」）、**書式を明示していないファイルは日時未解析の生表示になります。**

生成される `hakutaku.yaml` には、`02-dt-004.log` 向けに `datetime_format: LOG-DT-004` を明示したプロファイルが入っているため、設定を置いた状態では上表のとおり解析されます（`CFG-008`）。続けて、次の対比も確認してください。

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 7 | `hakutaku.yaml` を一時的に退避して `02-dt-004.log` を開き直す | **全行が「日時未解析の生表示」になる**（行の背景色がわずかに変わり、本文が斜体になる）。見出し「02-dt-004.log: 日時未解析の生表示で開きました」という案内のダイアログ（エラーと同じ機構の情報表示）が表示される。ダイアログを閉じると、左ペインのこの行に「プロファイル」（既定は「指定しない」）と「日時書式」（既定は「自動判定」）の2つのセレクトと「再解析」ボタンが現れている | `LOG-022` |

手順8・9の「日時書式」は、`log_profiles` の定義とは独立した指定です。**設定ファイルを書かずに開いたファイルでも、UI の操作だけで日時付き表示へ再解析できます。** 手動で選んだ書式は、プロファイルの `datetime_format` 設定より優先されます。

2つのセレクトはどちらか一方だけでも、両方同時でも指定できます。どちらも既定（「指定しない」「自動判定」）のまま「再解析」を押した場合は、結果が変わらないため何も起きません。

手動で選んだプロファイル・日時書式は、その1回の読み込み限りの指定です（Rust 側は保持しません）。同じ対象で「再試行」を押した場合や、退避されたソースが再読み込みされた場合は、自動解決・自動判定へ戻ります。恒久的に同じ書式で開きたい場合は、`hakutaku.yaml` のプロファイルへ `datetime_format` を書きます（手順4・10）。

| 2 | `logs` 配下の診断ログを開く | ここまでの操作（起動経路、対象を開く、文字コードの判定経路、確定した日時書式と「日時書式の決定経路」、コピーの行数・バイト数）が記録されている。決定経路は、[4.4](#44-日時書式と元の精度)の手順4・10（設定の `datetime_format` で決まる）が「プロファイル指定（datetime_format）」、手順8・9（UI で選んで再解析）が「UI での手動選択」、それ以外（手順1〜3・5〜7）が「内容からの自動判定」と記録される。**ログ本文そのものは記録されていない** | `DIAG-005`、`SEC-004` |
| 3 | アプリを終了して再度起動する | `temp` の内容が起動時に清掃される | `SEC-009` |
| 4 | 新規作成直後の `logs\hakutaku.log` を開き、冒頭9行を確認する | `# Hakutaku 診断ログ` で始まり、実値をマスキングしない方針（「マスキングせずそのまま記録します」）と、`logs` フォルダの閲覧制限・持ち出し・保管・削除が利用者・導入組織の責任範囲であること（「利用者・導入組織の責任範囲です」「SEC-005」）が明記されている | `DIAG-003`、`DIAG-004`、`SEC-005` |
| 5 | ローテーションで新しくなった `hakutaku.log`（`hakutaku.log` → `hakutaku.1.log` への退避直後）の冒頭も確認する。既定は1ファイル10 MiBのため、早く再現したい場合は `hakutaku.yaml` の `diagnostics.rotate_mib`（`CFG-020`、最小値1）を小さくしてから操作し、退避を発生させてよい | 退避後の新しい `hakutaku.log` の冒頭も手順4と同じ見出しになっている。ローテーションの発生自体と世代数上限（超過世代の削除）は自動テスト（`crates/diagnostics/tests/diagnostics.rs` の `rotates_and_prunes_generations_beyond_limit`）で確認済み。退避後の新しい現行ファイルと退避された `hakutaku.1.log` 双方の見出し内容は、同ファイルの `rotated_files_all_start_with_required_header` で自動検証済みのため、本項目は実機での目視確認として実施する | `DIAG-002`、`SEC-005` |

診断ログと画面表示は仕様によりフルパス等の実値をマスキングしません（`DIAG-003`／`DIAG-004`、`ERR-002`）。確認に使ったログの取り扱いは利用者・導入組織の責任範囲です（`SEC-005`）。

### 4.17 横に長い行の表示

行は折り返さない設計のため（行高を一定に保つ仕様）、極端に長い行があれば横スクロールが必要になります。確認するのは、その横スクロールが**ログの表示領域の内側だけで起きる**ことです（[Issue #78](https://github.com/vyPeony/Hakutaku/issues/78)。以前はウィンドウ全体に横スクロールバーが出て、左ペインごと画面外へ流れていました）。

`11-wide-line.log`（50行。うち5行が 2,000〜4,000 文字）を使います。左ペインの事前定義データソース `11 横に長い行（数千文字）` からも開けます。

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | `11-wide-line.log` を開く | 5行目・15行目・25行目・35行目・45行目が `ペイロード=ABCDEFG…` と長く続く。**ウィンドウの最下部に横スクロールバーが出ない**（横スクロールバーはログの表示領域の下端にだけ出る） | `LOG-020` |
| 2 | ログの表示領域を右端まで横スクロールする（表示領域の横スクロールバー、または領域内で `Shift`+ホイール） | 長い行の続きが読める。**左ペイン「参照対象」とツールバーはその場に留まり、画面外へ動かない** | `ENV-005` |
| 3 | 横スクロールした状態のまま上下にスクロールする | 行の内容が正しく差し替わり、横位置も保たれる | `PERF-012` |
| 4 | ウィンドウ幅を狭める・広げる | どの幅でも手順1・2と同じ（ウィンドウ側に横スクロールバーが出ない） | `ENV-005` |

### 4.18 強制終了後の影響（他プロセスと共有資源）

`PERF-016` は、タスクマネージャー等で強制終了された場合も、参照対象へ影響を与えず、同じ端末で稼働する他の業務ソフトウェアの動作を妨げないことを求めます。このうち `temp` の清掃（`SEC-006`）は [4.16](#416-実行時フォルダと診断ログ)の手順3で確認するため、本項では**強制終了の後に他プロセス・共有資源へ影響が残らないこと**を確認します。

準備として、[4.13](#413-追記と再読み込み)と同じ [`scripts/append-log-writer.ps1`](../../scripts/append-log-writer.ps1) を別の PowerShell で走らせ（`-OutputPath $env:TEMP\hakutaku-samples\91-append.log -DurationSeconds 120`）、追記中のログと `08-large.log` を Hakutaku で開いた状態にします。同じ端末で稼働する他の業務ソフトウェアがログを書き続けている状況の再現です（`ENV-010`）。

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | タスクマネージャーから `Hakutaku.exe` を「タスクの終了」で強制終了する | Hakutaku のウィンドウと、その子プロセス（`msedgewebview2.exe` 群）が消える。`append-log-writer.ps1` は中断・エラーにならず、そのまま追記を続ける | `PERF-016`、`ENV-011` |
| 2 | 強制終了の直後に、開いていた `08-large.log` を別のソフト（メモ帳など）で開き、上書き保存・名前の変更・削除ができることを確認する | いずれもロックによる失敗（「別のプロセスが使用中です」）が起きない。内容とファイルサイズは Hakutaku で開く前と同じ | `PERF-016` |
| 3 | 実行ファイル直下の `temp` を確認する | 一時ファイルが残っていることがある（正常終了ではないため、終了時の削除は行われない）。残っていても、残っていなくてもよい | `SEC-006` |
| 4 | Hakutaku を再起動し、`temp` を確認する | 手順3で残っていた内容が起動時に清掃されている（`temp` が空になる） | `PERF-016`、`SEC-006` |
| 5 | 再起動した Hakutaku で、手順1と同じ2つの対象をもう一度開く | 通常どおり開ける。前回の強制終了に起因する破損・残留ロック・再試行の要求が起きない | `PERF-016` |

**この項目で確認できない範囲**: 「他の業務ソフトウェアの動作を妨げない」ことの本来の確認は、運用先の専用端末で実際の業務ソフトウェアを稼働させた状態でしか行えません（`PERF-015`、`ENV-010`。段階1／P13 の範囲）。本項は開発環境で確認できる範囲——参照対象へのロック残存、`temp` の残存物の清掃、追記を続ける別プロセスの継続——に限定します。

### 4.19 キーボードだけの操作とハイコントラスト

キーボードだけで主要な操作を完結できること、およびハイコントラスト表示で状態が見えることを確認します（[Issue #50](https://github.com/vyPeony/Hakutaku/issues/50)）。**マウスに触れずに**実施してください。`04-continuation.log`（継続行を含む）を使います。

| # | 操作 | 期待結果 | 対応要件 |
| --- | --- | --- | --- |
| 1 | 起動直後に `Tab` を繰り返し押す | フォーカスの位置が輪郭で常に分かる。「ファイルを開く」ボタン → 参照対象一覧 → タブ → ログ表示領域の順に進み、フォーカスがどこにも見えなくなる状態にならない | Issue #50 |
| 2 | `04-continuation.log` をキーボードで開く（一覧の行で `Enter`） | 対象が開き、タブができる | Issue #50 |
| 3 | 複数のタブがある状態で、タブへフォーカスを移し `←`／`→` を押す | フォーカスだけがタブ間を移り、**表示は切り替わらない**（端では反対側へ折り返す）。`Home`／`End` で先頭・末尾のタブへ移る | Issue #50 |
| 4 | 手順3のタブで `Enter`（または `Space`）を押す | そのタブが選択され、表示が切り替わる。フォーカスは選択したタブに残る（続けて `←`／`→` を押せる） | `LOG-015` |
| 5 | タブへフォーカスがある状態で `Delete` を押す | そのタブが閉じ、フォーカスは残ったタブ（後継のタブ）へ移る。`<body>` へ落ちない | Issue #50 |
| 6 | ログ表示領域へ `Tab` で入り、`Shift+↓` を数回押す | 先頭の可視行から選択が1行ずつ伸びる。`Shift+↑` で縮む | `COPY-001` |
| 7 | 手順6の状態で `Ctrl+C` を押す | 選択した行数のコピー完了通知が出る | `COPY-002` |
| 8 | ログ表示領域から `Tab` を押して「+N行」バッジまで進む | バッジに輪郭が付く。この状態で**マウスホイールを使わず** `Shift+↓` などで再描画が起きても、フォーカスがバッジまたはログ表示領域に留まり、`<body>` へ落ちない（落ちると次の `Tab` が画面の先頭へ戻ってしまう） | Issue #50 |
| 9 | バッジで `Enter` を押す | 詳細パネルが開き、**フォーカスがパネルへ移る**（パネルに輪郭が付く）。続けて `Tab` を押すとパネルの「×」へ進む | `LOG-014` |
| 10 | パネルへフォーカスがある状態で `Esc` を押す | パネルが閉じ、フォーカスが手順9で押したバッジへ戻る。**このとき選択は解除されない**（`Esc` はパネルを閉じる操作が優先する） | Issue #50 |
| 11 | パネルを閉じた状態で、ログ表示領域にフォーカスを置き `Esc` を押す | 選択が解除される（手順10との違いを確認する） | `COPY-001` |
| 12 | Windows の設定でハイコントラストテーマ（設定 → アクセシビリティ → コントラストテーマ）を有効にし、手順6・8をやり直す | **選択行がシステムの選択色で塗られて見分けられる**。`Tab` によるフォーカスの輪郭も見える。文字が背景に沈んで読めない箇所が無い | Issue #50 |
| 13 | ハイコントラストを元へ戻す | 通常の配色へ戻る | — |

手順12はテーマの切り替え中に画面が再描画されます。切り替え直後に表示が崩れて見える場合は、一度ウィンドウのサイズを変えてから確認してください。

**この節で確認できない範囲**: スクリーンリーダー（ナレーター等）での読み上げ内容そのものは本手順の対象外です。本節はキーボードによる到達性と、ハイコントラストでの可視性までを確認します（読み上げの網羅的な確認は実機・支援技術の組み合わせを要するため、[6章](#6-この手順で確認できないこと)に挙げています）。

## 5. 後片付け

[`scripts/start-manual-check.ps1`](../../scripts/start-manual-check.ps1) を使っている場合は、`-CleanUp` でサンプルフォルダと配置した設定ファイルの削除をまとめて行えます（既定以外の場所へサンプルを生成していた場合は、同じ `-SampleDir` を付けて実行します）。

```powershell
./scripts/start-manual-check.ps1 -CleanUp
```

手動で後片付けする場合は次の手順です。

1. Hakutaku を終了する
2. [4.12](#412-共有違反と再試行)・[4.13](#413-追記と再読み込み)で起動した `append-log-writer.ps1` が残っていないか確認する
3. 生成したサンプルを削除する

```powershell
Remove-Item -Recurse -Force "$env:TEMP\hakutaku-samples"
```

4. 確認のために実行ファイル直下へ置いた `hakutaku.yaml` を削除する（配布物と混ざらないようにするため）
5. `git status` で、リポジトリへ試験データや生成物が入っていないことを確認する

## 6. この手順で確認できないこと

- **段階1（LTSC 実機）の確認**: 実機での起動、資源制約下の挙動、同じ端末で稼働する他の業務ソフトウェアが動いている状態での読み取りは[ロードマップ](../roadmap.md)と[段階0検証記録](stage0-results.md)の範囲です
- **性能の合否判定**: `VER-005` により、本手順で観測した速度・メモリ量は参考値であり判定に使いません
- **`LOG-023`（削除・切り詰め・置換の検知）**: 検知は読み込み中と再読み込み時に働くため、手動では再現の時機を揃えにくく、本手順には含めていません（自動テストで確認済み）
- **`LOG-028` の明示的な再読み込みが上限超過で拒否される経路（ADR-0007）**: [4.13](#413-追記と再読み込み)のとおり、確認自体は可能ですが大きなディスク容量を要するため必須項目には含めていません（自動テストで確認済み）
- **`PERF-004`／`PERF-006` の上限**: [4.14](#414-同時に開けるファイル数の上限)のとおり本手順には含めていません
- **スクリーンリーダーでの読み上げ内容**: [4.19](#419-キーボードだけの操作とハイコントラスト)はキーボードによる到達性とハイコントラストでの可視性までを確認します。ナレーター等での読み上げ文言・読み上げ順序の網羅的な確認は、支援技術の版ごとの差が大きく本手順では判定できないため含めていません（実装が付与している `role`／`aria-*` は [Issue #50](https://github.com/vyPeony/Hakutaku/issues/50) の変更差分を正本として確認してください）
