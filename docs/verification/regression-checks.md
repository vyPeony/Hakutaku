# 回帰検査の対象と判定方法

- 状態: 採用済み（Accepted）
- 管理責任者: リポジトリメンテナー
- 最終更新日: 2026-08-17

## 目的

CI はビルド、テスト、整形、静的解析、文書リンクを実行しますが、大規模データで初めて壊れる部分——保持行数・保持バイト数の上限（`CFG-022`）、表示範囲から遠い行の破棄と再取得（`PERF-012`）、スクロール高さのクランプ——は、これまで手動計測でしか確認できませんでした（[Issue #16](https://github.com/vyPeony/Hakutaku/issues/16)）。

本書は、回帰を検知したい対象、自動判定してよい範囲、重い試験を自動化の対象から除外した理由を定める正本です。実行するコマンドの一覧そのものは[開発ワークフローの「段階0の標準検査」](../development/workflow.md#段階0の標準検査)が正本であり、ここでは複製しません。

## 回帰を検知したい対象

| 対象 | 代表的な退行 | 検知手段 | 実行契機 |
| --- | --- | --- | --- |
| 仮想スクロールの規模依存ロジック（純粋関数） | 2000万行規模でスクロールの末尾へ到達できない。保持上限の判定が効かない。破棄の順序が非決定的になる | [`scripts/check-virtual-scroll.mjs`](../../scripts/check-virtual-scroll.mjs) | CI（`quality` ジョブ）で毎回。ローカルでは `node scripts/check-virtual-scroll.mjs` |
| Rust コアの内部状態（ヒープ会計、表示集合、範囲取得、設定読み込み） | 予算判定の抜け、境界のずれ、設定値の解釈違い | `cargo test --workspace --locked` | CI（`lint-test` ジョブ）。ビルド入力が変わった PR で実行 |
| 大規模データでの実際の内部状態（保持行数・保持バイト数の推移、破棄と再取得の発生、ヒープ会計） | 非同期の取得と破棄の競合による保持上限の一時超過。実機のスクロール挙動の退行 | 計測モードと `scale_verify`（[手動で実行する手段](#除外した重い試験を手動で実行する手段)） | 手動。段階0検証の再実施と段階1（P13） |
| 性能値・メモリ量（起動時間、初回表示時間、スクロール応答、`PrivateUsage`） | — | 計測モードの記録 | 手動。`VER-005` により合否判定には使わない |

### 自動検査が判定する性質

[`scripts/check-virtual-scroll.mjs`](../../scripts/check-virtual-scroll.mjs) は [`src/virtual_scroll.js`](../../src/virtual_scroll.js) の純粋関数（DOM にも Tauri IPC にも触れない）を Node から直接呼び、次を判定します。行数だけを2000万に設定すれば規模依存の経路をそのまま通せるため、試験データも WebView2 も必要としません。

- **スクロール高さのクランプ**: 実効総高さが `min(総行数 × 行高, MAX_TOTAL_HEIGHT_PX)` であること。比例写像へ切り替わるのは上限を**超えた**ときだけで、上限ちょうどでは切り替わらないこと（0行、1行、上限ちょうど、上限+1、実運用の行高22pxでの境界行数を含む）
- **比例写像**: 先頭・中央・末尾の対応、スクロール位置が最大のとき必ず表示集合の末尾へ到達すること、スクロールに対して可視範囲が逆行しないこと、行インデックスとスクロール位置の往復が1行の誤差に収まること、上限未満では従来の1:1方式へ委譲して挙動が変わらないこと
- **スペーサ高さ**: 上下スペーサと実描画行の高さの合計が、可視範囲の位置によらず常に実効総高さと一致すること。先頭で上スペーサが0px、末尾で下スペーサが0pxになること
- **破棄判定（`CFG-022`、`PERF-012`）**: 上限以下なら破棄しないこと、行数・バイト数のどちらの超過でも破棄が起きること、表示中のチャンクを破棄しないこと、遠い順・同距離は番号昇順という決定的な順序、上限を満たした時点で止める（過剰に破棄しない）こと、破棄後に保持上限を満たすこと
- **必要チャンクの選定**: 可視範囲からチャンク番号を求める部分と、総項目数によるクリップ
- **前提の同期**: 検査が動作点として使う定数（行高22px、チャンク512行、バッファ50行）が [`src/log_view.js`](../../src/log_view.js) の値と一致していること

判定に含めないもの: 実行時間、メモリ使用量、DOM の描画結果、Tauri コマンドの応答。いずれもこの検査の対象外です。

### 期待値の決め方

期待値は、実装が現在返す値を写したものではなく、各関数の JSDoc が定める仕様から独立に導いた値を書きます。導出の根拠（どの式へどの数値を代入したか）は、検査スクリプト内の各検査の直前にコメントとして残します。

実装の出力をそのまま期待値にすると、実装を書き換えたときに期待値も一緒に書き換えることになり、検査が何も守らなくなるためです。仕様が変わる場合は、まず JSDoc（および必要なら要件文書）を更新し、そのうえで期待値を導き直します。

## 判定方法

`VER-005` は、段階0で計測した性能値を参考値とし、`PERF-014` の既定値決定および `PERF-009`・`PERF-015` の合否判定には使わないと定めています（[技術検証の確定要件](../architecture/overview.md#技術検証の確定要件)）。段階0で確認するのは、計測手段そのものが機能することまでです。

このため、自動判定の対象は**決定的な内部状態に限ります**。

- **自動で合否を判定してよいもの**: 同じ入力から必ず同じ結果になる値。クランプ結果、比例写像の結果、破棄対象と破棄順、破棄後に保持上限を満たすかどうか
- **記録にとどめるもの**: 実行時間、メモリ量、スクロール応答などの性能値。測定条件（端末、ストレージ、他の業務ソフトウェアの稼働状態）と組にして記録し、合否は段階1の実機実測（`PERF-015`、`VER-006`）で判定します

この区別は[手動での動作確認手順](manual-check.md)の方針と同じです。同手順でも、観測した速度・メモリ量は参考値として扱い、判定には使いません。

## 実行契機

- **CI で毎回**: 軽量な純粋ロジック検査だけを [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) の `quality` ジョブ（Ubuntu、Node のみ。`npm ci` も不要）で実行します。数十秒で終わるため、変更範囲によらず常に実行します
- **CI でビルド入力の変更時**: Rust のテストと release ビルドは Windows のジョブで実行します。省略されたジョブが PR を滞らせないよう、ブランチ保護の必須ステータスチェックには集約ジョブ `CI 完了判定` を指定しています
- **手動**: 大規模データを使う検証（次節）と、画面操作を伴う確認

## 重い試験を CI の自動化対象から除外する理由

1 GB 級・2000万行級の試験は、**CI の自動化対象に含めません**。理由は次の4点です。

1. **試験データの生成が重い**: 2000万行の生成は段階0の実測で 589.32 秒（約9分49秒、[試験データ生成](stage0-results.md#22-試験データ生成2000万行)）と 730.04 秒（約12分10秒、[2000万行の再検証](stage0-results.md#105-2000万行の再検証)）でした。生成物は 2,478,888,847 バイト（約 2.3 GiB）で、これを PR ごとに共有ランナー上で用意することになります
2. **実行環境の要求が大きい**: フロントエンド側の大規模検証は release ビルド（段階0の実測で2分01秒〜2分57秒）と WebView2 Runtime を必要とし、Windows ランナー限定です。読み込み時のプロセス群の `PrivateUsage` は段階0の実測でピーク約 2.24 GiB に達しました。Rust 側のヒープ会計検証も、1 GiB 未満のファイル2本（合計約 1.8 GB）を用意して初めて成立します
3. **測っても合否に使えない**: `VER-005` により、段階0の環境で計測した性能値は `PERF-009`・`PERF-015` の合否判定に使えません。合否の基準は、`PERF-015` が定める「同じ端末で稼働する他の業務ソフトウェアが稼働している状態」での実測であり、その判定は段階1（`VER-006`）で行います。CI の共有ランナーは実機でも運用環境でもないため、そこで得た値は合否判定に使えません
4. **決定的でない**: 大規模データでの実測は、取得と破棄の非同期な進み方に依存します。段階0では、同じ手順でも到達判定が結果によって揺れる事象を実際に観測しました（[2000万行の連続スクロール検証](stage0-results.md#23-2000万行の連続スクロール検証計測モード)）。合否を自動判定する検査には向きません

除外は「検査しない」ことではありません。これらの対象は、段階0検証の再実施と段階1（P13）で、次の手段により手動で確認します。純粋ロジックだけを CI で毎回検査するのは、手動検証の間隔が空いても、規模依存の判断そのものの退行はその日のうちに気付けるようにするためです。

### 除外した重い試験を手動で実行する手段

| 目的 | 手段 |
| --- | --- |
| 試験データの生成 | [`scripts/generate-test-log.ps1`](../../scripts/generate-test-log.ps1)。`-LineCount 20000000 -OutputPath <一時領域>\huge.log` のように、リポジトリ外の一時領域へ出力します |
| フロントエンドの大規模検証（保持上限、破棄と再取得、DOM 行ノードの非増加、`PrivateUsage` の推移） | 計測モード。release ビルドの実行ファイルに環境変数 `HAKUTAKU_MEASURE_FILE`（絶対パス）を設定して起動すると、読み込みから連続スクロール検証、結果ファイルの出力までが自動で完了します（[`src/measurement.js`](../../src/measurement.js)、開発・検証専用） |
| Rust コアのヒープ会計と規模上限（`PERF-004`〜`008`） | [`crates/core-services/examples/scale_verify.rs`](../../crates/core-services/examples/scale_verify.rs)。環境変数 `SCALE_FILES` にセミコロン区切りの絶対パスを渡して実行します |
| 過去の実測値・基準値との突き合わせ | [段階0検証記録](stage0-results.md)。[2000万行の連続スクロール検証](stage0-results.md#23-2000万行の連続スクロール検証計測モード)と[ヒープ会計](stage0-results.md#24-ヒープ会計scale_verify)に、当時の測定条件と結果が残っています |
| 画面と操作を通した確認 | [手動での動作確認手順](manual-check.md) |
