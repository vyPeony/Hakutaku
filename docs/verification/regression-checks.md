# 回帰検査の対象と判定方法

- 状態: 採用済み（Accepted）
- 管理責任者: リポジトリメンテナー
- 最終更新日: 2026-08-25

## 目的

CI はビルド、テスト、整形、静的解析、文書リンクを実行しますが、大規模データで初めて壊れる部分——保持行数・保持バイト数の上限（`CFG-022`）、表示範囲から遠い行の破棄と再取得（`PERF-012`）、スクロール高さのクランプ——は、これまで手動計測でしか確認できませんでした（[Issue #16](https://github.com/vyPeony/Hakutaku/issues/16)）。

本書は、回帰を検知したい対象、自動判定してよい範囲、重い試験を自動化の対象から除外した理由を定める正本です。実行するコマンドの一覧そのものは[開発ワークフローの「段階0の標準検査」](../development/workflow.md#段階0の標準検査)が正本であり、ここでは複製しません。

### 自動検査が判定する性質

[`scripts/check-virtual-scroll.mjs`](../../scripts/check-virtual-scroll.mjs) は [`src/virtual_scroll.js`](../../src/virtual_scroll.js) の純粋関数（DOM にも Tauri IPC にも触れない）を Node から直接呼び、次を判定します。行数だけを2000万に設定すれば規模依存の経路をそのまま通せるため、試験データも WebView2 も必要としません。

- **スクロール高さのクランプ**: 実効総高さが `min(総行数 × 行高, MAX_TOTAL_HEIGHT_PX)` であること。比例写像へ切り替わるのは上限を**超えた**ときだけで、上限ちょうどでは切り替わらないこと（0行、1行、上限ちょうど、上限+1、実運用の行高22pxでの境界行数を含む）
- **比例写像**: 先頭・中央・末尾の対応、スクロール位置が最大のとき必ず表示集合の末尾へ到達すること、スクロールに対して可視範囲が逆行しないこと、行インデックスとスクロール位置の往復が1行の誤差に収まること、上限未満では従来の1:1方式へ委譲して挙動が変わらないこと
- **スペーサ高さ**: 上下スペーサと実描画行の高さの合計が、可視範囲の位置によらず常に実効総高さと一致すること。先頭で上スペーサが0px、末尾で下スペーサが0pxになること
- **破棄判定（`CFG-022`、`PERF-012`）**: 上限以下なら破棄しないこと、行数・バイト数のどちらの超過でも破棄が起きること、表示中のチャンクを破棄しないこと、遠い順・同距離は番号昇順という決定的な順序、上限を満たした時点で止める（過剰に破棄しない）こと、破棄後に保持上限を満たすこと
- **必要チャンクの選定**: 可視範囲からチャンク番号を求める部分と、総項目数によるクリップ
- **前提の同期**: 検査が動作点として使う定数（行高22px、チャンク512行、バッファ50行）が [`src/log_view.js`](../../src/log_view.js) の値と一致していること

判定に含めないもの: 実行時間、メモリ使用量、DOM の描画結果、Tauri コマンドの応答。いずれもこの検査の対象外です。

[`scripts/check-selection.mjs`](../../scripts/check-selection.mjs) は [`src/selection.js`](../../src/selection.js) の純粋関数を同じやり方で呼び、次を判定します（[Issue #85](https://github.com/vyPeony/Hakutaku/issues/85)）。

- **基本操作**: 単一選択・`Shift` 拡張（アンカーを保ったまま置き換える、逆向きでも両端を含む）・全選択（0行なら選択なし、2000万行でも範囲は1つ）・クリア
- **`Ctrl+クリック` のトグル（`COPY-001`）**: 未選択の行の追加、選択済みの行の除外による範囲の分割、隣接する範囲の結合、2範囲の間を埋めたときの結合、最後の1行を外したときにアンカーも手放すこと
- **ドラッグ更新**: 開始行から現在行までの1範囲で置き換えること、向きによらず同じ範囲になること
- **クランプ**: 表示集合の項目数の外へ出た範囲を捨て、またぐ範囲を切り詰め、範囲外のアンカーを手放すこと
- **`isRowSelected` の二分探索**: 範囲の先頭・末尾・その1つ外の境界、100範囲に対する全位置
- **コピー範囲への変換**: `copy_selection` へ渡す範囲列が、Rust 側（`hakutaku_core::assemble_copy`）の受け入れ条件（`start` 昇順・互いに素・行数1以上・表示集合の範囲内）を必ず満たすこと
- **操作の組み合わせ**: 決定的な擬似乱数で作った400手の操作列の各段階で、範囲集合の不変条件・`isRowSelected`・選択行数・コピー範囲が、行インデックスの集合（参照モデル）と一致すること
- **前提の同期**: [`src/log_view.js`](../../src/log_view.js) が選択モデルの関数を実際に使っていること、廃止したコピー列 UI（[ADR-0011](../architecture/decisions/0011-copy-raw-text-only.md)）を参照していないこと

[`scripts/check-tabs.mjs`](../../scripts/check-tabs.mjs) は [`src/tabs.js`](../../src/tabs.js) の純粋関数を同じやり方で呼び、次を判定します（[Issue #52](https://github.com/vyPeony/Hakutaku/issues/52)）。

- **追加と再オープン**（`upsertTab`）: 新しい対象は末尾へ追加してアクティブにすること。同じ対象を開き直した場合は**位置を変えず**に内容（表示集合 ID・世代・総行数）だけを差し替えること（`LOG-028`）。他のタブを巻き添えで書き換えないこと
- **後継タブの選び方**（`closeTab`）: アクティブなタブを閉じたら右隣、右が無ければ左隣を選ぶこと。最後の1枚を閉じたら `activeTargetId` を手放すこと。背景のタブを閉じても利用者が見ているタブを動かさないこと
- **フォーカスを動かさない内容更新**（`updateTabContent`）: 並びもアクティブなタブも変えずに内容だけを更新すること（`LOG-028` の再読み込みは背景の行にも押せるため、視点を奪わない）。見出しと対象 ID を保つこと
- **防御的な既定動作**: 存在しない `targetId` を渡した場合（一覧の再同期のずれ、二重クリック）に、状態を壊さず同一の状態をそのまま返すこと。`getActiveTab` が一覧に無いアクティブ ID に対して `null` を返すこと
- **不変更新**: 呼び出しのたびに新しいオブジェクトを返し、引数の状態をその場で書き換えないこと（[ADR-0006](../architecture/decisions/0006-frontend-vanilla-es-modules.md) の素の ES モジュール構成では、呼び出し側が戻り値を再代入する形で使うため）
- **操作の組み合わせ**: 決定的な擬似乱数で作った300手の操作列の各段階で、`targetId` が重複しないこと、`activeTargetId` が `null` か現在のタブのいずれかを必ず指すこと、`getActiveTab` の結果と一致すること
- **前提の同期**: [`src/shell.js`](../../src/shell.js) がタブの追加・切り替え・クローズ・再読み込みをこのモデルへ委ねていること

[`scripts/check-targets.mjs`](../../scripts/check-targets.mjs) は [`src/targets.js`](../../src/targets.js) の純粋関数を同じやり方で呼び、次を判定します（[Issue #52](https://github.com/vyPeony/Hakutaku/issues/52)）。

- **並び順と突き合わせ**: 設定由来（`get_config_status` の順序）→ アドホック（登録順）の順に並ぶこと。設定由来の名前に対応するセッションが無ければ「未読み込み」の行を作ること。名前に一致しない設定由来のセッション（通常は起こらない）を末尾へ回すこと
- **行の鍵の安定性**（`TargetRow.key`。[Issue #48](https://github.com/vyPeony/Hakutaku/issues/48)）: 設定由来の行は未読み込み・読み込み中・読み込み済みのすべてで同じ鍵（`configured:<名前>`）を指し、対象 ID を含まないこと。一覧の中で鍵が一意であること。鍵が変わると左ペインの DOM が作り直され、読み込み中のポーリング（500ms 間隔）のたびにキーボードフォーカスと select の選択値が失われる
- **状態 DTO の変換**: 読み込み中の進捗（総量不明は `null` のまま。0 に潰さない）、読み込み済み（`LOG-022` の生表示退避、`LOG-028` の更新未反映）、キャンセル済み・部分読み込み（`LOG-027`）、エラー（`ERR-002` の5要素、`PRIV-002` のアクセス拒否）。数値は文字列で届いても数値へ、省略された真偽値は `false` へ揃えること（昇格ボタンを誤って出さないため）
- **防御的な既定動作**: 未知の状態種別は「読み込み中」として扱い、画面を壊さないこと
- **前提の同期**: [`src/shell.js`](../../src/shell.js) が左ペインの行をこのモデルから作り、`TargetRow.key` を DOM 要素の対応表の鍵に使っていること

[`scripts/check-capabilities.mjs`](../../scripts/check-capabilities.mjs) は、`src/` の純粋関数ではなく**ソースの静的な対応関係**を突き合わせます（[Issue #52](https://github.com/vyPeony/Hakutaku/issues/52)）。Tauri のコマンドは、`src-tauri/src/lib.rs` の `tauri::generate_handler!`（IPC の受け口）と、`src-tauri/permissions/<コマンド名>.toml`＋`src-tauri/capabilities/default.toml`（許可）の2箇所へ書く必要があり、片方だけを書いた状態はビルドでも静的解析でも検出できません。

- **登録と許可の双方向**: 登録したコマンドに許可があること、許可があるコマンドが登録されていること。前者が欠けると実行時に失敗し、後者が残ると最小権限（`SEC-012`）が崩れる
- **許可定義と Capability の列挙**: 定義した許可がすべて `default.toml` に列挙され、列挙された識別子すべてに定義があること（定義しただけでは許可されない）
- **最小権限の形**: 1つの許可定義が1コマンドだけを許可すること。識別子とファイル名が規約（`allow-<コマンド名>`）どおりであること。1つのコマンドを複数の許可が重複して認めていないこと
- **呼び出し側との整合**: `src/` が `invoke(...)` で呼ぶコマンドがすべて登録・許可されていること
- **解析できない場合は失敗させる**: 想定した記法（`generate_handler!` の並び、`[[permission]]`、`commands.allow`）が見つからない・複数ある場合は、0件と比較して「差分なし」と報告せずエラーで停止する

### 取得と破棄の順序競合の扱い

段階0の2000万行実測では、保持行数が上限を一時的に超える事象を観測しました（241サンプル中18件、最大 +12.6%。[2.3.1節](stage0-results.md#231-機能ゲート-保持行数保持バイト数cfg-022)）。原因は [`src/log_view.js`](../../src/log_view.js) の再描画が「取得を**開始する**（`ensureChunksLoaded`。非同期、完了を待たない）→ その時点でキャッシュ済みのものだけを破棄対象にする（`evictFarChunks`）」の順に進むことにあり、対処として「取得完了直後にも破棄判定を再実行する」方式（`runPostFetchEvictionPass`）を採りました（[10.1節](stage0-results.md#101-採用した修正方針)）。

この競合を CI で毎回検知するため、[`scripts/check-virtual-scroll.mjs`](../../scripts/check-virtual-scroll.mjs) に次の2つを置いています。**どちらも `log_view.js` の非同期処理そのものは実行しません。**

1. **順序モデル**: 公開されている純粋関数（`computeVisibleRangeForScroll`・`computeRequiredChunkIndices`・`computeChunkRange`・`selectChunksToEvict`）だけで「スクロール → 取得開始 → 遅れて完了」の順序を組み立て、観測点ごとの保持量を確かめます。取得完了ごとに破棄する現在の方式では上限（`CFG-022`）を満たすこと、**対照実験**としてバッチ末尾でしか破棄しない旧方式では超過が再現することの両方を判定します。対照実験を置くのは、モデルが競合を表現できなくなったときに「問題なし」と報告し続けることを防ぐためです
2. **呼び出し順の突き合わせ**: `log_view.js` のソースから、再描画が `ensureChunksLoaded` → `evictFarChunks` の順であること、`fetchChunk` がキャッシュ格納の直後に `runPostFetchEvictionPass` を呼ぶことを確認します

**実物の非同期経路そのものは自動化していません。** `ensureChunksLoaded`・`evictFarChunks`・`runPostFetchEvictionPass` は `log_view.js` のモジュール内部の関数で、export されておらず、モジュール内の `state`・DOM（`requestAnimationFrame`、行要素の組み立て）・`window.__TAURI_INTERNALS__.invoke` に密結合しています。Node から実物を動かすには、(a) 内部関数を export する（検査のためにプロダクションコードの境界を変える）か、(b) DOM と IPC の代替実装を持ち込む（外部依存を増やし、[ADR-0006](../architecture/decisions/0006-frontend-vanilla-es-modules.md) の素の ES モジュール構成から外れる）ことになり、どちらも検査で得られるものに見合いません。実物の経路は次の2つで確認します。

- **画面操作を通した確認**: [GUI 自動検査](#gui-自動検査scriptscheck-guimjs)の「仮想スクロール」シナリオ（10万行を全域までスクロールし、DOM 行ノード数が上限を超えないこと）
- **大規模データでの実測**: 計測モードによる2000万行の連続スクロール検証（[手動で実行する手段](#除外した重い試験を手動で実行する手段)）。保持行数・保持バイト数の推移そのものはここでしか観測できません

### 期待値の決め方

期待値は、実装が現在返す値を写したものではなく、各関数の JSDoc が定める仕様から独立に導いた値を書きます。導出の根拠（どの式へどの数値を代入したか）は、検査スクリプト内の各検査の直前にコメントとして残します。

実装の出力をそのまま期待値にすると、実装を書き換えたときに期待値も一緒に書き換えることになり、検査が何も守らなくなるためです。仕様が変わる場合は、まず JSDoc（および必要なら要件文書）を更新し、そのうえで期待値を導き直します。

## 判定方法

`VER-005` は、段階0で計測した性能値を参考値とし、`PERF-014` の既定値決定および `PERF-009`・`PERF-015` の合否判定には使わないと定めています（[技術検証の確定要件](../architecture/overview.md#技術検証の確定要件)）。段階0で確認するのは、計測手段そのものが機能することまでです。

このため、自動判定の対象は**決定的な内部状態に限ります**。

- **自動で合否を判定してよいもの**: 同じ入力から必ず同じ結果になる値。クランプ結果、比例写像の結果、破棄対象と破棄順、破棄後に保持上限を満たすかどうか
- **記録にとどめるもの**: 実行時間、メモリ量、スクロール応答などの性能値。測定条件（端末、ストレージ、他の業務ソフトウェアの稼働状態）と組にして記録し、合否は段階1の実機実測（`PERF-015`、`VER-006`）で判定します

この区別は[手動での動作確認手順](manual-check.md)の方針と同じです。同手順でも、観測した速度・メモリ量は参考値として扱い、判定には使いません。

## 実行契機

- **CI で毎回**: 軽量な純粋ロジック検査（仮想スクロール・行選択・タブ・参照対象一覧）と静的な対応関係の検査（登録コマンドと Capability）だけを [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) の `quality` ジョブ（Ubuntu、Node のみ。`npm ci` も不要）で実行します。数十秒で終わるため、変更範囲によらず常に実行します
- **CI でビルド入力の変更時**: Rust のテストと release ビルドは Windows のジョブで実行します。省略されたジョブが PR を滞らせないよう、ブランチ保護の必須ステータスチェックには集約ジョブ `CI 完了判定` を指定しています
- **定期実行（週1回）**: 依存関係の脆弱性検査（[`.github/workflows/audit.yml`](../../.github/workflows/audit.yml)）。PR のゲートにはしません（[理由](#依存の脆弱性検査githubworkflowsaudityml)）
- **手動**: 画面操作を通した検査（[GUI 自動検査](#gui-自動検査scriptscheck-guimjs)）と、大規模データを使う検証（[手動で実行する手段](#除外した重い試験を手動で実行する手段)）

## GUI 自動検査（`scripts/check-gui.mjs`）

フロントエンドのビジネスロジック（[`src/log_view.js`](../../src/log_view.js)、[`src/shell.js`](../../src/shell.js) など）は、純粋関数の検査（`check-virtual-scroll.mjs`・`check-selection.mjs`・`check-tabs.mjs`・`check-targets.mjs`）でも静的検査（`check-frontend.mjs`）でも到達できない部分が残ります。表示ラベルの更新、行 DOM の組み立て、イベント委譲、Tauri コマンドとの往復は、実際に画面を動かさなければ壊れたことに気付けません（[Issue #52](https://github.com/vyPeony/Hakutaku/issues/52) の指摘、[Issue #57](https://github.com/vyPeony/Hakutaku/issues/57)）。

[`scripts/check-gui.mjs`](../../scripts/check-gui.mjs) は、release ビルドの `Hakutaku.exe` を環境変数 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<ポート>` 付きで起動し、`playwright-core` の `chromium.connectOverCDP` で WebView2 へ接続してこの隙間を埋めます。プロダクトコード（`src/`・`src-tauri/`・`crates/`）は一切変更していません。

### 検査するシナリオ

1回の起動で、次の10シナリオを**直列に**実行します。試験データは [`scripts/generate-sample-logs.ps1`](../../scripts/generate-sample-logs.ps1) が生成する `%TEMP%\hakutaku-samples` を使い、無ければ検査スクリプトが生成します。

生成の要否は「設定が指すファイルが存在するか」に加えて「シナリオが開く表示名がすべて設定にあるか」でも判定します（`inspectSampleSet`）。ファイルの存在だけを見ると、**サンプルが増えたときに古い一式が「使える状態」と誤判定され**、新しいサンプルを開くシナリオだけが原因の分かりにくい失敗になるためです（[Issue #78](https://github.com/vyPeony/Hakutaku/issues/78) で恒久対策にしました）。

| シナリオ | 主な表明（関連する要件） |
| --- | --- |
| 起動スモーク | ウィンドウ生成、`#open-file-button` の可視、`get_config_status` が正常起動（`CFG-014`）、左ペインの件数（`CFG-003`）、通知バナー0件、JS コンソールエラー0件 |
| 設定由来データソースを開く | 読み込み元ラベル、表示集合の件数、タブの生成と選択状態、左ペインの状態追随、先頭行の中身（`LOG-001`、`LOG-020`） |
| 日時精度 | `fetch_log_range` が返す日時の表示文字列が、ミリ秒3桁のログでは3桁ちょうど（`LOG-024`）、1/100秒2桁のログでは2桁のまま（`LOG-025`）であること。行一覧の日時列は [Issue #78](https://github.com/vyPeony/Hakutaku/issues/78) で、コピー列は [Issue #85](https://github.com/vyPeony/Hakutaku/issues/85) で廃止したため、**画面・コピーのどちらにも提示箇所が無く**（統合表示の改修（[Issue #82](https://github.com/vyPeony/Hakutaku/issues/82)）で表示予定）、この IPC 境界の桁数が精度を確認できる唯一の自動検査点です |
| 仮想スクロール | 10万行を全域までスクロールしても DOM 行ノード数が上限を超えない（`PERF-012`）、末尾へ到達する |
| 行番号ジャンプ | 範囲内の値でその行が描画範囲に入る、範囲外は先頭・末尾へ丸めて入力欄へ書き戻す |
| 選択とコピー | Ctrl+A で全行選択（`COPY-001`）、Ctrl+C でコピー完了通知（`COPY-002`）、Ctrl+クリックで離れた行だけを選ぶ・もう一度で外す、実マウスのドラッグ（`mousedown`→`mousemove`→`mouseup`）で連続範囲、飛び飛びの選択でも完了通知の行数が選択合計と一致する（[Issue #85](https://github.com/vyPeony/Hakutaku/issues/85)） |
| 複数タブと時系列統合トグルの非活性化 | 複数ファイルでタブが並ぶ（`LOG-006`、`LOG-015`）。統合トグルが disabled、aria-pressed が false のまま、title に Issue #82 への案内がある、統合タブ（`tab--merged`）が現れない（Issue #83） |
| タブを閉じる | × でタブが消え、左ペインの状態が「未読み込み」へ追随する |
| 継続行バッジと詳細パネル | バッジのクリックで詳細パネルが開き、改行を保った全文を表示し、閉じると内容を保持しない（`LOG-014`）。既定時と閉じた後は計算後の `display` が `none` であること（見た目の非表示。[Issue #78](https://github.com/vyPeony/Hakutaku/issues/78)） |
| 横スクロールの封じ込め | 数千文字の行があってもウィンドウ全体に横スクロールが出ず（`documentElement` の `scrollWidth` ≦ `clientWidth`）、横スクロールは `#log-viewport` の内側だけに存在し、右端まで送っても左ペインの位置が動かない（`ENV-005`。[Issue #78](https://github.com/vyPeony/Hakutaku/issues/78)） |

判定に含めないもの: 実行時間、スクロール応答、メモリ使用量。所要時間はシナリオごとに出力しますが、`VER-005` により合否には使いません。

この方式で表明できないものもあります。

- **CDP 接続より前のコンソール出力**: 実行ファイルを起動してからデバッグポートへ接続するため、接続が成立する前にフロントエンドが出力したエラーは原理的に拾えません。起動スモークの「コンソールエラー0件」は、接続以降に観測した範囲の表明です
- **ネイティブのファイル選択ダイアログを伴う経路**（`PROD-016`／`LOG-020` のアドホックな選択）、権限昇格（`PRIV-002`）、共有違反、追記中のファイルの再読み込み（`LOG-028`）。いずれも[手動での動作確認手順](manual-check.md)で確認します
- **クリップボードの中身そのもの**: 書き込みの正しさは Rust 側の単体テストが受け持ちます。GUI 検査が確認するのは、操作から完了通知までの経路がつながっていることまでです
- **統合表示のコード経路**（`enable_merged_view`／`disable_merged_view`、`src/log_view.js` の統合経路）: Issue #83 により UI 入口（`#merged-view-toggle`）が非活性化されているため到達できません。#82 の改修実装まで回帰検査の対象外です。「複数タブと時系列統合トグルの非活性化」シナリオは、この非活性化そのもの（disabled・title・統合タブが現れないこと）だけを確認します

### 実行手順

```
npm ci                                  # 初回のみ
npm run tauri -- build --no-bundle      # release ビルドを作る
node scripts/check-gui.mjs              # 全シナリオを直列に実行する
```

`--exe <実行ファイル>` と `--port <デバッグポート>` を指定できます（既定は `target/x86_64-pc-windows-msvc/release/Hakutaku.exe` とポート 9455）。失敗したシナリオの画面は `%TEMP%\hakutaku-gui-check` へ保存されます。

副作用は次の4つです。リポジトリ内へは何も生成せず、実データ（個人情報等の機密データを含み得るログ）は一切扱いません。

- OS のクリップボードを上書きする（選択とコピーのシナリオ）
- `%TEMP%\hakutaku-samples` へ試験データを生成する（無い場合のみ）
- 実行ファイル直下へ `hakutaku.yaml` を配置する（`target/` 配下。Git 管理外。`CFG-014`）
- `%TEMP%\hakutaku-gui-check` へ失敗時のスクリーンショットを書き出す

### 検査を書くときの規約

1. **ネイティブのファイル選択ダイアログ（`#open-file-button`）を押さない。** CDP からは操作できず、開いてしまうと以降の応答が不安定になることを実測済みです。同じ状態には設定由来のデータソース（`CFG-003`）を左ペインから開けば到達できます
2. **並列実行しない。** WebView2 のユーザーデータフォルダは実行ファイル直下に固定されるため（`SEC-009`）、同じ実行ファイルを同時に動かすと状態が壊れます
3. **クリップボードを上書きする試験は最小のサンプル（200行）だけで行う。** 利用者がコピー中の内容を壊す量を最小にするためです
4. **`HAKUTAKU_MEASURE_FILE` を設定しない。** 計測モード（[`src/measurement.js`](../../src/measurement.js)）が自動で走り、検査の操作と競合します。呼び出し元の環境に残っていた場合は、検査スクリプトが子プロセスの環境から取り除きます
5. **待機は行の中身に対して書く。** 行 DOM は先に「（読み込み中…）」のプレースホルダーとして描画され、中身は後から差し替わります。加えて、表示を切り替えると読み込み元ラベルが先に更新され、行の描画は次のフレーム以降に進むため、ラベルだけを待つと切り替え前のファイルの行を掴みます（実測で発生）。ハーネスは切り替え前の描画内容と一致しなくなるまで待ちます
6. **性能値・所要時間を合否に使わない**（`VER-005`）

### CI に入れない理由

この検査は**当面ローカル専用**とし、[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) には入れません。

1. **実行環境の要求が大きい**: release ビルド済みの実行ファイル、WebView2 Runtime、そして画面を持つ Windows セッションが必要です。ヘッドレスの共有ランナーでは前提が成立しません
2. **待機が非決定的**: 描画は `requestAnimationFrame` と範囲取得（Tauri コマンド）の応答という2段階で進み、完了の瞬間を外から一意に決められません。ハーネス側で「行の集合が落ち着くまで待つ」ようにしていますが、共有ランナーの負荷変動の下でも安定するかは未確認です
3. **副作用が共有環境に向かない**: OS のクリップボードを上書きし、実行ファイル直下へ設定ファイルを配置します

CI へ組み込むかどうかは、ローカルで安定して動き続けることを確認したうえでの**第2段階の判断**とします。組み込む場合は、シナリオごとの再試行方針と、共有ランナーでの副作用の扱いを先に決める必要があります。

## 重い試験を CI の自動化対象から除外する理由

1 GB 級・2000万行級の試験は、**CI の自動化対象に含めません**。理由は次の4点です。

1. **試験データの生成が重い**: 2000万行の生成は段階0の実測で 589.32 秒（約9分49秒、[試験データ生成](stage0-results.md#22-試験データ生成2000万行)）と 730.04 秒（約12分10秒、[2000万行の再検証](stage0-results.md#105-2000万行の再検証)）でした。生成物は 2,478,888,847 バイト（約 2.3 GiB）で、これを PR ごとに共有ランナー上で用意することになります
2. **実行環境の要求が大きい**: フロントエンド側の大規模検証は release ビルド（段階0の実測で2分01秒〜2分57秒）と WebView2 Runtime を必要とし、Windows ランナー限定です。読み込み時のプロセス群の `PrivateUsage` は段階0の実測でピーク約 2.24 GiB に達しました。Rust 側のヒープ会計検証も、1 GiB 未満のファイル2本（合計約 1.8 GB）を用意して初めて成立します
3. **測っても合否に使えない**: `VER-005` により、段階0の環境で計測した性能値は `PERF-009`・`PERF-015` の合否判定に使えません。合否の基準は、`PERF-015` が定める「同じ端末で稼働する他の業務ソフトウェアが稼働している状態」での実測であり、その判定は段階1（`VER-006`）で行います。CI の共有ランナーは実機でも運用環境でもないため、そこで得た値は合否判定に使えません
4. **決定的でない**: 大規模データでの実測は、取得と破棄の非同期な進み方に依存します。段階0では、同じ手順でも到達判定が結果によって揺れる事象を実際に観測しました（[2000万行の連続スクロール検証](stage0-results.md#23-2000万行の連続スクロール検証計測モード)）。合否を自動判定する検査には向きません

除外は「検査しない」ことではありません。これらの対象は、段階0検証の再実施と段階1（P13）で、次の手段により手動で確認します。純粋ロジックだけを CI で毎回検査するのは、手動検証の間隔が空いても、規模依存の判断そのものの退行はその日のうちに気付けるようにするためです。

### 除外した重い試験を手動で実行する手段

| 目的 | 手段 |
| --- | --- |
| 試験データの生成 | [`scripts/generate-test-log.ps1`](../../scripts/generate-test-log.ps1)。`-LineCount 20000000 -OutputPath <一時領域>\huge.log` のように、リポジトリ外の一時領域へ出力します |
| フロントエンドの大規模検証（保持上限、破棄と再取得、DOM 行ノードの非増加、`PrivateUsage` の推移） | 計測モード。release ビルドの実行ファイルに環境変数 `HAKUTAKU_MEASURE_FILE`（絶対パス）を設定して起動すると、読み込みから連続スクロール検証、結果ファイルの出力までが自動で完了します（[`src/measurement.js`](../../src/measurement.js)、開発・検証専用） |

## 依存の脆弱性検査（`.github/workflows/audit.yml`）

依存関係（`Cargo.lock`・`package-lock.json`）に既知の脆弱性が報告されていないかを、`cargo audit` と `npm audit --audit-level=high` で確認します（[Issue #52](https://github.com/vyPeony/Hakutaku/issues/52)）。

**PR のゲートにはしません。** 週1回の定期実行（`schedule`）と手動実行（`workflow_dispatch`）だけで動かし、`pull_request`・`push` では起動しません。脆弱性の勧告（advisory）は依存の更新と無関係に任意の日へ新しく公開されるため、必須検査にすると、その PR の差分と因果関係のない失敗でマージが止まります。対処（依存の更新、影響評価、除外の判断）は、その PR とは別の作業として扱うほうが速く安全に進みます。ブランチ保護の必須ステータスチェックは `ci.yml` の集約ジョブ `CI 完了判定` に固定しており、このワークフローはその判定に一切関与しません。失敗は Issue にせず、ワークフローの失敗として通知されます。

結果の読み方には注意が必要です。

- **ビルド対象との照合が要る**: `cargo audit` は `Cargo.lock` 全体を見ます。Hakutaku のビルド対象は Windows（`x86_64-pc-windows-msvc`。[Windows ビルド互換性](../development/windows-build-compatibility.md)）に固定されているため、**実際にはビルドへ入らない依存（Linux 限定の推移依存など）の勧告も報告され得ます**。報告を受けたら、まずビルド対象で実際に使われるかを確認してから対処の要否を判断します
- **警告では失敗させない**: 既定の `cargo audit` は脆弱性で失敗し、未保守（unmaintained）などの警告は報告するだけです。緊急度が違うため、この既定のままにしています
- **実行環境**: ビルドを行わずロックファイルの依存グラフだけを見るため ubuntu で実行します。ロックファイルの内容は OS に依存しません
