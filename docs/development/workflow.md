# 開発ワークフロー

- 状態: 採用済み（Accepted）
- 管理責任者: リポジトリメンテナー
- 最終更新日: 2026-08-21

## 目的

この文書は、Issue からブランチ、コミット、プルリクエスト、レビュー、マージ、後処理までの標準手順です。役割、タスク状態、例外は[リポジトリ運用規則](repository-operations.md)、複数セッションの排他は[並行セッション](concurrent-sessions.md)を参照します。

Issue、プルリクエスト、レビュー、コメント、コミットメッセージは、[使用言語と文章の規則](repository-operations.md#使用言語と文章)に従い、分かりやすい日本語で書きます。

## 標準フロー

1. Issue をトリアージし、対象範囲と受け入れ条件を着手可能（`Ready`）にする
2. タスク責任者と作業セッションが担当範囲を宣言する
3. 最新の `origin/main` を基点に、専用の worktree とブランチを用意する
4. 一つの目的に絞って変更し、意味のある変更単位ごとに検証する
5. 早い段階で下書き PR を作り、対象範囲と競合範囲を可視化する
6. レビュー開始条件を満たして下書きを解除する
7. 重大なレビュー指摘を解消し、必要な再検証を行う
8. 原則としてスカッシュマージする
9. マージ後の検査、Issue、ブランチ、worktree、文書を整理する

## Issue とトリアージ

非自明な変更または並行セッションの変更は Issue を必須とします。Issue には、問題、対象範囲と対象外、検証可能な受け入れ条件、タスク責任者、依存関係、リスクを記載します。タイトルと本文は日本語で書き、固定の状態名や技術識別子には必要に応じて日本語の説明を添えます。

GitHub を利用できない、または書き込み権限がない状態で、利用者が明示したローカル作業だけは、[タスク記録の例外](repository-operations.md#タスク記録)を使えます。この状態はリポジトリ全体の担当権限を持ちません。同一利用者が管理する現在のタスクの一対一の継続・引き継ぎを除き、独立タスクとの共有、リモートへの送信、PR、リポジトリ単位の引き継ぎを行う前に、着手可能（`Ready`）な Issue へ同期します。

次は特に、実装前に着手可能な Issue 上、またはその Issue に関連付けた設計用の下書き PR で合意します。

- 大きな機能、破壊的変更、複数領域にまたがる変更
- 対象範囲、要件、信頼境界、公開 API・形式を変える変更
- 複数の有力な設計選択肢がある変更
- リポジトリ規則、CI、リリース、セキュリティ設定を変える変更

Issue の作成だけでは着手承認を意味しません。情報不足なら「情報不足（`Needs info`）」、採用しない場合は理由付きの「不採用（`Declined`）」、重複なら正本の Issue へ関連付けて「重複（`Duplicate`）」とします。

小さな誤字、リンク、明白な一ファイルの修正は Issue を省略でき、PR をタスク記録にします。脆弱性の詳細は公開 Issue / PR に書かず、[`.github/SECURITY.md`](../../.github/SECURITY.md) に従います。

## ブランチと worktree

`type/issue-id-short-kebab-description` を基本とします。

- `feat/123-add-log-reader`
- `fix/456-handle-api-timeout`
- `docs/789-define-connector-contract`
- `refactor/321-isolate-parser`
- `test/654-add-redaction-cases`
- `chore/987-update-tooling`

Issue を省略できる小変更では `docs/fix-broken-link` のように番号を省略できます。並行セッションと非自明な変更では Issue 番号が必須です。ローカル限定の例外で番号がまだない場合はブランチを公開せず、一対一のローカル引き継ぎを超えて共有する前に着手可能（`Ready`）な Issue を作り、Issue 番号付きのタスクブランチへ収容します。

- ブランチは最新の `origin/main` から作る。ローカルの `main` が最新だと推測しない
- 一つの作業セッションに一つの専用 worktree とブランチを使う
- 同じブランチを複数の worktree へチェックアウトしない
- 共有ブランチの履歴を無断で書き換えない
- リベースは自分だけが使う未共有ブランチに限定する
- `main` を強制送信、リベース、リセットしない

Codex 管理の worktree、detached HEAD、引き継ぎの扱いは[並行セッション](concurrent-sessions.md)を参照します。

## コミット

コミットと PR のタイトルは、軽量な Conventional Commits 形式を使用します。`type` と任意の `scope` は機械処理用の英語表記を保ち、その後の要約を日本語で書きます。

```text
type(optional-scope): 日本語の要約
```

使用する type:

- `feat`, `fix`, `docs`, `refactor`, `test`, `chore`
- 必要に応じて `build`, `ci`, `perf`, `revert`

例:

```text
feat(log-reader): 複数行の項目を読み取れるようにする
fix(api): タイムアウト後も取得済みの結果を保持する
docs: 対応する入力形式を明確にする
```

- 一つのコミットは、レビュー可能な一つの論理変更にする
- 対象範囲外の差分をステージせず、自分のタスクの変更だけをコミットする
- 秘密情報、本番データ、一時ファイル、生成物がないかをコミット前に確認する
- 本文は分かりやすい日本語で書く。理由、制約、検証がタイトルだけでは分からない場合に追加する
- 作業途中のコミットは引き継ぎ・バックアップ用とし、レビュー前に意図が分かる履歴へ整理する

コミットやリモート送信の権限がない AI エージェントは、自律的に実行せず、差分と必要性を報告します。

## 下書きプルリクエスト

非自明な変更は、最初の意味ある差分または設計方針を共有できた時点で、下書きプルリクエスト（Draft PR）を作ります。下書き PR は早期レビューと担当範囲の可視化のためであり、未検証の差分をマージ可能と示すものではありません。

PR の本文は日本語で書き、次を記載します。

- 目的、Issue、受け入れ条件
- 対象範囲と対象外、主要な変更
- 作業セッション、担当範囲、引き継ぎ
- テスト、静的解析、手動確認、文書確認の結果
- 互換性、性能、セキュリティ、データ、切り戻しへの影響
- 未実施項目、既知の制約、後続課題
- AI 支援を使った場合、その範囲と人間が確認した内容

対象範囲が変わった場合は、タイトル、本文、受け入れ条件、担当範囲を変更前に更新します。

Issue を完全に満たす場合だけ `Closes #123` を使います。部分対応や参照だけなら `Refs #123` とし、残作業を閉じません。

## 関連文書の同時更新

次の変更では、実装と同じ PR で関連文書を更新します。

- 対応データソースやコネクター能力の追加・変更
- 公開される設定、API、ファイル形式、データモデルの変更
- 認証情報、キャッシュ、履歴、外部通信の扱いの変更
- 利用者から見える振る舞い、制約、エラーの変更
- 後戻りが高コストな設計判断

重要な判断には [ADR](../architecture/decisions/README.md) を使用します。ADR が不要な局所変更まで文書化を強制するものではありません。

## レビュー開始条件

下書き（Draft）を解除する条件は、[リポジトリ運用規則のレビュー開始条件](repository-operations.md#レビュー開始条件)を満たすことです。項目はここへ複製せず、正本を参照してください。

## レビュー

レビュー担当は次を確認します。指摘と判断理由は分かりやすい日本語で書き、コード、ログ、固定識別子など原文が必要な箇所だけ原文を保ちます。

- 対象範囲と受け入れ条件を満たし、目的外の差分がない
- 既存のプロダクト原則、要件、アーキテクチャ、用語に整合する
- エラー、キャンセル、部分的な失敗、大きすぎる入力、不正な入力を必要な範囲で扱う
- 認証情報、取得元データ、キャッシュ、診断、ネットワーク、永続化への影響が安全で説明されている
- テストと文書が振る舞いを証明し、未決事項を隠していない
- 移行、切り戻し、互換性がリスクに応じて考慮されている

指摘は、重大（`blocking`）または軽微・提案（`non-blocking / suggestion`）に分類します。重大な指摘は、修正するか、安全に対象範囲を縮小して原因を差分から除去するまで解消しません。後続 Issue へ送れるのは、レビュー担当またはメンテナーが理由を記録し、軽微へ再分類した項目だけです。読み取り専用、セキュリティ、データ安全性、受け入れ条件未達、必須検証の失敗は、未解消のまま軽微へ再分類しません。

レビュー後に大きな差分、対象範囲、セキュリティ上の前提が変わった場合は、古い承認をそのまま根拠にせず、再レビューと再検証を行います。レビュー担当が作者のブランチを変更する場合は事前に合意し、変更を PR に記録します。

単独開発では、自己レビューと必要な条件を満たせば自己マージできます。ただし高リスク変更は、AI の自己レビューだけで完了とせず、メンテナー自身が差分を確認します。

## 競合の解消

競合の解消担当は、原則として PR の作者です。

1. 両側の Issue、受け入れ条件、正本文書、差分を確認する
2. 最新の `main` をタスクブランチへ取り込む
3. 一方を機械的に捨てず、意味上の意図を保って解消する
4. 競合周辺と影響範囲の検査を再実行する
5. 意味のある差分が変わった場合は PR 本文を更新し、再レビューを依頼する

複数の作業中セッションが関係する場合は、[競合時の手順](concurrent-sessions.md#競合時の手順)に従います。

## マージ

- 必須条件と要修正（`blocking`）のレビュー指摘を完了してからマージする
- 原則としてスカッシュマージし、PR のタイトルを最終コミットメッセージとして整える
- メンテナーによる通常手順の省略は、[緊急変更](repository-operations.md#緊急変更)の条件に限定する
- `main` の履歴を書き換えない
- マージ後に重大問題が起きた場合は、[切り戻し](repository-operations.md#切り戻しと壊れた-main)に従う

競合し得る PR のマージは順番に行い、一つ目のマージ後に、次の PR の競合と検査結果を再確認します。

## マージ後

1. マージ後の検査があれば結果を確認する
2. Issue を終了または更新し、残作業を担当者付きの後続 Issue にする
3. リモートのタスクブランチを削除する
4. 自分の worktree がクリーンで、必要なコミットがリモートへ送信済み・マージ済みか確認する
5. 一時ファイル、デバッグ設定、生成物を残していないことを確認する
6. 要件、ADR、ロードマップ、文書の状態を実態と整合させる
7. Issue / PR の状態を完了（`Done`）にする

Worktree の後片付けは自分のセッションだけを対象とし、他セッションのブランチ、worktree、プロセスを削除しません。

## 正式リリース前と将来の自動化

現在は[正式リリース前の方針](repository-operations.md#正式リリース前の方針)に従い、リリースブランチ、タグ、配布物、バックポートを作りません。

### 段階0の標準検査

Rust、Tauri、またはビルド構成を変更した場合は、リポジトリルートで次のコマンドを実行し、レビュー開始前に結果を PR へ記録します。文書だけの変更などで実行対象外としたコマンドがある場合は、そのコマンドと理由を記録します。Tauri CLI を初めて実行する環境では、先に `npm ci` で `package-lock.json` に固定された依存を導入します。

| 目的 | 標準コマンド |
| --- | --- |
| workspace の debug ビルド | `cargo build --workspace --locked` |
| workspace のテストと文書テスト | `cargo test --workspace --locked` |
| 全ターゲットの静的解析（警告を失敗扱い） | `cargo clippy --workspace --locked --all-targets -- -D warnings` |
| Rust コードの整形確認 | `cargo fmt --all -- --check` |
| Tauri アプリの release ビルド（インストーラー生成なし） | `npm run tauri -- build --no-bundle` |

Rust 以外の資産を変更した場合は、次も実行します。cargo と Tauri のビルドはこれらの
中身を検証しないため、破損しても上表のコマンドでは検出できません。いずれも外部依存を
導入せず、Node と PowerShell Core の標準機能だけで動作します。

| 目的 | 標準コマンド |
| --- | --- |
| `src/` の構文、相対 import の解決、`index.html` の参照先 | `node scripts/check-frontend.mjs` |
| 仮想スクロールの規模依存ロジック（クランプ、比例写像、破棄判定。[対象と判定方法](../verification/regression-checks.md)） | `node scripts/check-virtual-scroll.mjs` |
| 行選択モデル（飛び飛びの選択、ドラッグ、クランプ、コピー範囲の変換。[対象と判定方法](../verification/regression-checks.md)） | `node scripts/check-selection.mjs` |
| Markdown の相対リンクと見出しアンカーの整合（外部 URL は対象外） | `node scripts/check-docs-links.mjs` |
| PowerShell スクリプトの構文解析（実行はしない） | `pwsh -File scripts/check-powershell.ps1` |

`src/` のフロントエンドを変更した場合は、次も**手元で**実行します。上の5つと違い、release ビルド済みの実行ファイルと GUI セッションを必要とするため、CI では実行しません（理由と規約は[回帰検査の対象と判定方法](../verification/regression-checks.md#gui-自動検査scriptscheck-guimjs)）。

| 目的 | 標準コマンド |
| --- | --- |
| 画面操作を通したフロントエンドの回帰検査（起動、対象を開く、日時精度、仮想スクロール、ジャンプ、選択とコピー（ドラッグ・Ctrl+クリックを含む）、統合トグルの非活性化確認、タブ、詳細パネル、横スクロールの封じ込め） | `npm run tauri -- build --no-bundle` のあとに `node scripts/check-gui.mjs` |

このコマンドは OS のクリップボードを上書きし、`%TEMP%` へ試験データとスクリーンショットを書き出します（リポジトリ内へは何も生成しません）。実行前に副作用と規約を確認してください。

`--locked` を付けた検査では、意図しない `Cargo.lock` の更新を許可しません。`--no-bundle` はアプリ本体の release ビルドを検証し、正式な配布物は生成しません。

これらの検査は CI（[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)）でも push と PR ごとに自動実行されます。CI は目的ごとにジョブへ分かれ、ビルド入力に影響しない変更（文書、タスク記録、スクリプトなど）では Windows 上の Rust ジョブを省略します。判定できない場合は安全側で実行します。省略されたジョブが PR を滞らせないよう、ブランチ保護の必須ステータスチェックには、常に結果を返す集約ジョブ `CI 完了判定` を指定しています。設定は[リポジトリ運用規則の「`main` のブランチ保護」](repository-operations.md#main-のブランチ保護)を参照します。

技術スタックの最終確定後に、上記の標準コマンドを必要に応じて見直し、次をこの文書または専用の採用済み（`Accepted`）文書へ追加します。

- 開発環境の構築
- テストの分類と必須範囲
- 段階1（P13）の実機検証を踏まえて追加する CI の検査
- 依存関係の更新とセキュリティ検査
- バージョン付け、リリース、移行、サポート
