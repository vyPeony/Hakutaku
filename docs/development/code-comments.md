# コードコメント規約

- 状態: 採用済み（Accepted）
- 管理責任者: リポジトリメンテナー
- 最終更新日: 2026-08-16

## 目的

この文書は、Hakutaku のソースコードに書く doc コメントと行内コメントの書き方の正本です。現在のコードは、モジュールや公開項目の doc コメント（Rust の `//!`／`///`、JS の JSDoc）が充実しており、要件 ID や ADR、採用理由まで記載する実践が既に定着しています。一方で、関数本体の中で「なぜこの手順・この分岐なのか」を説明する行内コメントは少なく、その書き方を定めた正本もありませんでした。

対象読者は、Rust、Tauri、本プロダクトの要件 ID 体系に不慣れな読み手（初学者）です。この文書の目的は、そうした読み手が実装を追いながら「何が起きているか」だけでなく「なぜそうなっているか」を理解できる状態にすることです。この規約は現状の良い実践を明文化し、不足している行内コメントの書き方を補うためのものであり、既存の doc コメントの実践を置き換える理想論は述べません。コード本体への行内コメント補完そのものはこの文書の対象外です（別の変更で行います）。

コメントに使う言語そのものの規則（原則として日本語で書く）は、[リポジトリ運用規則の「使用言語と文章」](repository-operations.md#使用言語と文章)を正本とし、ここでは複製しません。

## 適用範囲

Rust（`crates/`、`src-tauri/`）と JS（`src/`）のソースコードに書くコメントに適用します。テストコード（`tests/`、`#[cfg(test)]`）は、本文の関数本体と性質が異なるため「[テストコードの受け入れ条件コメント](#テストコードの受け入れ条件コメント)」で別に定めます。

## doc コメントに書くこと

モジュール doc コメント（Rust の `//!`、JS のファイル冒頭のブロックコメント）と、公開項目の doc コメント（Rust の `///`、JS の `/** */`）には、次を書きます。

- **責務**: このモジュール・関数・型が何を担い、何を担わないか
- **要件 ID・ADR・Issue 番号との対応**: どの要件・設計判断を実装したものか（[要件 ID・ADR・Issue 番号の参照](#要件-idadrissue-番号の参照)を参照）
- **失敗の意味**: エラーの種類や異常系の戻り値が、呼び出し側にとって何を意味するか、呼び出し側がどう扱うべきか

3点目は、[エラーコード体系の採番手順](error-codes.md#採番手順)が定めるエラーコード定数の規則（「定数の doc コメントへ、失敗の意味と関連する要件 ID を書く」）と同じ考え方を、doc コメント全般に広げたものです。

複数手順から成る処理では、モジュール doc コメントに手順の一覧（番号付き箇条書き）を書き、各手順が対応する関数・要件 ID を示すと、読み手が実装ファイルをまたいで追跡できます（`crates/core-services/src/loader.rs`、`src-tauri/src/bootstrap/runtime.rs` を参照）。

### 良い例

`crates/config/src/load.rs` の `LoadOutcome`（`load_config` の戻り値）です。

```rust
/// `load_config` の結果。`hakutaku.yaml` の3つの起動経路に対応する
/// （`tasks/phase-03-configuration.md` の「設定の三つの起動経路」）。
#[derive(Clone, Debug)]
pub enum LoadOutcome {
    /// 正常起動。`hakutaku.yaml` があり、構文と値がすべて妥当だった。
    Loaded(HakutakuConfig),
    /// 既定値起動（`CFG-015`）。`hakutaku.yaml` が存在しない。
    ///
    /// 呼び出し側は組み込み既定値（[`HakutakuConfig::default`]）で起動し、
    /// 設定未検出を非致命的な通知として表示する。
    Missing,
    /// 安全モード（`CFG-016`）。`hakutaku.yaml` は存在するが構文または値が不正。
    ///
    /// 呼び出し側は誤設定を黙って既定値に置換せず、設定由来のデータソース・
    /// プロファイル・キャッシュを無効化した状態で UI を起動する。
    Invalid(ConfigErrors),
}
```

各バリアントに、要件 ID（`CFG-015`／`CFG-016`）だけでなく「呼び出し側は何をすべきか」まで書かれています。バリアント名（`Missing`）を言い換えるだけの説明（例:「`hakutaku.yaml` が無い場合」）では、この情報は伝わりません。

## 行内コメントに書くこと

関数本体の中では、次のいずれかに該当する場合に行内コメントを書きます。

- **分岐・失敗経路の意図**: この条件で処理を分ける理由、このエラー経路を選ぶ理由
- **順序依存の意図**: この処理をこの順番で呼ぶ必要がある理由（先に呼ぶと壊れる、後に呼ぶと意味がない、など）
- **「なぜこうするか」「なぜ他の方法にしないか」**: 一見遠回り・非対称に見える実装を選んだ根拠。特に、素直な実装（愚直な総当たり、単純な条件分岐など）を採らなかった場合は、その理由
- **非自明な不変条件・前提**: コードの型や名前だけでは読み取れない、呼び出し前後で成立している必要がある条件

すべての行に書く必要はありません。コード自体（変数名、関数名、型、制御構文）から意図が明らかな箇所には書きません。

### 良い例

`crates/config/src/load.rs` の `validate_data_sources` の一部です。

```rust
// 名前の重複検出（`tasks/phase-03-configuration.md` P03-2 の「重複」）。
// 名前は UI 表示とソース識別に使うため、同名の定義は起動時検証エラーに
// する。glob パターンの意味的な重複（同優先度 glob の重複検出）は P05 の
// 所有であり、ここでは扱わない。
let mut seen_names: std::collections::HashSet<String> = std::collections::HashSet::new();
```

「何をするか」（`HashSet` を作る）ではなく、「なぜ重複を検出するか」「この関数はどこまでを扱い、どこからを扱わないか」という、コードだけでは読み取れない設計上の境界線を説明しています。

## 書かないこと

- **コードをそのまま日本語へ言い換えただけの説明**: 変数名・関数名・制御構文から明らかな内容の言い換え。読み手はコードを読めば分かることを、コメントからも同じ手間で読まされるだけになります
- **変更履歴やレビュー向けの弁明**: 「以前はこうだったが直した」「レビュー指摘で修正」といった、PR の説明であるべき情報。コミット履歴や PR の議論はそちらが正本であり、コードへ残すと将来書き換えたときに陳腐化します
- **doc コメントの重複**: モジュール doc コメントや呼び出し先の doc コメントが既に説明している設計判断を、行内コメントで同じ言葉のまま繰り返すこと。読み手が二重に読む負担になり、片方だけ更新されて食い違う原因になります。既に説明済みの内容は要点の参照（関数名・要件 ID）に留め、その場所で新たに分かる情報（局所的な「なぜ」）だけを書きます

### 悪い例（実在コードではなく一般化した例）

```rust
// count に 1 を足す
count += 1;

/// 設定を検証する関数
fn validate(node: &MarkedYaml) -> Config { /* ... */ }

// 以前はここで panic していたが、レビュー指摘（2026-07 頃）で
// エラーを返すよう修正した
if !ok {
    return Err(/* ... */);
}
```

1行目はコードの言い換え、2行目は関数名を読めば分かる内容の反復（責務・要件 ID・失敗の意味のいずれも書かれていない）、3行目は変更履歴です。3行目を書き直すなら、「なぜエラーを返す必要があるか（呼び出し側が継続不能と判断する必要があるため、など）」を書きます。

## 要件 ID・ADR・Issue 番号の参照

既存コードの実例に合わせ、次の書式を使います。

- **要件 ID**（例: `LOG-022`、`CFG-008`、`DIST-006`）: バッククォートで囲みます。複数の要件にまたがる場合は読点で区切って列挙します（例: `DIST-006`、`DIST-008`）
- **ADR**: コード中は番号だけを本文に書きます（例: 「ADR-0005 により相対パスと…」）。バッククォートは付けません。`docs/` 配下の Markdown 文書から参照する場合は、[アーキテクチャ判断記録の一覧](../architecture/decisions/README.md#一覧)に合わせて `[ADR-0005](../architecture/decisions/0005-config-path-validation.md)` のようにリンクにします
- **Issue 番号**: `Issue #123` のように書きます。同一コメント内で既に文脈が明らかな場合は `#123` だけでも構いません

要件 ID・ADR の対応は、実装が正しいことの証明ではなく、読み手が正本文書へたどり着くための道しるべです。要件そのものの内容はコメントへ複製せず、要件文書側を参照します。

### 既存コードにある `tasks/...` への参照

既存のコメント（本書の例を含む）には、`tasks/phase-03-configuration.md` のようなフェーズ計画への参照が残っています。**`tasks/` は 2026-08-16 に削除しました。** ローカル開発時の実装計画であり、段階0（P00〜P12）の完了により役目を終えたためです。参照先の内容は次で確認できます。

- 削除前の全文: Git 履歴（[Issue #17](https://github.com/vyPeony/Hakutaku/issues/17)）
- 未完了・未着手だった内容: [Issue #12](https://github.com/vyPeony/Hakutaku/issues/12)（段階1検証）、[#13](https://github.com/vyPeony/Hakutaku/issues/13)（後続バックログ）、[#14](https://github.com/vyPeony/Hakutaku/issues/14)〜[#16](https://github.com/vyPeony/Hakutaku/issues/16)

既存の参照は、設計判断の由来を示す記述として残しています。**新しいコメントでは `tasks/` を参照しません。** 要件 ID、ADR、Issue 番号を使ってください。

## テストコードの受け入れ条件コメント

`tests/` および `#[cfg(test)]` 内のテスト関数には、テスト関数名や個々のアサーションを言い換える行内コメントではなく、そのテストが検証する受け入れ条件を、対応する要件 ID とともに `#[test]` の直前へ書きます。書式は次のいずれかです。

```rust
// 受け入れ条件: <検証する内容>（<関連する要件 ID>）。
#[test]
fn ...
```

```rust
// 受け入れ条件（<関連する要件 ID>）: <検証する内容>。
#[test]
fn ...
```

どちらの書式も既存コード（`crates/format-detection/tests/encoding.rs`、`src-tauri/src/targets.rs`）で使われており、要件 ID をどちらの位置に置くかは統一していません。新規に書く場合はどちらでも構いませんが、同じファイル内では既存の書式に合わせます。

## レビュー観点

コメントの過不足をレビューするときの基準は、次の一点です。

> その関数だけを読んで、前提を知らない読み手が処理の意図を追えるか

「充実したモジュール doc コメントが冒頭にあるから、関数本体は自明で構わない」とは判断しません。読み手は関数の途中から読み始めることも、モジュール doc コメントを読んだ後に時間を置いて関数本体だけを読み返すこともあります。分岐や順序依存の理由が関数本体に書かれていなければ、モジュール doc コメントの存在はその関数を読む助けになりません。

## コメントの陳腐化を防ぐ

コメントは、説明対象のコードと乖離した瞬間に、読み手を誤らせる負債になります。動作を変える PR では、その変更が影響する doc コメント・行内コメントを同じ変更で更新します。これは [`AGENTS.md` の「作業中」](../../AGENTS.md#作業中)が定める「利用者向けの挙動、形式、互換性、信頼境界が変わる場合は正本文書を同時に更新する」という原則を、コードコメントにも適用したものです。

レビューでは、差分が既存コメントの前提（分岐条件、順序、不変条件）を崩していないかを確認します。コメントが古い前提のまま残っている場合、削除または更新のどちらかを差分に含めます。
