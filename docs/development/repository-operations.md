# リポジトリ運用規則

- 状態: 採用済み（Accepted）
- 管理責任者: リポジトリメンテナー
- 最終更新日: 2026-08-15

## 目的

この文書は、Hakutaku リポジトリにおける役割、タスクの流れ、権限、品質条件、例外、切り戻し、正式リリース前の運用を定義します。Git の具体的な手順は[開発ワークフロー](workflow.md)、並行セッションの排他は[並行セッション](concurrent-sessions.md)を正本とします。

## ファイルの配置

リポジトリのルートは、ツールの自動検出、リポジトリ全体への適用、法的・配布上の理由によってルート配置が必要なファイルだけに保ちます。探しやすさや慣習だけを理由に、説明文書をルートへ追加しません。

| 配置先 | 置くもの |
| --- | --- |
| ルート | プロジェクトの入口 `README.md`、ライセンス `LICENSE`、AI エージェントの自動検出入口兼正本 `AGENTS.md`、特定ツールがルートでのみ自動検出する入口ファイル（Claude Code の `CLAUDE.md` など。正本ではなく `AGENTS.md` への入口に限る）、リポジトリ全体へ適用する `.gitignore`、`.gitattributes`、`.editorconfig`、採用したツールがルートを要求する機械可読のマニフェストやロックファイル |
| `docs/` | プロダクト、要件、設計、セキュリティ設計、開発運用、テンプレートなど、人が読む一般文書の正本 |
| `.github/` | 貢献ガイド、脆弱性報告、Issue / PR テンプレート、GitHub Actions など、GitHub の機能と直接結び付く文書と設定 |
| ツール固有ディレクトリ | そのツールが所定の場所を要求する、リポジトリ共通の機械可読設定だけ |

ツール固有ディレクトリへ説明用の README、作業中タスク、セッション状態、認証情報、個人設定を置きません。説明が必要な場合は `docs/` の該当する正本へ記載し、機械可読設定から参照できる場合だけリンクします。例えば `.codex/config.toml` を将来追加する場合や、Claude Code の `.claude/settings.json` を置く場合は、全員に適用する安定した設定だけを置き、個人のモデル、推論、承認、認証情報、MCP 設定をコミットしません。個人設定は `.claude/settings.local.json` のような Git 管理外のファイルへ置き、`.gitignore` で除外します。追加する設定の対象機能、信頼要件、設定が使えない場合の代替手順を文書化し、通常のレビューを行います。

ルートの入口ファイルを別ツール向けに追加する場合も、規則本文を複製せず、`AGENTS.md` を読ませる入口に限定します。現在は Claude Code 向けの `CLAUDE.md` が該当し、その内容の正本はルートの [`AGENTS.md`](../../AGENTS.md) です。

新しいルートファイルを追加する変更では、ルートでなければ機能しない理由を Issue または PR に記載します。既存の正本へ追加できる説明のために新しい文書を作らず、同じ規則を入口文書、テンプレート、ツール固有文書へ複製しません。配置を変える場合は、`README.md`、[`docs/README.md`](../README.md)、GitHub テンプレート、相対リンクを同じ変更で整合させます。

## 使用言語と文章

リポジトリに残る、人が読む文章の第一言語は日本語です。短くするために英単語を並べるのではなく、前提を知らない読者にも判断の理由と次の行動が伝わる、簡潔で分かりやすい日本語で書きます。

### 適用対象

- GitHub の Issue、プルリクエスト、レビュー、コメント、Discussion のタイトルと本文
- README、設計文書、要件、ADR、運用ガイド、テンプレート
- コミットメッセージ、引き継ぎ記録、リリースノート
- リポジトリに記録するコードコメント、診断の説明、開発者向けメッセージ
- 人間または AI エージェントが作成・更新する上記の文章

### 書き方

- 結論または目的を先に書き、背景、変更内容、確認結果、残る課題を読み分けられるようにする
- 一般的な日本語がある語は日本語を使う。例えば `scope` は「対象範囲」、`outcome` は「期待する結果」、`review` は「レビュー」、`rollback` は「切り戻し」と書く
- 正確な原語も必要な専門用語は、「下書きプルリクエスト（Draft PR）」のように日本語の説明を先にし、初出時に原語を添える
- Issue、プルリクエスト、コミットのタイトルは、何をどうする変更かを日本語で要約する。Conventional Commits の固定接頭辞を使う場合は `docs: 日本語の要約` の形式にする
- 状態名など照合に必要な固定値は、「着手可能（`Ready`）」のように日本語で意味を説明する
- ログや英語のエラーを載せる場合は原文を改変せず、その直前または直後に日本語の要約と必要な対応を書く

### 原文を保つ例外

次は、翻訳で機械処理や技術的な意味が変わるため、原文のままで構いません。ただし、読者が意味を判断できない場合は日本語の説明を添えます。

- ソースコード、API 名、型名、変数名、設定キー、コマンド、オプション
- ファイルパス、URL、ブランチ名、コミットハッシュ
- YAML の `id`、GitHub のラベル値、状態コードなど、機械処理する固定値
- `Closes #123`、`Refs #123` など、外部サービスが解釈する構文
- 製品名、規格名、ライセンス原文、ログ、エラーメッセージ、外部仕様からの引用
- Bot や外部ツールが自動生成し、このリポジトリ側で文章を制御できない記録

利用者が別の言語を明示的に指定した成果物と、多言語対応そのものを扱う成果物は例外です。日本語以外で届いた外部報告は言語だけを理由に拒否せず、メンテナーがトリアージ時に非機密の日本語要約を補います。脆弱性の内容は翻訳のために公開せず、[`.github/SECURITY.md`](../../.github/SECURITY.md) の非公開経路で扱います。

この規則はリポジトリ上の開発記録を対象とし、製品の画面、API 応答、外部向けエラーメッセージの表示言語は決めません。製品の表示言語は、利用者要件と多言語対応方針で別途決定します。

## 役割と責任

| 役割 | 責任 |
| --- | --- |
| メンテナー（Maintainer） | トリアージ、対象範囲の承認、規則・設定、最終的なマージ・リリース判断 |
| タスク責任者（Task owner） | Issue に割り当てられた人間。受け入れ条件、AI 利用を含む差分、引き継ぎ、完了に責任を持つ |
| 作業セッション（Writing session） | タスク責任者の下で、専用の対象範囲を変更する一つの人間または AI セッション |
| レビュー担当（Reviewer） | 作者と独立した観点で差分・検証・リスクを確認し、重大か軽微かを明示する |
| 統合担当（Integrator） | 複数タスクの順序、横断ファイル、競合を統合する担当。通常はメンテナー |

単独開発の現在は、メンテナー、タスク責任者、レビュー担当、統合担当を同一の利用者が兼ね、作業セッションは人間セッションまたは AI セッションが担います。

AI を使ったことは責任移譲を意味しません。AI が作成した差分、説明、テスト結果を、タスク責任者またはレビュー担当が確認します。セキュリティ、信頼境界、認証情報、外部通信、永続化、依存関係、リリースに関わる高リスク変更は、人間が差分をレビューするまで完了としません。

## タスク記録

通常、非自明な変更または並行セッションで行う変更は、書き込み開始前に着手可能（`Ready`）な GitHub Issue を持ちます。Issue には最低限、次を記録します。

- 解決する問題と期待する結果
- 対象範囲と対象外
- 検証可能な受け入れ条件
- 人間のタスク責任者と担当者
- 関連する文書、ADR、Issue、PR
- 依存タスクと既知のリスク

例外は次のとおりです。

| 状況 | タスク記録 | 共有できる範囲 |
| --- | --- | --- |
| 通常の非自明・並行作業 | 着手可能（`Ready`）な Issue。下書き PR は差分と検証の正本 | 通常フロー |
| 単独の誤字、リンク、明白な一ファイル修正 | PR をタスク記録にできる | 一つの作業セッションのみ |
| GitHub を利用できない、または書き込み権限がない状態で、利用者が明示したローカル作業 | 現在の利用者タスクと引き継ぎを暫定記録にできる | 同一利用者が管理する一対一の継続・引き継ぎだけ。それ以外の独立タスクとの共有、リモート送信、PR、リポジトリ単位の引き継ぎ前に、着手可能（`Ready`）な Issue へ同期 |
| 脆弱性 | 非公開の脆弱性報告（Private vulnerability report）または Security Advisory | 公開 Issue や PR に詳細を出さない |

暫定的なローカルタスクは、リポジトリ全体の担当権限を取得せず、既存の作業中範囲と競合しないと確認できる範囲だけを扱います。着手可能（`Ready`）な Issue への同期は、利用者または GitHub の書き込み権限を持つ人が行います。

Issue の作成は、着手承認や実装予定を意味しません。メンテナーが背景と受け入れ条件を確認し、着手可能（`Ready`）と判断してから着手します。

## タスクの状態

| 状態 | 意味 | 次の状態へ進む条件 |
| --- | --- | --- |
| 提案中（`Proposed`） | トリアージ前 | 着手可能、情報不足、不採用、重複のいずれかを判断 |
| 情報不足（`Needs info`） | 背景、対象範囲、受け入れ条件など、着手判断に必要な情報が不足 | 必要情報を追加し、再トリアージする |
| 着手可能（`Ready`） | 対象範囲と受け入れ条件が着手可能 | タスク責任者と作業セッションが担当範囲を宣言 |
| 作業中（`In progress`） | 専用の対象範囲で作業中 | レビュー、阻害中、または引き継ぎへ進む |
| 阻害中（`Blocked`） | 外部判断・依存・権限が必要 | 解除条件を満たし、作業中へ戻す |
| レビュー中（`Review`） | 下書き解除条件を満たした PR をレビュー中 | マージするか作業中へ戻す |
| 完了（`Done`） | マージとマージ後処理が完了 | 原則として最終状態 |
| 不採用・重複（`Declined` / `Duplicate`） | 実装しない、または別タスクへ集約 | 理由と関連先を残す |

状態は Issue 本文または最新の明示的な状態コメントで追跡します。ラベルや GitHub Project を導入した場合は自動化できますが、未導入のラベルを必須条件にしません。

## 担当範囲

- タスク責任者は人間の責任者、作業セッションは実行主体として分けて記録する
- 着手時に Issue へセッション、ブランチ、予定するファイル・ディレクトリの範囲、依存関係、状態を記載する
- 担当範囲の宣言が競合した場合、後続セッションは書き込みを開始せず、メンテナーが分割、順序、統合担当を決める
- セッションが停止しただけでは担当は解除されない。保留理由と引き継ぎを残し、後任が受諾した時点で移管する
- ロードマップ、ローカル worktree、チャット、未コミットの差分を、作業中の担当範囲の正本にしない

詳細と記録例は[並行セッション](concurrent-sessions.md)を参照します。

## 権限と外部への変更

人間・AI ともに、自分へ付与されたリポジトリ権限とタスクの対象範囲内で操作します。次は、メンテナーまたは明示的に委任された人だけが行います。

- リポジトリ設定、ブランチ保護、秘密情報、環境、外部連携の変更
- マージ、タグ、リリース、成果物やパッケージの公開
- Security Advisory の公開と脆弱性情報の開示
- 共有ブランチの削除、緊急時における通常条件の省略

AI の詳細な権限境界は、ルートの [`AGENTS.md`](../../AGENTS.md) を参照します。

## レビュー開始条件

下書き状態（Draft）を解除する前に次を満たします。

- 対象範囲と受け入れ条件が現在の PR 本文・Issue と一致する
- 作者が差分全体を自己レビューした
- 現在利用可能な関連テスト、静的解析、整形、文書・手動検査が成功した
- 関連する要件、設計、ADR、利用者文書を更新した
- 未実施の検査、既知の制約、互換性、セキュリティ、データへの影響を記載した
- 最新の `main` との競合と、他の作業中タスクの担当範囲との重複がない
- 認証情報、本番データ、デバッグ用成果物、意図しない生成物が差分にない

CI は [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) で導入済みであり、標準検査（[開発ワークフローの「段階0の標準検査」](workflow.md#段階0の標準検査)）を push と PR ごとに自動実行します。ブランチ保護による必須化は P13 完了後に扱います。存在しないコマンドの実行を装いません。

## レビュー判断

- 指摘を「要修正（`blocking`）」または「任意・提案（`non-blocking / suggestion`）」に区別する
- 重大な指摘は、修正するか、安全に対象範囲を縮小して原因を差分から除去するまでマージしない
- 後続 Issue へ送れるのは、レビュー担当またはメンテナーが理由を記録して「任意（`non-blocking`）」へ再分類した項目だけとする
- 読み取り専用性、セキュリティ、データ安全性、受け入れ条件未達、必須検証の失敗は、未解消のまま再分類しない
- 対象範囲や重要差分がレビュー後に変わった場合、PR 本文と受け入れ条件を更新し、影響範囲を再検証、再レビューする
- レビュー担当が作者のブランチを直接変更する場合、先に合意し、変更内容を PR に残す
- 単独開発の自己マージでも PR、自己レビュー、検証結果を残す

## 切り戻しと壊れた main

マージ後に `main` の重大な後退、データやセキュリティのリスク、ビルド不能が判明した場合、履歴を書き換えません。

1. 影響を記録し、必要なら新規変更のマージを止める
2. 原因 PR のスカッシュコミットを戻す、取り消し PR を第一候補にする
3. 小さく即時検証でき、取り消しより安全な場合だけ後続修正を選ぶ
4. 取り消しまたは修正を元の Issue、PR と相互にリンクする
5. 影響範囲の検査と文書状態を更新する

## 緊急変更

緊急扱いは、データ漏えい・破損、公開済み脆弱性、`main` の全面停止、外部仕様変更による重大障害など、待つリスクが通常条件を短縮するリスクを明確に上回る場合に限定します。

- 原則として `fix/...` の最小差分 PR を使う
- 利用可能な最小限の検証、秘密情報の除去確認、切り戻し案は省略しない
- 省略したレビューや検査、理由、判断者を非機密な範囲で記録する
- 脆弱性の詳細は公開 Issue / PR に書かず、Security Advisory 内で扱う
- 次の作業機会に通常レビュー、追加テスト、原因分析、規則や道具の改善を行う

直接の送信が避けられなかった場合も、事後に PR 相当の差分、判断、検証、切り戻し記録を残します。

## マージ後

- マージ後の検査がある場合は結果を確認し、失敗時は修正または取り消し方針を記録する
- `Closes` で閉じなかった Issue を更新し、残作業を責任者付きの Issue に分ける
- リモートのタスクブランチを削除し、作業者自身の不要な worktree を安全に解放する
- 一時ファイル、デバッグ設定、生成物が残っていないことを確認する
- ADR、要件、ロードマップの状態を実態と整合させる。未決事項を暗黙に採用済み（Accepted）にしない
- Issue / PR の動的状態を `Done` にする

## 正式リリース前の方針

現在は正式リリース前です。

- `main` は開発版であり、安定した API、設定スキーマ、保存形式、対応プラットフォーム、互換性をまだ約束しない
- 破壊的変更を無言で行わず、PR に影響を明示し、関連文書とサンプルを同時に更新する
- リリースブランチ、バージョンタグ、成果物の公開、バックポートを行わない
- セキュリティ対応は [`.github/SECURITY.md`](../../.github/SECURITY.md) に従い、現在は最新の `main` を対象とする

初回リリース前に、バージョン付け、変更履歴・リリースノート、対応バージョン・環境、成果物の来歴・署名、移行・切り戻し、リリース権限、セキュリティ修正のバックポートを、採用済み（`Accepted`）の運用文書として追加します。
