## 記法と範囲

本書の ID 付き要件表を利用者機能の確定事項の正本とします。本書の状態は、この変更が `main` へマージされた時点で採用済みになります。要件 ID は版1.10を保ち、実装と検証の順序は[ロードマップ](../roadmap.md)を参照します。

初期リリースはテキストログを中心とします。`LOG-017`～`019`、`DB-*`、`DCM-*`、DICOM・キャッシュ関連設定は後続リリースです。後続要件も確定要件として本書に保持しますが、初期リリースの実装範囲には含めません（`PROD-009`）。

## テキストログ

### 確定要件

| ID | 要件 |
| --- | --- |
| LOG-001 | テキスト形式のログファイルを読み込めること。 |
| LOG-002 | 基本的に各行の先頭に日時があるログを対象とすること。 |
| LOG-003 | 項目の区切りは主に空白だが、空白数などが一定でない形式を扱えること。 |
| LOG-004 | ログレベルが存在しない形式も扱えること。 |
| LOG-005 | ファイルごとにログ形式が異なる可能性を考慮すること。 |
| LOG-006 | 複数のログファイルを同時に開けること。 |
| LOG-007 | 複数ファイルのログを、ファイル横断で時系列順に把握しやすく表示できること。 |
| LOG-008 | 時系列統合表示は常時強制せず、ユーザーが ON/OFF を切り替えられること。 |
| LOG-009 | 既知の日時書式として、後述する6形式を扱えること。 |
| LOG-010 | 開いているログへの追記をリアルタイム追従する機能は初期要件に含めない。ログローテーション、ファイル名変更、ファイル切り替えへの自動追従も不要とする。 |
| LOG-011 | 対象ログの日時には年が含まれるものとする。 |
| LOG-012 | タイムゾーン表記のない日時は、同じ端末のローカル時刻として比較する。 |
| LOG-013 | ログ解析プロファイルは設定ファイルによる指定を優先し、内容からの自動判定は補助的な扱いとする。 |
| LOG-014 | 日時を持たない継続行は、直前の日時付き行と同じ論理ログ項目の一部として扱う。時系列統合表示でも直前の日時付き行と一体で表示する。 |
| LOG-015 | 時系列統合表示が OFF の場合は、ファイル別タブで表示を切り替える。分割表示は不要とする。 |
| LOG-016 | 複数の端末やプロセスの時計がずれている場合も、Hakutaku では時刻補正を行わず、ログに記録された日時をそのまま使用する。 |
| LOG-017 | 初期リリースには検索・絞り込みを含めない。ログビューアの第2段階では検索・絞り込みを必須機能とする。 |
| LOG-018 | ログビューアの第2段階では、文字列検索、正規表現検索、日時範囲、ログレベル、読み込み元ファイルによる絞り込みを提供する。 |
| LOG-019 | 検索・絞り込み結果のファイルエクスポートは不要とする。 |
| LOG-020 | 設定ファイルに記載されていない任意のローカルログファイルも、ファイル選択 UI からアドホックに開けること。設定編集と再起動を必須としない。 |
| LOG-021 | ログ解析プロファイルとファイルの対応付けは、手動選択、絶対パス完全一致、優先度付き glob、内容による自動判定の順に解決すること。 |
| LOG-022 | 複数の日時書式またはプロファイルが同時に一致して一意に決められない場合、貪欲マッチで推測せず、プロファイル選択を求めるか日時未解析の生表示にすること。 |
| LOG-023 | 開いている元ファイルの削除、切り詰め、置換を検知した場合、その対象の追加読み込みを停止し、索引を無効化してエラーを表示すること。アプリ全体は継続動作すること。 |
| LOG-024 | 解析した日時には元の精度（分、秒、1/100秒、1/1000秒など）を保持すること。利用者へ提示する場合に失わないこと（現行 UI に提示箇所は無く、統合表示の改修（[Issue #82](https://github.com/vyPeony/Hakutaku/issues/82)）で表示を予定）。比較・マージにはミリ秒精度へ正規化した日時比較キーを使用し、書式に含まれない下位桁は 0 として補完すること。 |
| LOG-025 | `LOG-DT-003`／`LOG-DT-004` の秒未満2桁は 1/100 秒とする。`.45` および `:45` は 450 ミリ秒として扱う（45 ミリ秒ではない）。 |
| LOG-026 | `ENV-010` により、**同じ端末で稼働する他の業務ソフトウェアが書き込み中のログを開くことを標準ケースとする**。読み込み時点の末尾が行の途中で終わっている場合、その断片を破棄せず「書き込み途中の可能性がある未確定行」として区別して表示すること。解析エラーとして扱わないこと。 |
| LOG-027 | 他の業務ソフトウェアの稼働中でもログファイルを読み取れることを前提とする（`Q-038`。稼働中にメモ帳でログを開けた実績による）。ただし全ログファイル・全機種・全動作局面での保証ではないため、共有を許可しない方法で開かれていて読み取れない場合の経路も実装する。その場合はロックの強制解除やコピーによる迂回を行わず、対象ファイルと理由を表示し、再試行できるようにすること。他の対象の閲覧は継続すること。 |
| LOG-028 | `LOG-010` のとおり追記へのリアルタイム追従は行わないため、開いた後に追記された内容は表示されない。利用者が明示的に再読み込みを指示した場合に限り、対象を開き直して最新状態を反映できること。 |

`LOG-017`～`019` は後続リリースの要件です。初期リリースでは検索・絞り込みと検索結果のファイルエクスポートが存在しないことを確認します。

### 既知の日時書式

| ID | 書式 | 例 | 元の精度 | 比較キー |
| --- | --- | --- | --- | --- |
| LOG-DT-001 | `YYYY/MM/DD HH:mm:ss.SSS` | `2026/07/28 15:12:23.456` | ミリ秒（3桁） | `15:12:23.456` |
| LOG-DT-002 | `YYYY-MM-DD HH:mm:ss:SSS` | `2026-07-28 15:12:23:456` | ミリ秒（3桁） | `15:12:23.456` |
| LOG-DT-003 | `YYYY/MM/DD HH:mm:ss.SS` | `2026/07/28 15:12:23.45` | 1/100 秒（2桁） | `15:12:23.450` |
| LOG-DT-004 | `YYYY/MM/DD HH:mm:ss:SS` | `2026/07/28 15:12:23:45` | 1/100 秒（2桁） | `15:12:23.450` |
| LOG-DT-005 | `YYYY/MM/DD HH:mm:ss` | `2026/07/28 15:12:23` | 秒 | `15:12:23.000` |
| LOG-DT-006 | `YYYY/MM/DD HH:mm` | `2026/07/28 15:12` | 分 | `15:12:00.000` |

全書式をミリ秒精度の比較キーへ正規化し、書式にない下位桁は 0 とします。原文と元の精度は別に保持し、表示で失いません。同一比較キーではファイル表示順、次にファイル内出現順を使う案を、暫定設計および暫定的な受け入れ条件として検証します。この同順位規則は ID 付き確定要件へ昇格させません。

## 文字コード

| ID | 要件 |
| --- | --- |
| ENC-001 | Windows の OS 言語設定に応じた ANSI エンコーディングのログを扱えること。ここでいう ANSI は Shift_JIS 固定ではなく、ログ生成環境で使用された Windows コードページを指す。 |
| ENC-002 | OS 言語設定に依存しない UTF-8 のログを扱えること。 |
| ENC-003 | UTF-8 は BOM ありと BOM なしが混在する可能性を考慮すること。 |
| ENC-004 | 同じ配置場所・ファイル種別でも、ログ生成環境の OS 言語設定によって ANSI エンコーディングが変わり得ること。生成環境と Hakutaku 実行環境のコードページが同じとは限らない。 |
| ENC-005 | 設定で文字コードを明示指定できること。明示指定（ログ解析プロファイルの `encoding` の名前指定、または `ansi_codepage`）があれば、それを最優先で使用する。`auto`（明示指定なし）の場合は、UTF-8 BOM、BOMなし UTF-8 の妥当性確認、実行環境の Windows ANSI コードページの順に判定する。 |
| ENC-006 | UTF-16 LE/BE は初期リリースの対応対象に含めない。UTF-16 の BOM（`FF FE` / `FE FF`）を検出した場合は、明示指定の有無にかかわらず未対応として通知し、そのファイルを読み込まない。 |
| ENC-007 | ログ解析プロファイルに、`ansi_codepage: 932` のような任意の Windows コードページ識別子を指定できること。 |

明示指定は自動判定より優先します。ただし UTF-16 の BOM の判定だけは明示指定より前に行い、明示指定があっても `ENC-006` の未対応通知に乗せます。明示指定を先に見ると、UTF-16 のファイルが「指定した文字コードで読めた」ことになり、全面的に文字化けした本文が正常な内容として表示されてしまうためです。UTF-8 BOM と明示指定が矛盾する場合は警告し、暗黙に別エンコーディングへ切り替えません。デコードできない元バイトを破棄せず、対象、位置、選択された文字コードを表示します。

`encoding` に指定できる文字コード名は `auto`、`utf-8`、`windows-<コードページ番号>`（例: `windows-932`）です。`encoding` の名前指定と `ansi_codepage` は同時に指定できません（同時に書くと `encoding` だけが使われ、`ansi_codepage` は黙って無視されるためです）。受理できない文字コード名、UTF-16 のコードページ（1200 / 1201）、デコードできないバイト列の位置を報告できないコードページ、実行環境に存在しないコードページは、いずれも `CFG-016` の起動時検証でまとめて提示します。

## 選択とクリップボードコピー

| ID | 要件 |
| --- | --- |
| COPY-001 | ビューア上の行を、クリック（単一）、`Shift+クリック`（範囲）、`Ctrl+クリック`（行単位の追加・除外による飛び飛びの選択）、ドラッグ（連続範囲）、`Ctrl+A`（全選択）で選択できること。 |
| COPY-002 | 選択範囲を `Ctrl+C` で Windows のクリップボードへコピーできること。コピー内容は常に選択行の原文そのままとする。 |
| COPY-003 | クリップボードコピーはファイルエクスポートとは区別し、初期リリースから提供する。 |
| COPY-004 | 1回のコピー上限は、UTF-8換算 16 MiB または10万行のうち先に到達した方とする。上限値は設定で変更可能にする。飛び飛びの選択では、選択したすべての範囲の合計に対して判定する。 |
| COPY-005 | 選択範囲が上限を超える場合は部分コピーを黙って行わず、コピー全体を拒否して上限と選択量を表示する。 |
| COPY-006 | DICOM タグ、DB セル、ログ本文には機密情報または個人を識別し得る情報が含まれ得ることを前提とし、コピーは明示的なユーザー操作時だけ行う。 |

コピー内容を原文そのままに限り、列の選択（行番号・日時・本文の組）と quoted TSV を提供しないことは、[ADR-0011](../architecture/decisions/0011-copy-raw-text-only.md)の決定です（[Issue #85](https://github.com/vyPeony/Hakutaku/issues/85)。それ以前の形式は[ADR-0009](../architecture/decisions/0009-clipboard-copy-format.md)にあり、現在は廃止しています）。複数行ログの改行を保持すること、上限判定後に必要なバッファをメモリ予算へ予約してから生成することは暫定設計です。

### プライベートタグ解析スキーマ仮案 v1

次のスキーマは**暫定方針**です。これで最初の実装を進めますが、実データの試作結果により `config_version` を上げて改訂できます。ID 付き確定要件へ昇格させません。

パーサー定義は `name`、`group`、`element`、`struct_length`、`fields` を必須とします。任意項目は `private_creator`、`byte_order`（既定 `little_endian`）、`default_string_encoding`（既定 `utf-8`）、`repeat`（`once` または `fill`、既定 `once`）、`on_length_mismatch`（`error` または `skip`、既定 `error`）です。

フィールド定義は `name`、`offset`、`type` を必須とします。`string`、`bytes`、`padding` では `length` も必須です。任意項目は `count`（既定1、上限1024）、`encoding`、`byte_order`、`description` です。

| 分類 | 型名 | 長さ |
| --- | --- | --- |
| 符号なし整数 | `uint8`、`uint16`、`uint32`、`uint64` | 1／2／4／8バイト |
| 符号付き整数 | `int8`、`int16`、`int32`、`int64` | 1／2／4／8バイト |
| 浮動小数点 | `float32`、`float64` | 4／8バイト |
| 文字列 | `string` | `length` で指定 |
| バイト列 | `bytes` | `length` で指定し16進表示 |
| パディング | `padding` | `length` で指定し解析結果には表示しない |

文字コード名は `utf-8`、`ascii`、`windows-<コードページ番号>` を使います。暗黙のアラインメントやパディングを持ち込まず、詰め物は `padding` として明示します。

起動時には、フィールド範囲が `struct_length` を超える、フィールドが重なる、長さ指定の過不足、`count` の範囲外、未知の型・文字コード、名前の重複、不正な16進タグを検出します。違反時は `CFG-016` の安全モードで起動し、ファイル名・行・列・理由を表示します。

## データベース（後続リリース）

`DB-*` は確定要件ですが、`PROD-009` により初期リリースには含めません。SQLite のみを最初の DB 実装対象とし、SQL Server は要件が確定するまで設計・実装しません。

| ID | 要件 |
| --- | --- |
| DB-001 | SQLite データベースを、論理的内容を変更しない読み取り専用接続で開くこと。`ENV-010` により、**同じ端末で稼働する他の業務ソフトウェアが使用中のデータベースへ接続するケースを標準ケースとして扱う**。使用中でない状態を前提にした実装・試験にしないこと。 |
| DB-002 | **SQL Server 対応は初版では提供しない**（`Q-032`、`DEC-011`）。将来候補としては残すが、要件が確定するまで設計・実装の対象に含めない。対象バージョン、認証方式、暗号化接続、名前付きインスタンス、認証情報の保存方針が判明した時点で再検討する。 |
| DB-003 | GUI 操作で任意のテーブルを選び、その内容を表示できること。 |
| DB-004 | 複数テーブルの同時並列表示は必須としない。 |
| DB-005 | 別テーブルの内容へ、タブなどで切り替えられること。 |
| DB-006 | データベースの論理的内容およびスキーマを編集しないこと。 |
| DB-007 | SQLite の最初の実装では、選択したテーブルの全レコードを閲覧対象とする。並べ替え、検索、絞り込みは必須としない。 |
| DB-008 | SQLite ビューアの第2段階では、レコードの検索・絞り込みを検討対象とする。 |
| DB-009 | 他プロセスの排他ロックにより SQLite を開けない場合、ロックを強制解除せず、開けない理由をユーザーへ表示する。 |
| DB-010 | SQLite の BLOB 列は、最初の実装では BLOB であることとバイトサイズだけを表示する。内容の16進表示や文字列表示は不要とする。 |
| DB-011 | 現時点のデータベース対応では認証情報を扱わない。認証を必要とする接続先は、要件が確定するまで対応対象外とする。 |
| DB-012 | WAL モードの SQLite を参照する際、SQLite ライブラリが必要とする `-wal`、`-shm` の作成、アクセスまたは更新を許容する。主 DB の論理的内容を変更しないことと、付随ファイルへの書き込みが発生し得ることを区別する。 |
| DB-013 | WAL モードで、必要な `-wal` と `-shm` が存在して読み取り可能という条件を満たさず、かつ DB ディレクトリにも書き込みできない場合は、読み取り専用接続に失敗し得ることを既知の制約とする。 |
| DB-014 | 使用中または変更される可能性がある DB に対して `immutable=1` を自動適用しない。初期実装では `immutable=1` を使用しない。 |

SQLite は更新系 SQL、DDL、永続状態を変更する PRAGMA を発行しません。WAL の `-wal`、`-shm` を独自に無視、コピー、削除、強制解除せず、SQLite の整合性・ロック規則に従います。大きなテーブルを一括メモリ取得しないことは暫定設計で、ページングまたは仮想スクロールを候補とします。

## 設定ファイル

初期リリースでは、実行ファイルと同じフォルダの固定名 `hakutaku.yaml` を使用します。`CFG-004`、`CFG-005`、`CFG-019` は DICOM 提供時、`CFG-012`、`CFG-021` はキャッシュ提供時に適用する後続要件です。

| ID | 要件 |
| --- | --- |
| CFG-001 | JSON は使用しない。 |
| CFG-002 | 初期リリースでは YAML を使用する。HCL は初期対応に含めない。 |
| CFG-003 | 読み込み先のフォルダやファイルなどのパスを事前定義できること。 |
| CFG-004 | DICOM プライベートタグの対象と解析形式を拡張可能に定義できること。 |
| CFG-005 | DICOM 内文字列の文字コードを指定できること。 |
| CFG-006 | 設定変更の反映はアプリ再起動時でよく、起動中の再読み込みは不要とする。 |
| CFG-007 | `PERF-008` のヒープ確保量を基準とするメモリ予算を設定できること。初期値は 2 GB とする。 |
| CFG-008 | ログ解析プロファイルごとに文字コードまたは自動判定を指定できること。`ansi_codepage` に任意の Windows コードページ識別子を明示でき、未指定時のみ実行環境の Windows ANSI コードページを使用できること。 |
| CFG-009 | 保持する設定は1つとし、アプリ内で複数設定を切り替える機能は不要とする。 |
| CFG-010 | 読み込み対象にはローカルの絶対パスを使用する。相対パスとネットワーク共有パスは対応不要とする。 |
| CFG-011 | **索引キャッシュは初期リリースでは提供しない**（`Q-034`、`DEC-043`）。設定項目、保存先フォルダ、消去手段のいずれも初期リリースには含めない。後続リリースで提供する場合は、設定で ON/OFF でき、既定値を OFF とする。 |
| CFG-012 | 後続リリースでキャッシュを提供する場合、保存内容、保存期間、容量に運用制約を設けない。ログ本文、DB セル値、DICOM タグ値を平文で保存してよく、暗号化、アクセス制御、保持期限、自動削除のいずれも要件としない。削除は利用者による手動操作のみとする。 |
| CFG-013 | 現時点では DB 認証情報を設定ファイルに保持しない。 |
| CFG-014 | 設定ファイルは実行ファイルと同じフォルダに、固定名 `hakutaku.yaml` で配置する。 |
| CFG-015 | `hakutaku.yaml` が存在しない初回起動でも、組み込み既定値でアプリを起動し、アドホックなファイル選択を利用できること。設定未検出を非致命的な通知として表示する。 |
| CFG-016 | `hakutaku.yaml` が存在するが構文または値が不正な場合、誤設定を黙って既定値に置換しない。安全モードで UI を起動し、設定由来のデータソース、プロファイル、キャッシュを無効化して、ファイル名・行・列・理由を表示すること。 |
| CFG-017 | 設定ファイルは起動時のショートカット、既定値、解析プロファイルを提供するものであり、アドホックなファイル・フォルダ選択の前提条件ではない。 |
| CFG-018 | クリップボードコピーの最大バイト数と最大行数を設定できること。初期値は 16 MiB、10万行とする。 |
| CFG-019 | DICOM フォルダ走査の最大ファイル数と最大深さを設定できること。初期値は1万ファイル、32階層とする。 |
| CFG-020 | 診断ログのローテーションサイズと保持数を設定できること。初期値は1ファイル 10 MiB、5世代とする。 |
| CFG-021 | 後続リリースでキャッシュを提供する場合、索引キャッシュは対象ファイルの指紋（サイズ、最終更新時刻、および先頭・末尾の部分ハッシュ）と対応付けて保存すること。読み込み時に指紋を照合し、一致しない場合はキャッシュを使用せず破棄して索引を再構築すること。指紋を照合できない場合もキャッシュを使用しないこと。**この要件を満たせない実装でキャッシュを提供してはならない。** |
| CFG-022 | フロントエンドが保持する行数およびバイト数の上限を設定できること（`PERF-012`）。初期値は段階0（P04-3）の実測により決定済み（保持行数 10,000 行、保持バイト数 64 MiB）。実測を踏まえた見直しの要否は段階1（P13）で判断する。 |
| CFG-023 | Fixed Version WebView2 Runtime を強制使用するかを設定できること（`DIST-017`）。既定は自動判定とする。 |
| CFG-024 | 解析の同時実行数、読み込み時の I/O 発行間隔、Hakutaku プロセスの優先度を設定できること（`PERF-014`）。既定値は運用先の専用端末での実行を前提に定める。 |

アプリは `hakutaku.yaml` を自動生成・上書きしません。初期リリースでは `cache` セクションと `cache` フォルダを作りません。設定の形式バージョン、共通設定、データソース、ログ解析プロファイル、DICOM 解析規則の具体的な構造は暫定設計であり、対応する ID 付き要件を満たす範囲で段階0に確定できます（`VER-007`）。

## 権限昇格

| ID | 要件 |
| --- | --- |
| PRIV-001 | Hakutaku は通常、Windows の `asInvoker` 相当の非昇格プロセスとして起動する。常時管理者権限を要求しない。 |
| PRIV-002 | 参照対象へのアクセスが拒否された場合、理由を表示し、ユーザー操作により Windows の `runas` 相当で新しい昇格済み Hakutaku プロセスを開始できること。実行中プロセス自体が昇格するものとは扱わない。 |
| PRIV-003 | 元の非昇格プロセスは開いた状態を維持し、昇格プロセスへ既存タブ、表示位置、解析済みデータを自動転送しない。昇格プロセスでは対象を選び直す。 |
| PRIV-004 | 昇格が拒否・キャンセル・ポリシーで禁止された場合、元プロセスを終了せず、アクセスできなかった対象だけをエラーにする。 |

UAC の有効・無効や資格情報入力の要否は Windows のポリシーに従います。実行中プロセスが権限だけを変更する動作は定義しません。

## エラー処理

| ID | 要件 |
| --- | --- |
| ERR-001 | 1ファイル、1行、1 DICOM タグまたは1 DB 接続の失敗で、無関係な参照対象の閲覧を停止しない。 |
| ERR-002 | ユーザー向けエラーには、対象を識別できる名称またはパス、発生位置、理由、継続可否、必要な次操作を示す。`DIAG-003`／`DIAG-004` により実値の表示を制限しないため、原因調査に必要であればフルパスを表示してよい。 |
| ERR-003 | ログおよび DICOM の参照元ファイルは変更せず、不要なロックやタイムスタンプ変更を避ける。SQLite には `DB-012`～`014` の例外と制約を適用する。 |
| ERR-004 | 設定駆動のバイナリ解析には、読み取り範囲、配列長、再帰、処理時間の上限を設ける。 |

接続拒否、権限不足、共有違反、未対応形式、解析失敗、設定不正、資源上限、キャンセルを区別し、失敗した対象以外の取得済み結果と操作を維持します。

## 暫定設計と受け入れ確認

確定要件と区別して、次を現時点の実装候補とします。

- ログ解析プロファイルには日時、区切り、ログレベル、文字コード、パスとの対応付けを持たせる。
- ファイルを個別に解析・索引化し、統合結果全体の複製を避けて時系列マージする。
- 全件一括読み込みを避け、チャンク読み込み、遅延表示、仮想スクロール、ページングを使う。
- DICOM は仮想化したファイル一覧と選択式のタグ比較表を第一案とする。
- SQLite の大きなテーブルはページングまたは仮想スクロールで段階取得する。
- 設定は起動時に一度読み、形式バージョンを持たせる。壊れた設定でも UI は安全モードで起動する。

暫定設計を変更しても、対応する ID 付き要件を満たす限り要件変更とは扱いません。暫定設計を確定する場合は ADR または関連する採用済み文書へ判断理由を記録します。
