## 導入手順（両運用形態、`DIST-015`）

Evergreen WebView2 Runtime の導入状況は機種により異なるため（`ENV-008`）、次の両方を正式な運用形態として保守しています。

### 形態A: Evergreen WebView2 Runtime 導入済み機種

1. `Hakutaku-0.1.0.zip` を展開する。
2. できた `Hakutaku` フォルダをそのまま実行可能な場所（書き込み権限のあるローカルフォルダ）へ配置する。
3. `Hakutaku.exe` を実行する。導入済みの Evergreen Runtime が自動的に使用される。

### 形態B: Evergreen WebView2 Runtime 未導入機種（`DIST-012` の既知の制約）

1. `Hakutaku-0.1.0.zip` を展開する。
2. `Hakutaku-WebView2Runtime-150.0.4078.105.zip` を、できた `Hakutaku` フォルダの直下へ展開する（`Hakutaku\WebView2Runtime\` になるように、フォルダの中身ではなく `WebView2Runtime` フォルダごと展開する）。
3. `Hakutaku.exe` を実行する。Evergreen が見つからない場合、実行ファイル直下の `WebView2Runtime`（Fixed Version）が自動的に使用される。

事前確認や配置手順の詳細は[WebView2 Runtime 導入手順書](../deployment/webview2-runtime-installation.md)を参照してください。

どちらの形態でも、`logs`・`temp`・`WebView2`（WebView2 のユーザーデータ）は Hakutaku 自身が起動時に自動生成します。ネットワークからの取得は行わず、配布物一式だけで起動できます（`DIST-005`、`PROD-014`、`ENV-006`）。

設定を変更したい場合は、`hakutaku.yaml.sample` を `hakutaku.yaml` へコピー・リネームし、必要な項目を編集してください。`hakutaku.yaml` が無い場合は組み込み既定値で起動します（`CFG-015`）。

## 既知の制約

- Evergreen WebView2 Runtime が未導入の端末では、Runtime 追加パッケージの事前配置が起動の前提条件です。本体 ZIP のみでは起動できません（`DIST-012`）。Hakutaku が実行時にネットワークから Runtime を取得することはありません。
- Fixed Version Runtime は自動更新されません。Runtime 側の修正を取り込む場合は、`WebView2Runtime` フォルダ一式を新しい版で置き換える形の再配布が必要です（`DIST-011`、`DIST-016`）。利用者が任意の版へ差し替えた場合の動作は保証しません。
- インストーラーは提供しません（`DIST-001`、`PROD-011`）。展開して実行するだけの構成です。導入フォルダごと削除すれば片付けられます。
- 初期リリースには次を含みません: 検索・絞り込み（`LOG-017`）、検索結果のファイルエクスポート（`LOG-019`）、DICOM 匿名化・機密データのマスキング表示・操作監査ログ（`SEC-007`）、`cache` フォルダとキャッシュ関連設定（`CFG-011`）、SQLite・DICOM ビューア（`DB-*`、`DCM-*`）、ドラッグ＆ドロップによる参照対象の追加、資源状況を監視して自動抑制する機構（`ENV-012`）。
- 起動時間、初回表示時間、スクロール応答、`PrivateUsage` の実測値は現時点では参考値であり、合否判定には使用していません（`VER-005`）。既定値・合否基準の確定は段階1（P13）で行います。
- 対応 OS の下限（Windows 10 1809 / LTSC 2019、build 17763）と ACL 要否の最終確定は段階1（P13）で行います（`ENV-001`、`DIST-010`）。
- 文字コードを明示指定しない場合（既定の `auto`）、BOM のない ANSI バイト列が、たまたま妥当な UTF-8 バイト列としても解釈できることがあります。この場合 `auto` は UTF-8 と誤判定し、文字化けした表示になります。判定順序（`ENC-005`）に内在する、実装では解消できない既知の限界です。既知の生成元のログには、`auto` に依存せず、ログ解析プロファイルで `encoding`（例: `windows-932`）または `ansi_codepage`（例: `932`。`ENC-007`）を明示指定してください。
- 複数ファイルの時系列統合表示は、端末やプロセスの時計がずれている場合も時刻補正を行わず、ログに記録された日時をそのまま使用します（`LOG-016`）。時計がずれた環境で記録された複数ファイルを統合すると、表示順が実際の発生順と異なって見えることがありますが、これは不具合ではなく仕様です（`LOG-007`）。同じ比較キー（ミリ秒精度に正規化した日時）の行が複数の読み込み元にまたがる場合、順序の手がかりは行ごとの読み込み元列（読み込み元の識別）だけであり、時刻そのものからは判別できません。
- 画面表示および診断ログ（`logs\hakutaku.log`）は、ログ本文やフルパスなどの実値をマスキングせずそのまま表示・記録します（`ERR-002`、`DIAG-003`〜`DIAG-005`）。画面共有やスクリーンショットの撮影を行うと、これらの実値が第三者にそのまま見える可能性があるため注意してください。`logs` フォルダの閲覧制限、持ち出し、保管、削除は利用者・導入組織の責任範囲です（`SEC-005`。詳細は[README の「セキュリティ」節](../../README.md#セキュリティ)を参照）。
- 資源抑制（`PERF-014`、設定の `performance` 区分、`CFG-024`）の既定値は、運用先の専用端末での実行を前提に控えめに定めています。`ENV-010` により実行場所で機能差を設けないため、開発用 PC など専用端末以外の環境で実行した場合も同じ既定値が適用され、性能が抑えられて見えることがあります。既定値そのものの確定は段階1（P13）で行います。体感速度を優先したい場合は、`hakutaku.yaml` の `performance.parse_concurrency`（解析の同時実行数）・`performance.io_interval_ms`（I/O 発行間隔）・`performance.process_priority`（プロセス優先度）を調整してください。

段階0の検証範囲と検証記録は[段階0検証記録](../verification/stage0-results.md)を参照してください。
