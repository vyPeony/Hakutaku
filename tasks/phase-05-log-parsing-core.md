# P05 ログ解析コア（書式・プロファイル・文字コード）

- 状態: 草案（Draft）
- 開始条件: P04 の完了ゲートを満たすこと。特に内部表現と範囲取得契約が確定していること
- 前提フェーズ: P04
- 段階: 段階0（`VER-007` により段階0で確定してよい範囲）
- 期待成果物: 6 書式の日時解析と精度保持、プロファイルの4段階解決、文字コード判定、継続行の結合、曖昧性の検出、試験データ一式
- 予定変更範囲: コア側のパーサークレート、プロファイル解決クレート、文字コード判定クレート、試験用の入力データ

## 目的

P04 で 1 書式・UTF-8 固定で通した解析経路を、仕様どおりの一般形へ広げます。

`VER-007` は、このフェーズの内容を段階0で確定してよい範囲として明示しています。

> 段階0の期間中に確定してよいのは、`ENV-*` および `DIST-*` に依存しない設計事項に限る。ログ解析プロファイル、日時正規化、文字コード判定、時系列マージ、内部表現、設定スキーマは段階0で確定してよい。

LTSC 実機を待つ必要がないため、このフェーズは段階1の結果に依存しません。

## 対象要件

### 対象ログと解析

| ID | 要求の要旨 |
| --- | --- |
| `LOG-002` | 基本的に各行の先頭に日時があるログを対象とする |
| `LOG-003` | 項目の区切りは主に空白だが、空白数などが一定でない形式を扱える |
| `LOG-004` | ログレベルが存在しない形式も扱える |
| `LOG-005` | ファイルごとにログ形式が異なる可能性を考慮する |
| `LOG-009` | 既知の6書式（`LOG-DT-001`〜`006`）を扱える |
| `LOG-011` | 対象ログの日時には年が含まれる |
| `LOG-012` | タイムゾーン表記のない日時は、同じ端末のローカル時刻として比較する |
| `LOG-014` | 日時を持たない継続行は、直前の日時付き行と同じ論理ログ項目の一部として扱う |
| `LOG-016` | 時計がずれている場合も時刻補正を行わず、記録された日時をそのまま使用する |
| `LOG-024` | 解析した日時には元の精度を保持し、表示時に失わない。比較・マージにはミリ秒精度へ正規化した比較キーを使用し、書式に含まれない下位桁は 0 として補完する |
| `LOG-025` | `LOG-DT-003`／`004` の秒未満2桁は 1/100 秒とする。`.45` および `:45` は 450 ミリ秒として扱う |

### 既知の日時書式

| ID | 書式 | 例 | 最小の時刻精度 | 比較キー |
| --- | --- | --- | --- | --- |
| `LOG-DT-001` | `YYYY/MM/DD HH:mm:ss.SSS` | `2026/07/28 15:12:23.456` | ミリ秒 | `15:12:23.456` |
| `LOG-DT-002` | `YYYY-MM-DD HH:mm:ss:SSS` | `2026-07-28 15:12:23:456` | ミリ秒 | `15:12:23.456` |
| `LOG-DT-003` | `YYYY/MM/DD HH:mm:ss.SS` | `2026/07/28 15:12:23.45` | 1/100 秒 | `15:12:23.450` |
| `LOG-DT-004` | `YYYY/MM/DD HH:mm:ss:SS` | `2026/07/28 15:12:23:45` | 1/100 秒 | `15:12:23.450` |
| `LOG-DT-005` | `YYYY/MM/DD HH:mm:ss` | `2026/07/28 15:12:23` | 秒 | `15:12:23.000` |
| `LOG-DT-006` | `YYYY/MM/DD HH:mm` | `2026/07/28 15:12` | 分 | `15:12:00.000` |

**秒未満2桁は 1/100 秒です。`.45` は 45 ミリ秒ではなく 450 ミリ秒へ展開します**（`LOG-025`）。

### プロファイルの対応付け

| ID | 要求の要旨 |
| --- | --- |
| `LOG-013` | 設定ファイルによる指定を優先し、内容からの自動判定は補助的な扱いとする |
| `LOG-021` | 手動選択、絶対パス完全一致、優先度付き glob、内容による自動判定の順に解決する |
| `LOG-022` | 複数の日時書式またはプロファイルが同時に一致して一意に決められない場合、貪欲マッチで推測せず、プロファイル選択を求めるか日時未解析の生表示にする |
| `CFG-008` | プロファイルごとに文字コードまたは自動判定を指定できる |
| `VER-007` | ログ解析プロファイル、日時正規化、文字コード判定、内部表現は段階0で確定してよい |

解決の優先順は次のとおりです（4.1 の暫定方針）。

1. 開く際にユーザーが指定したプロファイル
2. 設定内の絶対パス完全一致
3. `priority` が高い順の glob パターン
4. 内容による自動判定

**同じ優先度の複数 glob が一致する設定は起動時検証でエラーとします。** 完全一致と glob は、正規化したローカル絶対パスに対して Windows と同様に大文字・小文字を区別せず評価します。glob の `*` と `?` は1階層内、`**` は複数階層を対象とし、パス区切りは設定読込時に正規化します。

### 文字コード

| ID | 要求の要旨 |
| --- | --- |
| `ENC-001` | Windows の OS 言語設定に応じた ANSI エンコーディングのログを扱える。ANSI は Shift_JIS 固定ではなく、ログ生成環境で使用された Windows コードページを指す |
| `ENC-002` | OS 言語設定に依存しない UTF-8 のログを扱える |
| `ENC-003` | UTF-8 は BOM ありと BOM なしが混在する可能性を考慮する |
| `ENC-004` | 同じ配置場所・ファイル種別でも、生成環境の OS 言語設定によって ANSI が変わり得る。生成環境と実行環境のコードページが同じとは限らない |
| `ENC-005` | 設定で文字コードを明示指定できる。`auto` の場合は、UTF-8 BOM → BOM なし UTF-8 の妥当性確認 → プロファイルの `ansi_codepage` → 未指定時のみ実行環境の Windows ANSI コードページ の順に判定する |
| `ENC-006` | UTF-16 LE/BE は初期リリースの対応対象に含めない |
| `ENC-007` | プロファイルに `ansi_codepage: 932` のような任意の Windows コードページ識別子を指定できる |

## 作業項目

1. **日時解析と精度保持。** 6 書式を解析し、**元の精度と原文を保持**したまま、ミリ秒精度の比較キーを別フィールドとして持ちます。欠落した下位桁は 0 で補完します。秒未満2桁は 1/100 秒として展開します。
   - 日時パターンは行頭に固定し、日時直後の区切り条件までプロファイルで定義します（4.1）
2. **曖昧性の検出。** `HH:mm:ss:SS` と `HH:mm:ss` の両方が成立するなど自動判定が曖昧な場合、**長い方を貪欲に選ばず**、自動判定失敗として扱います。プロファイル選択を求めるか、日時未解析の生表示にします。
3. **プロファイルの4段階解決。** `LOG-021` の優先順で解決します。パスの正規化、大文字・小文字を区別しない比較、glob の階層規則を実装します。同優先度の複数 glob 一致は起動時検証（P03）でエラーにするため、検証規則を P03 側へ渡します。
4. **文字コード判定。** `ENC-005` の4段階を実装します。
   - 明示指定がある場合はその指定を優先します
   - **BOM と明示指定が矛盾する場合は警告し、暗黙に別エンコーディングへ切り替えません**（4.3）
   - UTF-16 の BOM を検出した場合は、未対応形式として通知します（`ENC-006`）
   - デコードできないバイト列を検出した場合は、対象ファイル、位置、選択された文字コードを表示し、**元バイトを破棄しません**
   - 選択された判定経路を診断情報で確認できるようにします
5. **継続行の結合。** 日時を持たない行を直前の日時付き行へ継続行として追加し、改行を保った一つの論理ログ項目にします。**ファイル先頭など直前の日時付き行が存在しない場合は破棄せず**、日時未確定の生データとして扱います。
6. **内部表現の確定。** 各ログ行に、少なくとも日時、読み込み元、ファイル内位置または行番号、原文、任意のログレベルを保持します。表示では原文を失わず、解析済みの項目は列や色分けに利用できる形にします。
7. **ログレベルの任意性。** ログレベルが存在しない形式でも解析が成立することを保証します（`LOG-004`）。
8. **試験データの整備。** 6 書式、BOM あり／なし UTF-8、コードページ 932、コードページ 1252、継続行、曖昧な日時、デコード不能バイト列、日時なしで始まるファイルを含む試験用入力を用意します。

## 影響

- **セキュリティ:** デコード失敗時に元バイトを保持するため、ログ本文がメモリ上に残ります。P02 の会計へ計上します
- **データ:** 参照ファイルを読み取り専用で開き、変更しません（`ERR-003`）。原文を保持するため、表示のための変換で情報を失いません
- **性能:** 文字コード判定と日時解析は全行に乗ります。`TECH-001` により、行あたりの処理コストを測定対象に含めます
- **互換性:** 内部表現と比較キーの定義は P08・P09 が依存します。`VER-007` により段階0で確定させます

## リスクと未決事項

### 確定要件に起因するもの

- **BOM なしの ANSI バイト列が偶然 UTF-8 としても妥当になる場合があります**（4.3）。この場合 `auto` は UTF-8 と判定し、誤った表示になります。仕様は「既知の生成元については `auto` に依存せず、プロファイルで `encoding` または `ansi_codepage` を明示することを推奨する」としており、実装で解消できません。**利用者向けの説明に反映する必要があります**
- `LOG-022` の曖昧性検出は「プロファイル選択を求めるか日時未解析の生表示にする」の二択です。どちらを既定にするかは実装判断であり、UI 設計（P07）と連動します
    - **解消済み:** 自動判定が構造的に曖昧になる `LOG-DT-004`（`YYYY/MM/DD HH:mm:ss:SS`）については、プロファイルの `datetime_format` で書式を明示するか、生表示へ退避した対象の再解析 UI（P07 の手動選択。`src/shell.js` の `buildReparseControl`）で書式を選べば解析できます。設定を書かずに開いたアドホックなファイルも後者で解析できます。曖昧性検出そのもの（貪欲マッチで推測しない規則）は変更していません。**どちらも指定しないファイルは従来どおり生表示へ退避します**（既定の挙動は変えていません）

### 暫定設計に起因するもの

- 日時パターンを行頭に固定し、日時直後の区切り条件までプロファイルで定義する方式は 4.1 の暫定方針です。実データで不足が判明した場合、プロファイルのスキーマ拡張が必要になります
    - **一部着手済み:** プロファイルへ `datetime_format`（`auto` と `LOG-DT-001`〜`006`）を追加しました。追加できるのは既知6書式からの選択だけで、書式そのものを設定で定義する方式ではありません。スキーマの形の確定は `VER-007` により段階0の範囲です
- glob の階層規則と `priority` の扱いは 4.1 の暫定方針です。要件 ID を持ちません

### 人間判断待ち

- 試験データに実機のログを使う場合、個人情報等の機密データが含まれ得ます。**リポジトリへ実データをコミットしません**（[`docs/README.md`](../docs/README.md) の更新ルール）。合成データで代替するか、リポジトリ外に置く判断が必要です

## 完了ゲート

- 6 書式、文字コード判定、プロファイル解決、継続行、曖昧性検出がすべて機能している
- 内部表現と比較キーが確定し、P08・P09 が依存できる状態（`VER-007`）
- 試験データ一式が揃い、異常系が回帰テストとして残っている
