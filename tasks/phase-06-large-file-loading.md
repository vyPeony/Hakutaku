# P06 大容量読み込み、索引、キャンセル、変更検知

- 状態: 草案（Draft）
- 開始条件: P04 の完了ゲート（範囲取得契約）、**P04-6（進捗・エラー・キャンセルの共通契約）**、P05 の完了ゲート（解析コア）を満たすこと
- 前提フェーズ: P04、P04-6、P05
- 段階: 段階0
- 期待成果物: チャンク読み込み、行索引、複数ファイルの同時読み込み、サイズ・数・合計の上限判定、キャンセル、ファイル変更検知、書き込み中ログの扱い、明示的な再読み込み
- 予定変更範囲: コア側の読み込みクレート、索引クレート、ファイル監視・整合性確認、進捗とキャンセルの通知経路

## 目的

単一 1 GB・最大 10 ファイル・合計 2 GB という規模のログを、全件一括読み込みせずに扱える基盤を作ります。あわせて、`ENV-010` により**標準ケースとなる「他の業務ソフトウェアが書き込み中のログを開く」状況**を正しく扱います。

このフェーズは初期リリースの中核です。入力資料 5.1 の性能要件と、4.1 の異常系要件（`LOG-023`、`LOG-026`〜`028`）が集中します。

## P09 との担当境界

複数ソースを扱う責務を、次のように一意に分けます。

| 所有 | 内容 |
| --- | --- |
| **P06** | 複数ソースの登録、各ソース内の安定した順序、`source_id` と読み込み元の来歴、世代、ソースごとの独立した走査 |
| **P09** | ソースをまたぐ**グローバルな全順序**と、同一比較キーの同順位解決（tie-break） |

層をまたぐ契約は P04 の複数ソース相当の試験データで先に検証済みです。したがって、このフェーズはマージのアルゴリズムを持ちません。ソースを並べる材料（安定順序、識別子、来歴、世代）を揃えるところまでが範囲です。

## 上限の優先関係（誤解しやすい点）

`PERF-006` が**最上位の拘束条件**です。

| 要件 | 内容 | 関係 |
| --- | --- | --- |
| `PERF-004` | 単一ファイル最大約 1 GB | ただし追加後も合計 2 GB を満たす場合に限り開ける |
| `PERF-005` | 同時に最大約10ファイル | ただし合計が 2 GB 以内である場合に限る |
| `PERF-006` | **合計サイズ 2 GB** | ファイル単位サイズおよびファイル数より**上位**。超えるファイルの追加を拒否する |
| `PERF-007` | 行数だけの上限は設けない | 拘束条件は `PERF-004`〜`006` のサイズ・数・合計 |

つまり「1 GB のファイルを 2 つ」は合計 2 GB で許容範囲ですが、そこに 1 KB を追加することはできません。逆に「10 ファイルだが合計 3 GB」は拒否されます。

## 対象要件

### 規模と性能

| ID | 要求の要旨 |
| --- | --- |
| `PERF-001` | 多数のファイルを扱える |
| `PERF-002` | 単一の巨大ファイルを扱える |
| `PERF-004` | 単一ファイルは最大約 1 GB を想定する |
| `PERF-005` | 同時に最大約10ファイルを開く可能性を想定する |
| `PERF-006` | 合計サイズ 2 GB を上位の拘束条件とし、超えるファイルの追加を拒否する |
| `PERF-007` | 10万行超を現実的な性能試験条件に含める。行数だけの上限は設けない |
| `LOG-006` | 複数のログファイルを同時に開ける |
| `PERF-008`／`PERF-010` | 読み込みバッファ、索引、デコード結果の確保を予約経路へ通す |

### 異常系と書き込み中データ

| ID | 要求の要旨 |
| --- | --- |
| `LOG-010` | 開いているログへの追記をリアルタイム追従する機能は初期要件に含めない。ローテーション、ファイル名変更、ファイル切り替えへの自動追従も不要 |
| `LOG-023` | 開いている元ファイルの削除、切り詰め、置換を検知した場合、その対象の追加読み込みを停止し、索引を無効化してエラーを表示する。アプリ全体は継続動作する |
| `LOG-026` | 読み込み時点の末尾が行の途中で終わっている場合、その断片を破棄せず「書き込み途中の可能性がある未確定行」として区別して表示する。解析エラーとして扱わない |
| `LOG-027` | 他の業務ソフトウェア稼働中でもログを読み取れることを前提とする。共有を許可しない方法で開かれていて読み取れない場合の経路も実装する。ロックの強制解除やコピーによる迂回を行わず、対象と理由を表示し再試行できるようにする。他の対象の閲覧は継続する |
| `LOG-028` | 追記へのリアルタイム追従は行わない。利用者が明示的に再読み込みを指示した場合に限り、対象を開き直して最新状態を反映する |
| `ERR-003` | 参照元ファイルを変更せず、不要なロックやタイムスタンプ変更を避ける |
| `ERR-001` | 1ファイル、1行の失敗で無関係な参照対象の閲覧を停止しない |

## 作業項目

1. **チャンク読み込み。** 全件一括読み込みを前提とせず、必要範囲を段階的に読みます（5.2）。読み込み途中でも、解析済み範囲から閲覧を開始できるようにします（3.2）。
2. **行索引の構築。** ファイル内の日時や行位置について軽量な索引を作り、ジャンプ、スクロール、統合表示に利用します。
   - 5.2 の暫定方針は「行索引は 1 行あたり 24 バイト以下」を設計制約としています。合計 2 GB・平均 100 バイト/行（約 2000 万行）では索引だけで約 480 MB を占める見積もりです
   - **索引は起動のたびにメモリ上へ構築します。** 索引キャッシュは初期リリースでは提供しません（`CFG-011`）
3. **上限判定。** ファイル追加時に `PERF-006` を最上位として判定します。上限を超える場合、そのファイルを開かず、理由と上限値を表示します。**既に開いているファイルの表示は維持します。**
4. **キャンセルと進捗。** 読み込み、索引作成をキャンセル可能にします。進捗、処理中の対象、失敗した対象を UI へ通知できる経路を用意します（表示は P07）。
5. **ファイル整合性の確認。** ファイルを開いた時点でファイル識別子、サイズ、最終更新時刻を記録し、未読み込み範囲を読む前に整合性を再確認します（4.1）。
   - 削除、縮小、別ファイルへの置換を検知した対象は「変更済み」として停止し、**手動で閉じて開き直すまで再利用しません**
   - 検知した対象だけをエラーにし、アプリ全体と他の対象は継続します
6. **未確定行の扱い。** 読み込み時点の末尾が行の途中で終わっている場合、断片を破棄せず「未確定行」として区別します。**解析エラーとして扱いません。** 表示上の区別は P08 と連携します。
7. **共有違反の経路。** 共有を許可しない方法で開かれていて読み取れない場合、対象と理由を表示し、再試行できるようにします。**ロックの強制解除やコピーによる迂回を行いません。** 他の対象の閲覧は継続します。
8. **明示的な再読み込み。** 利用者の指示で対象を開き直し、最新状態を反映します。リアルタイム追従は実装しません（`LOG-010`）。

### 再読み込みで合計 2 GB を超える場合（推奨案）

仕様に明示的な記述がない箇所です。`PERF-006`（合計 2 GB が最上位の拘束条件）と `LOG-028`（明示的な再読み込みで最新状態を反映）が競合します。次を推奨案として記録します。

**部分読み込みは採りません。** `PERF-006` は開いているファイルの合計サイズを最上位の拘束条件とし、`LOG-028` は最新状態の反映を求めます。「最新の一部だけを読む」は両方の意味を曖昧にし、利用者が何を見ているのか分からなくなります。

| 状況 | 挙動 |
| --- | --- |
| 再読み込み前の事前判定で合計が上限を超える | **再読み込み全体を拒否する。** 現在の合計、再読み込み後の見込み、上限値、閉じるべき対象を表示する |
| 純粋な追記であり、同一ファイルと確認できる | 従来のスナップショットを**旧 EOF に固定して表示を維持**し、「更新未反映」と示す |
| 削除・切り詰め・置換を検知 | `LOG-023` どおり索引を無効化する。**従来の索引を有効扱いで維持しない** |
| 他の対象を閉じたあと | 再試行できる |

#### 「原子的」の適用範囲

外部プロセスが追記し続けるファイルに対して、**サイズ取得と後続の読み込みをファイルシステム上のトランザクションにはできません**。排他ロックを取らない限り、判定した瞬間にサイズは変わり得ます。したがって「原子的」は次の意味に限定します。

| 対象 | 意味 |
| --- | --- |
| **アプリ内の合計サイズの判定と予約** | 合計サイズの比較と確保（compare-and-reserve）を、他の追加操作と競合しない形で行う。**ここが原子的** |
| ファイル側 | 観測した長さを `snapshot_end` として固定し、**そこまでしか読まない**。`snapshot_end` より先に追記されても、その回では読まない |
| 縮小・置換 | `LOG-023` により索引を無効化する。サイズ判定の対象にしない |

`snapshot_end` を固定することで、判定した量と実際に読む量が一致します。判定後に追記された分は「更新未反映」として扱い、次の再読み込みで反映します（`LOG-028`、`LOG-010`）。

3番目の行に注意してください。追記の場合は従来のスナップショットが有効ですが、削除・切り詰め・置換の場合は無効です。**上限超過を理由に「従来の索引をそのまま使う」と決めると、`LOG-023` の変更検知と衝突します。**
9. **抑制の接続点。** 同時実行数の上限と I/O 発行間隔を外から与えられる形にします。既定値と設定は P11 で扱います。
10. **メモリ会計への接続。** 読み込みバッファ、索引、デコード結果の確保を P02 の予約経路へ通します。ソフトしきい値到達時に解放する対象として、索引と本文バッファを登録します。

## 影響

- **セキュリティ:** ログ本文がメモリ上に大量に載ります。P02 の会計へ計上し、ソフトしきい値で解放します。`SEC-005` により診断ログへ本文が出力され得ます
- **データ:** **このフェーズが「読み取り専用」を実装として担保する中心です。** `ERR-003` により不要なロックとタイムスタンプ変更を避けます。共有違反時に迂回しないこと（`LOG-027`）が、参照元を壊さない保証の一部です
- **性能:** チャンクサイズ、索引構造、同時実行数が性能を左右します。段階0の値は参考値ですが（`VER-005`）、回帰の基準として記録します
- **互換性:** 索引の構造は P08・P09 が依存します。24 バイト制約を満たせない場合、予算配分の見直しが必要です

## リスクと未決事項

### 確定要件に起因するもの

- **`LOG-027` は「保証ではない」と明示されています。** `Q-038` の回答は「稼働中にメモ帳でログを開けた実績」に基づく前提であり、「全ログファイル・全機種・全動作局面での保証ではない」とされています。共有違反の経路は実装したまま残す必要があり、段階0で発生しなくても削除できません
- `PERF-006` の合計 2 GB は、開いているファイルの合計です。再読み込み（`LOG-028`）でファイルサイズが増えた場合に上限を超える可能性があり、**再読み込み時の上限判定を設計する必要があります**。仕様に明示的な記述がないため、着手時に判断が必要です

### 暫定設計に起因するもの

- 行索引 1 行 24 バイト以下は 5.2 の設計制約であり、要件 ID を持ちません。達成できない場合、索引構造か予算配分の見直しを検討します
- 「変更済みと判定した対象は手動で開き直すまで再利用しない」は 4.1 の暫定方針です
- チャンクサイズ、先読みの量、索引の粒度はすべて実測で調整する設計候補です

### 人間判断待ち

- **再読み込みでサイズが増えて合計 2 GB を超える場合の扱いが未決です。** 上記「再読み込みで合計 2 GB を超える場合（推奨案）」に方針を記録しました。仕様に記述がない箇所であるため、**ADR で確定させる必要があります**
- 1 GB 級の試験データをどう用意するかが未決です。実データは個人情報等の機密データを含み得るため、リポジトリへコミットしません。合成データ生成の手段が必要です（P12 で扱います）

## 完了ゲート

- 1 GB 単一ファイルと合計 2 GB の複数ファイルが開ける
- 上限超過、削除・切り詰め・置換、共有違反、書き込み中の末尾断片のすべてで、アプリ全体が継続動作する
- キャンセルと進捗の通知経路が機能する
- 索引と本文バッファがメモリ会計に載り、しきい値で解放される
