# P12 配布・検証フェーズ（配布物の作成と段階0検証の完了判定）

- 状態: 草案（Draft）
- 開始条件: P09、P10、P11 の完了ゲートを満たすこと
- 前提フェーズ: P09、P10、P11
- 段階: 段階0（配布物と検証用ツールの実装＋検証ゲート）
- 期待成果物: 本体配布物（単一 EXE または ZIP）、Runtime 追加パッケージ、段階0の検証記録、段階1で確認すべき事項の絞り込み
- 予定変更範囲: ビルド・パッケージング構成、リリースノート、検証記録、性能計測スクリプト、合成試験データの生成手段

## 目的

初期リリースの配布物を作り、段階0の検証を完了させます。

このフェーズは**二つの性質を併せ持ちます**。配布物と検証用ツール（合成データ生成器、追記テストプロセス）は実装であり、それ以外は検証ゲートです。実装単位はこの二つを分けています。

`VER-001` が定めるとおり、**段階0の完了をもって `TECH-003`（Rust＋Tauri）を確定としません。** `DEC-002` の状態は段階1（P13）の完了まで暫定決定を維持します。このフェーズの完了ゲートは「段階1で確認すべき事項が LTSC 固有の要因だけに絞り込めていること」です。

## `VER-005` によるゲートと参考値の切り分け

`VER-005` の原文は次のとおりです。

> 段階0で計測した性能値は参考値とし、`PERF-014` の既定値決定および `PERF-009`・`PERF-015` の合否判定には使用しない。**段階0では計測手段そのもの（ヒープ会計、`PERF-012` のメモリ推移計測）が機能することの確認までを行う。**

第2文が `PERF-012` のメモリ推移計測を名指ししています。したがって、**段階0で `PERF-012` について確認するのは「メモリ推移を計測できること」までです。** メモリ推移の値そのもの（単調増加しているか）を段階0のゲートにはしません。

では `PERF-012` の機能面をどう検証するかというと、**プロセスのメモリ量ではなく内部状態で検証します。** これは仕様への適合というだけでなく、検証手法として優れています。プロセスのメモリ量は WebView2 やアロケータの都合で変動し、機能不備の有無を決定的に示せません。内部状態なら決定的に判定できます。

| 対象 | 段階0での扱い | 検証方法 |
| --- | --- | --- |
| 保持行数と保持バイト数が `CFG-022` の上限以下である | **完了ゲート**（機能） | **内部状態**を観測 |
| 表示範囲から遠い範囲が破棄される | **完了ゲート**（機能） | **内部状態**を観測 |
| スクロールで戻ると正しく再取得される | **完了ゲート**（機能） | **内部状態**と表示を観測 |
| **フロントエンドが保持する全行データ**が上限を越えて増えない（自前キャッシュ、表示ライブラリ内部の行モデル、DOM と購読が保持する行参照を含む） | **完了ゲート**（機能） | 行モデルの生成・解放計数、DOM ノード数、購読解除の検証、必要に応じて heap snapshot |
| 2000 万行試験で `PrivateUsage` の時系列を**測定・記録できる** | **完了ゲート**（計測手段） | 計測記録の存在 |
| その時系列の**傾向値**（単調増加しているか） | **ゲート外の参考値** | 記録のみ。最終判定は P13 |
| `PrivateUsage` 合計 ≦ 予算値 + 1 GB | **ゲート外の参考値** | 記録のみ。`PERF-011` 自身が合否基準としないと明示 |
| 起動時間、初回表示時間、スクロール応答 | **ゲート外の参考値** | 記録のみ（`VER-005`、`PERF-009`） |

### 段階0で `PrivateUsage` が増えていた場合の扱い

| 状況 | 扱い |
| --- | --- |
| 内部の保持上限違反が**ある** | **`PERF-012` の機能不備としてブロックする。** 内部状態が直接の証拠 |
| 内部の保持上限違反が**ない** | 性能結果として記録する。ブロックしない。原因は WebView2 やアロケータ側の可能性があり、段階0では判定しない |

判断の根拠を「プロセスのメモリ量」ではなく「内部状態」に置くのがこの切り分けの要点です。

## 対象要件

### 配布物

| ID | 要求の要旨 |
| --- | --- |
| `PROD-011` | インストーラー形式は避ける。単一 EXE を第一候補とし、難しい場合は ZIP で展開可能なフォルダ一式として配布する |
| `DIST-001` | インストーラーは使用しない |

| `DIST-007` | Fixed Version Runtime は本体へ常時同梱せず、任意追加パッケージとして別 ZIP で提供できる。追加パッケージのサイズは `DIST-003` の目標に含めない |

| `DIST-016` | Fixed Version Runtime の版はビルドごとに固定し、リリースノートに対応する Runtime 版を明記する |
| `PROD-014`／`ENV-006` | オフラインで起動・利用できる |

配布物の構成は 10.3 のとおりです。

```text

├─ Hakutaku.exe
├─ hakutaku.yaml
├─ logs/              診断ログ（DIAG-001）
├─ temp/              一時ファイル（SEC-006）
├─ WebView2/          WebView2 のユーザーデータ。Hakutaku が自動作成（DIST-013）
└─ WebView2Runtime/   Fixed Version Runtime。任意追加パッケージを展開した場合のみ（DIST-006）
```

### 段階0の検証

| ID | 要求の要旨 |
| --- | --- |
| `VER-001` | 検証を段階0と段階1に分ける。**段階0の完了をもって `TECH-003` を確定としない** |
| `VER-002` | 段階0の目的は、現行の開発環境で Rust＋Tauri 構成が動作し、主要機能の骨格が成立することの確認。対象は起動、日本語表示、ファイル選択、ログ読み込み、時系列統合表示、仮想スクロール、ヒープ会計、クリップボードコピー |
| `VER-003` | 段階0でも Evergreen に依存せず、`DIST-017` により開発環境上でも Fixed Version 経路を通した動作確認を行う |
| `VER-005` | 段階0で計測した性能値は参考値とし、`PERF-014` の既定値決定および `PERF-009`・`PERF-015` の合否判定には使用しない。計測手段そのものが機能することの確認までを行う |
| `PERF-007` | 10万行超を現実的な性能試験条件に含める |
| `PERF-009` | 初回表示時間に一律の秒数目標は設けない |
| `PERF-011` | Rust コアと WebView2 子プロセス群の `PrivateUsage` 合計が、予算値 + 1 GB を超えないことを性能試験で確認する |
| `PERF-012`（確定本文） | フロントエンドは可視範囲と前後の一定バッファに限って行データを保持し、取得済みの行を累積しない。保持する行数・バイト数の上限を設け、超過時は遠い範囲を破棄し、必要時に再取得する。上限値は設定できる |
| 5.3 の暫定的な受け入れ条件 | 2000万行規模のログを先頭から末尾まで連続スクロールした後も、WebView2 プロセス群のプライベートコミット量が開始直後の水準から単調に増加し続けていない |

**この二つを区別してください。** `PERF-012` の確定本文は保持上限・破棄・再取得です。2000 万行と `PrivateUsage` の単調増加は 5.3 の「暫定的な受け入れ条件」に記載された**検証方法**であり、要件本文ではありません。
| `ENV-004` | SSD と HDD の両方を性能確認環境に含める。特に HDD での読み込み中も UI 応答性を維持する |
| `LOG-026`／`LOG-028` | 段階0では他の業務ソフトウェアが存在しないため、追記を行うテスト用プロセスを用意して代替検証する（10.6） |

## 作業項目

1. **本体配布物の作成。** 単一 EXE を試み、サイズと実現性を評価します。おおむね 100 MB 以下（`DIST-003`）を目標とします。難しい場合は ZIP 配布へ切り替えます（`DIST-004`）。**インストーラーは作りません。**
2. **Runtime 追加パッケージの作成。** Fixed Version Runtime を別 ZIP として用意します。版を固定し、リリースノートへ対応版を明記します（`DIST-016`）。
3. **両運用形態の確認。** Evergreen 導入済み機種向け（本体のみ）と未導入機種向け（本体 + Runtime パッケージ）の両方を、正式な運用形態として確認します（`DIST-015`）。
4. **オフライン起動の確認。** ネットワークを遮断した状態で、配布物一式から起動できることを確認します。
5. **合成試験データの生成手段。** 実データは個人情報等の機密データを含み得るためリポジトリへ置きません。次を生成できる手段を用意します。
   - 1 GB 単一ファイル
   - 合計 2 GB の複数ファイル（10 ファイル）
   - **2000 万行規模**（5.3 の暫定的な受け入れ条件で求められる規模）
   - 6 書式、BOM あり／なし、複数コードページの混在
6. **追記テストプロセスの作成。** 他の業務ソフトウェアの代替として、ログへ追記し続けるテスト用プロセスを用意します（10.6）。`LOG-026`（末尾断片）と `LOG-028`（再読み込み）の代替検証に使います。
7. **性能計測の実施と記録。** 起動時間、初回表示時間、スクロール応答、最大メモリ使用量を計測します（5.2）。
   - **値は参考値です**（`VER-005`）。合否判定に使いません
   - 計測手段そのものが機能することを確認します
   - 回帰試験の基準値として記録します
8. **SSD と HDD での確認。** 両方の環境で、大容量ログの読み込み中も UI が応答し続けることを確認します（`ENV-004`）。
9. **2000 万行の連続スクロール検証。** 二つを分けて行います。
   - **機能の確認（ゲート）:** 保持行数・保持バイト数が `CFG-022` の上限以下であること、遠い範囲が破棄されること、戻ると再取得されること、**フロントエンドが保持する全行データ**が上限を越えて増えないことを、**内部状態**で確認します。全行データには自前キャッシュに加え、表示ライブラリ内部の行モデル・キャッシュ、DOM が保持する行参照、購読・イベントハンドラーが保持する行参照を含めます
   - **計測手段の確認（ゲート）:** WebView2 プロセス群のプライベートコミット量の時系列を測定・記録できることを確認します。**傾向値の判定は行いません**（`VER-005`）。記録を P13 へ渡します
10. **`VER-002` の対象項目の総点検。** 起動、日本語表示、ファイル選択、ログ読み込み、時系列統合表示、仮想スクロール、ヒープ会計、クリップボードコピーを一通り確認します。
11. **`SEC-001` のプロセス単位の送信監視。** CSP（`SEC-011`）は WebView2 側しか制限しないため、Rust コアと依存クレートによる外部通信を別途確認します。
    - **識別可能な合成本文**（一意の文字列を埋め込んだ試験ログ）を読み込み、その文字列がプロセスの送信データに現れないことを確認します

    **監視位置と陽性対照を先に定義してください。** これがないと試験が無意味になります。

    | 論点 | 内容 |
    | --- | --- |
    | 監視位置 | **ネットワーク上の TLS 暗号文だけを見ると、実際に送信されていても平文のマーカーは現れません。**「見つからない」ことが証拠になりません。送信 API の直前など**暗号化前の層**を観測するか、どの層で送信データを見るかを定義します |
    | 陽性対照 | **同じ監視方法で、意図的にマーカーを送った場合に検知できることを確認します。** 検知できない監視方法で「見つからなかった」と結論しないためです |
    | 陽性対照の実施方法 | **Hakutaku に送信機能を追加しません。** 別の合成テストプロセス、または検証専用のハーネスを使います。試験のために製品へ外部通信経路を作ると `SEC-001` の前提自体を壊します |
    - 依存クレートの一覧と、外部通信を行い得る API の使用箇所を確認し、**Hakutaku が外部通信経路を実装・呼び出していない**ことを確認します
    - 観測した接続試行は**発生元を帰属して記録**します。アプリまたは依存クレート由来であれば是正します

    **「接続試行がゼロである」ことはゲートにしません。** `SEC-001` は参照内容を送信しないこと、`PROD-014`／`ENV-006` はインターネット接続を必須としないことを求めており、**接続試行そのものの禁止までは要求していません**。WebView2 や OS ランタイム由来の背景通信を含めると、Hakutaku の実装と無関係に失敗します。オフラインで起動・利用できることは、ネットワークを遮断した状態での起動確認（作業項目4）で別途確認します。

    ゼロ試行を要求する場合は、**新しい採用済み要件として明示する必要があります**。現在の要件からは導けません。
12. **初期リリースに含めない機能の不在確認。** 除外要件は「実装しない」ことが要求です。実際に存在しないことを確認します。
    - `LOG-017`: 検索・絞り込みの UI と機能がない
    - `LOG-019`: 検索結果のファイルエクスポートがない
    - `SEC-007`: DICOM 匿名化、機密データのマスキング表示、操作監査ログがない
    - `CFG-011`: `cache` フォルダとキャッシュ関連の設定項目がない
    - `DB-*`、`DCM-*`: SQLite・DICOM ビューアがない
    - ドラッグ＆ドロップによる参照対象の追加がない
    - `ENV-012`: 資源状況を監視して自動抑制する機構がない
13. **段階1の確認事項の絞り込み。** 10.6 の狙いどおり、段階1で新たに確認が必要な事項が「LTSC というエディション固有の挙動」「build 17763 固有の挙動」「他の業務ソフトウェアとの同時稼働」だけに絞られていることを確認します。

## 影響

- **セキュリティ:** 配布物に開発者ツールが有効なビルドを含めないことを確認します（`SEC-011`）。試験データに実データを使わないことで、リポジトリへの機密データ混入を防ぎます
- **データ:** 合成データを使うため、検証で実データを扱いません
- **性能:** このフェーズが回帰試験の基準値を作ります。以降の変更で著しい性能劣化がないことを、この基準と比較して確認します（5.4）
- **互換性:** 配布物の構成（フォルダ配置）は導入手順に組み込まれます。`SEC-009` により実行ファイル直下へ集約されており、導入フォルダごと処分できる状態を保ちます

## リスクと未決事項

### 確定要件に起因するもの

- **単一 EXE 100 MB 以下（`DIST-003`）が達成できない可能性があります。** `DIST-002` は「実現が容易で、実行ファイルが過度に巨大化しない場合」という条件付きであり、達成できなければ `DIST-004` の ZIP 配布へ切り替えます。要件違反ではありません
- **2000 万行規模の試験データは 2 GB 相当になります。** `PERF-006` の上限と一致するため、生成と保管の場所を確保する必要があります。生成に時間がかかる点も見込んでください
- `PERF-011` の「予算値 + 1 GB」は暫定値であり、「技術試作の実測により再確定する」と定められています。このフェーズの計測結果が再確定の根拠になります

### 暫定設計に起因するもの

- 10.6 の「段階1で新たに確認が必要なのは LTSC・build 17763 固有の挙動と他の業務ソフトウェアとの同時稼働に限定できる」という見込みは暫定方針です。実際に絞り込めたかはこのフェーズで判断します
- 追記テストプロセスによる代替検証は 10.6 の暫定方針です。実際の他の業務ソフトウェアの共有モードと異なる可能性があります

### 人間判断待ち

- **HDD 環境の確保が必要です。** `ENV-004` は SSD と HDD の両方を性能確認環境に含めることを求めています。開発環境に HDD がない場合、確保方法を判断してください
- 2000 万行規模の試験データの生成と保管場所の確保が必要です
- 単一 EXE と ZIP のどちらを採用するかは、サイズと実現性の実測を見た判断です

## 完了ゲート

- 両運用形態（Evergreen 導入済み／未導入）の配布物が揃い、オフラインで起動する
- `VER-002` の8項目すべてが確認できている
- **2000 万行規模でも、内部状態で保持上限・破棄・再取得と、フロントエンドが保持する全行データの非増加が確認できる**（機能ゲート）
- 2000 万行試験で `PrivateUsage` の時系列を測定・記録できている（計測手段のゲート）
- **合成マーカーが送信データに現れず、Hakutaku が外部通信経路を実装・呼び出していないことが確認できている**（`SEC-001`）
- 初期リリースに含めない機能が実際に存在しないことを確認できている（下記「不在確認」）
- 計測手段が機能し、性能値が参考値として記録され、回帰試験の基準になっている
- **段階1で確認すべき事項が LTSC 固有の要因だけに絞られている**
- `TECH-003`／`DEC-002` が暫定決定のまま維持されている

**性能値と、メモリ推移の傾向値はゲートに含めません**（`VER-005`）。2000 万行のメモリ傾向値と `PrivateUsage` の予算値 + 1 GB 比較は、**記録できること**がゲートであり、値そのものの判定は P13 で行います。段階0で機能不備を判定する根拠は、プロセスのメモリ量ではなく**内部状態**です。
