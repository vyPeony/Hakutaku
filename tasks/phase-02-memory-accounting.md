# P02 メモリ会計とヒープ予算の基盤

- 状態: 草案（Draft）
- 開始条件: P00 の完了ゲートを満たすこと。**確保を予約トークンへ帰属させる方式が ADR で決まっていること**（下記「帰属の方式」）
- 前提フェーズ: P00
- 段階: 段階0（既定値の妥当性確認は P13）
- 期待成果物: グローバルアロケータの計装、現在値とピーク値の取得、予約トークンによる予約・拒否・解放、参考指標（`PrivateUsage`）の計測
- 予定変更範囲: コア側のメモリ会計クレート、グローバルアロケータの設定、診断ログへの出力

## 目的

Rust コアプロセスのヒープ確保量を集計し、大きな確保の前に予算を検査して拒否できる仕組みを作ります。

このフェーズを機能実装より前に置く理由は、`PERF-010` が明示的に後付けを禁じているためです。

> メモリ会計をコア設計の一部として初期実装から組み込み、後付けにしない。予算判定は `PERF-008` のヒープ確保量に対して行い、大規模読み込み前の予約・拒否を必須とする。

5.2 はその理由も述べています。`PERF-008` のヒープ確保量を正確に集計するには「アロケータ層の計装、または確保経路をこのサービスへ一本化する必要があり、後付けが困難」です。ログ本文バッファや索引を作る P06 より後に着手すると、確保経路が散らばった状態から作り直すことになります。

### `VER-005` の適用範囲についての注意

`VER-005` は「段階0で計測した性能値は参考値とし、合否判定には使用しない」と定めています。**緩和されるのは性能値による合否判定だけです。** `PERF-010` の予約・拒否は機能要件であり、段階0でも完全に満たす必要があります。「段階0だから予約・拒否は後回しでよい」とは読みません。

`VER-005` が段階0の範囲としているのは「計測手段そのもの（ヒープ会計、`PERF-012` のメモリ推移計測）が機能することの確認」です。つまり**機能は作り、数値の合否は問わない**という切り分けです。

## 予算の定義（誤解しやすい点）

`PERF-008` の予算対象は **Rust コアプロセスのヒープ確保量の合計**です。次を区別してください。

| 指標 | 対象 | 用途 |
| --- | --- | --- |
| ヒープ確保量（`PERF-008`） | Hakutaku 自身と利用クレートによる未解放確保量。ログ本文バッファ、索引、デコード結果、DB 取得ページ、DICOM 解析結果、コピー用バッファを含む | **判定の基準。** 初期値 2 GB（`CFG-007` で変更可） |
| プライベートコミット量（`PERF-011`） | Rust コアプロセスと Hakutaku 専用の Tauri／WebView2 子プロセス群の `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage` の合計 | **参考指標。** 予算値 + 1 GB を超えないことを性能試験で確認する。合否判定には使わない |
| ワーキングセット | 現在物理 RAM 上にあるページ量 | **判定に使用しない。** 他プロセスの圧迫で変動するため |

WebView2 プロセス群の使用量は `PERF-008` の予算に含まれません（`PERF-011`、`PERF-012`）。フロントエンド側の累積はこの予算では検知できないため（`PERF-013`）、`PERF-012` の保持上限が一次的な歯止めになります。その実装は P04 と P08 です。

## 実確保と予約の会計関係（この設計の中心）

グローバルアロケータが実確保を全件計上する一方で、予約トークンも予算を占有します。**両者の関係を定義しないと、どちらかの方向で必ず破綻します。**

| 定義しない場合 | 起きること |
| --- | --- |
| 実確保時に予約を消費・振り替えない | **二重計上。** 予約 500 MB のあと実際に 500 MB 確保すると、会計上は 1 GB 使ったことになる |
| 予約が予算を占有しない | **並行処理が同時に予算を取り切る。** 3 つの処理がそれぞれ 800 MB を予約可と判定し、合計 2.4 GB を確保しようとする |

したがって、次の契約を実装します。

1. **二つの値を分けて保持する。**
   - `allocated_bytes`: グローバルアロケータが計上した未解放の実確保量
   - `outstanding_reserved_bytes`: 予約済みでまだ実確保に振り替えられていない量
2. **予約の可否を原子的に判定する。** `allocated_bytes + outstanding_reserved_bytes + request <= budget` を、他の予約と競合しない形で判定します。判定と加算が分離していると、並行予約が同時に通ります。
3. **実確保時に予約から振り替える。** 予約トークンの下で行われた確保は `outstanding_reserved_bytes` を減らし `allocated_bytes` へ移します。二重計上を避けるための中心的な操作です。
   - **「予約トークンの下で行われた」をどう判定するかが、この設計の最大の未決事項です。下記「帰属の方式」を参照してください。**
4. **未消費の予約はトークンの破棄で解放する。** 予約したが確保しなかった分を戻します。
5. **計装処理自体が確保やロックの再入を起こさないこと。** アロケータの中で確保やロック取得を行うと、無限再帰やデッドロックになります。

### この契約のテスト

| テスト | 確認すること |
| --- | --- |
| 並行予約 | 複数スレッドが同時に予約しても、合計が予算を超えない |
| 予約後の第三者クレートの確保 | 予約トークンの外で利用クレートが確保した分も `allocated_bytes` に計上される |
| `realloc` | 再確保で差分だけが正しく増減する |
| 確保失敗 | 確保が失敗した場合に予約が戻る |
| 未消費トークンの破棄 | 予約したまま確保しなかった分が解放される |
| 予約量より少ない確保 | 差分が解放され、予約したまま残らない |
| 予約量を超える確保 | 検知できる（またはそもそも起きない設計である）ことを確認する |
| 計装の再入 | アロケータ内で確保・ロック取得が発生しない |

**予約の外で利用クレートが行う確保は事前に予測できません。** `PERF-008` の対象は Rust プロセス内の全確保であるため、`allocated_bytes` には計上されますが予約は通っていません。この差により、予約が通ったあとに予算を超える可能性があります。ソフトしきい値（下記）がその検知手段です。

### 帰属の方式（着手前に決めるべき最大の未決事項）

**グローバルアロケータは、どの確保がどの予約トークンの下で起きたかを知りません。** したがって「実確保時に予約から振り替える」だけでは実装契約になっていません。次の状況すべてで帰属が定義されている必要があります。

| 状況 | 問題 |
| --- | --- |
| 並行処理 | 複数スレッドが同時に別々の予約の下で確保する |
| 非同期タスクのスレッド移動 | `await` の前後でスレッドが変わり、スレッドローカルな情報が追随しない |
| 入れ子の予約 | 予約の中でさらに予約する場合、どちらへ帰属するか |
| 第三者クレートの内部確保 | 予約の下で呼んだクレートが内部で行う確保を含めるか |
| `realloc` | 増加分だけを帰属させるのか、全体を付け替えるのか |
| 確保の失敗 | 失敗時に予約を戻す経路 |
| `dealloc` | 解放時にどちらの値を減らすか |
| 帰属できない確保 | 予約の外で起きた確保との区別 |

**方式の候補**

| 方式 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| 明示的な確保 API | 予約トークンを引数に取る確保関数を用意し、大きなバッファはそれを通す | 帰属が確実。スレッド移動の影響を受けない | 第三者クレート内部の確保を捕捉できない。呼び忘れが起き得る |
| スコープ情報の伝播 | 予約トークンをタスクローカルな情報として持ち、アロケータが参照する | 呼び出し側の変更が少ない | 非同期のスレッド移動と入れ子の扱いが複雑。アロケータ内で参照するため再入の危険 |
| 保守的な二重計上 | 帰属できない確保は `reserved` と `allocated` の両方に計上したままにする | 実装が単純。予算を超えない方向に安全 | 実際より多く見積もり、開けるはずのファイルを拒否し得る |

**この判断は ADR が必要です。** 方式が決まらないと、上記の原子的判定と振り替えのテストは実装できません。着手時に決めて記録してください。

#### 受け入れ条件は ADR の結果に従います

下記の受け入れ条件のうち、**「実確保時に振り替えられ、二重計上されない」と「予約量より少ない確保で差分が解放される」は、明示的な確保 API またはスコープ情報の伝播を選んだ場合の条件です。**

**保守的な二重計上を選んだ場合、この2条件は成立しません。** その方式では帰属できない確保が両方に計上されたまま残るためです。この方式を採る場合は、ADR の結果に合わせて会計契約と受け入れ条件を更新してください。

保守的な二重計上を採る場合、追加で次を評価します。

- **過大見積もりによる誤拒否が、`PERF-004`〜`006` の想定入力を不必要に開けなくしないか。** 単一 1 GB、10 ファイル合計 2 GB という上限は予算 2 GB に対して余裕がありません。二重計上分が積み上がると、仕様どおりの入力を拒否する可能性があります
- 代表ケース（1 GB 単一、合計 2 GB の 10 ファイル、2000 万行相当）で誤拒否が起きないことを実測で確認してください

なお `TECH-006` は「グローバルアロケータを計装して行い、対象を Rust プロセス内の全確保とする」と定めています。**全確保の計上（`allocated_bytes`）と、予約の帰属は別の話です。** 前者はアロケータ計装で必ず達成し、後者は上記の方式で扱います。帰属できない確保があっても `allocated_bytes` には計上されるため、`PERF-008` の定義は満たせます。

## 作業項目

1. **グローバルアロケータの計装。** `TECH-006` に従い、Rust コアプロセスのグローバルアロケータを計装して確保・解放を集計します。`PERF-008` の対象は Rust プロセス内の**全確保**であり、Hakutaku 自身の確保だけでなく利用クレートによる確保も含みます。
2. **現在値とピーク値の取得。** 現在の未解放確保量に加え、**ピーク値**を保持します。ピーク値がないと、処理後に解放されて正常に見える一時的な超過を検出できません。
3. **予約トークンの実装。** 5.2 の「メモリ会計サービスをコアに設け、大きなバッファ、索引、デコード結果、DB ページ、コピー用バッファの確保前に予約量を検査する」を実装します。
   - 予約の要求（予測確保量を渡し、可否を受け取る）
   - **予約は加算がオーバーフローしない形で実装します。** 巨大な予測値（不正なファイル長やタグ長に由来し得る）が加算で桁あふれすると、予算超過を通り抜けてしまいます
   - 予約トークンの破棄で自動的に解放される構造にし、解放漏れを型で防ぎます
   - 予約後に予算の 100% を超える処理は開始しません
4. **参考指標の計測。** Rust コアと Hakutaku 専用の Tauri／WebView2 子プロセス群を特定し、各プロセスの `PrivateUsage` を合算して定期計測します。合否判定には使いません。予算値 + 1 GB を超えた場合は、進行中の追加読み込みをキャンセルして警告します（5.2）。
   - **注意:** 「Hakutaku 専用の子プロセス群」の特定方法を決める必要があります。WebView2 は複数プロセス構成であり、**他アプリの WebView2 プロセスを誤って合算しないように**します
5. **ソフトしきい値の枠組み。** 設定上限に対する割合でしきい値を検知し、登録された解放処理と先読み停止を呼ぶ枠組みを作ります。**割合の具体値（5.2 は 90% を挙げています）は暫定設計であり、要件 ID を持ちません。** 設定可能にするか固定値にするかも含めて設計判断です。実際に解放する対象の登録は P06（索引・バッファ）と P08（表示範囲）で行います。
6. **設定値の受け取り。** `CFG-007` の予算値を P03 の設定読み込みから受け取れるようにします。P03 より前に着手する場合は、既定値 2 GB を組み込み値として持ち、設定からの上書き口だけを用意します。
7. **診断ログへの出力。** 予約の拒否、しきい値到達、参考指標の超過、ピーク値を診断ログへ記録します（`DIAG-005`）。
8. **計装のオーバーヘッド測定。** `TECH-001` と両立するかを確認するため、計装あり・なしの処理時間を測定して記録します。

| 他アプリの WebView2 プロセスが合算されない | 別アプリの WebView2 を起動した状態での計測 | 段階0 | 確定要件（`PERF-011`） |
| 参考指標が予算値 + 1 GB を超えた場合、進行中の追加読み込みがキャンセルされ警告が出る | 予算値を小さくした状態での確認 | 段階0 | 暫定設計（5.2。`PERF-011` は計測を求めるが対処は暫定方針） |
| しきい値到達を検知し、登録された解放処理と先読み停止が呼ばれる | 単体テスト | 段階0 | 暫定設計（5.2。割合の具体値は要件 ID を持たない） |
| 予約の拒否、しきい値到達、ピーク値が診断ログに記録される | 診断ログの内容 | 段階0 | 確定要件（`DIAG-005`） |
| 計装のオーバーヘッドを測定し記録している | 測定結果 | 段階0（値の合否は問わない） | 確定要件（`TECH-001`）、`VER-005` |

## 対象外

| 扱わないもの | 扱うフェーズ |
| --- | --- |
| 実際に解放する対象の登録（索引、ログ本文バッファ、表示範囲） | P06、P08 |
| フロントエンド側の保持上限（`PERF-012`、`CFG-022`） | P04（契約）、P08（運用） |
| 各読み込み経路を予約契約へ接続する作業 | P06、P08、P10 |
| 性能値の合否判定（`PERF-009`、`PERF-015`） | P13 |
| 資源状況を監視して自動的に抑制する機構。`ENV-012` により必須要件ではありません | 実装しない |

## 影響

- **セキュリティ:** 予約量の計算に外部入力（ファイル長、タグ長）が入る経路では、オーバーフローや過大確保が防御の一部になります。`ERR-004` は設定駆動のバイナリ解析に上限を求めており、その土台がここです
- **データ:** 参照データへの影響はありません
- **性能:** アロケータ計装は全確保経路に乗るため、オーバーヘッドが全体性能に影響します。`TECH-001` と衝突する場合は設計変更が必要です（下記リスク）
- **互換性:** 予約 API の形は P06・P08・P10 が依存します。後から変えると広範囲に影響するため、このフェーズで固めます

## リスクと未決事項

### 確定要件に起因するもの

- **`PERF-008` の「全確保」と、索引のサイズ見積もりの関係に注意が必要です。** 5.2 の暫定方針は「行索引は 1 行あたり 24 バイト以下」を設計制約とし、合計 2 GB・平均 100 バイト/行のログ（約 2000 万行）では索引だけで約 480 MB を占めると見積もっています。予算 2 GB のうち索引が占める割合を早期に見積もり、P06 の設計制約として渡してください
- **アロケータ計装のオーバーヘッドが `TECH-001` と衝突する可能性があります。** 許容できない場合の代替は 5.2 の「確保経路をこのサービスへ一本化する」方式ですが、こちらは利用クレート内部の確保を捕捉できず `PERF-008` の定義（Rust プロセス内の全確保）を満たしません。衝突した場合は ADR で整理してください

### 暫定設計に起因するもの

- ソフトしきい値の割合（5.2 は 90%）と、超過時に何をどの順で解放するかは暫定方針です。要件違反として扱わず、実測に基づいて調整します
- 1 行 24 バイト以下という索引の設計制約も暫定方針です。達成できない場合は、索引構造の見直しか予算配分の見直しを検討します

### 人間判断待ち

- **確保を予約トークンへ帰属させる方式が未決です。** 上記「帰属の方式」に候補と論点を整理しました。**これが決まらないと、原子的判定と振り替えのテストが実装できません。** 着手前に ADR で決めてください
- 「Hakutaku 専用の Tauri／WebView2 子プロセス群」の特定方法が未決です。誤って他アプリのプロセスを合算すると参考指標が無意味になります
- `PERF-011` の「+ 1 GB」は WebView2 の複数プロセス構成を前提とした暫定値であり、「技術試作の実測により再確定する」と定められています。再確定は P12・P13 の結果を見てからです

## 完了ゲート

- 予約・拒否・解放が機能し、以降のフェーズが大きな確保の前に予約を通す前提を置ける状態
- 計装のオーバーヘッドが判明し、`TECH-001` と両立するかの判断ができている
- 参考指標の計測手段が機能し、P04 の WebView2 メモリ推移の観測に使える状態
