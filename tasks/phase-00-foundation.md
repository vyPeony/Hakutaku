# P00 開発基盤と層境界

- 状態: 草案（Draft）
- 開始条件: [README の「実装着手前の前提」](README.md#実装着手前の前提)を満たすこと。特に版 1.10 の内容がリポジトリ正本へ取り込まれ、採用済み（`Accepted`）になっていること
- 前提フェーズ: なし（`origin/main` の起動確認アプリを基点とする）
- 段階: 段階0
- 期待成果物: GUI に依存しないコアクレート群、64 ビット・build 17763 相当を下限とするビルド構成、標準のビルド・テスト・静的解析コマンド、TOML 設定の可否判断
- 予定変更範囲: `src-tauri/`、`src/`、`package.json`、`docs/development/workflow.md`（標準コマンドの追記）

## 目的

以降の全フェーズが共有する土台を作ります。対象最古環境を下限としたビルド構成、Rust コア層と GUI 層の境界、標準のビルド・テスト・静的解析コマンドです。

このフェーズの価値は機能ではなく**制約の固定**にあります。`VER-004` は「開発環境にのみ存在する OS 機能・API に依存しない」ことを求めており、これを人手の注意ではなくビルド構成と検査で担保します。段階1（P13）で「開発環境でしか動かない実装」が判明する手戻りを防ぐのが狙いです。

## 対象要件

| ID | 要求の要旨 |
| --- | --- |
| `VER-004` | 段階0のビルド設定を build 17763 相当を下限として構成し、開発環境固有の API に依存しない |
| `PROD-002` | 対応 OS は Windows 10 / 11 の各64ビット版。32ビット版は対象外 |
| `PROD-010` | 新形式は内部モジュールとして追加し、再ビルドで提供する |
| `EXT-001` | 新しい非テキスト形式を将来追加できる設計にする |
| `EXT-002` | 内部モジュールとして追加し、再ビルドで提供できればよい |
| `EXT-003` | 第三者向けの外部プラグイン機構は設けない |
| `TECH-001`／`PROD-008`／`PERF-003` | 高速性を重視する |
| `TECH-004` | Tauri のアプリ・ビルド設定と Capability 定義には TOML を使用する |
| `PROD-015`／`ENV-007` | UI の表示言語は日本語のみ |
| `ENV-001` | LTSC を主対象とする。最古機種は 1809 / build 17763 相当と**想定**（確定は P13） |
| `PROD-003` | データの編集機能を提供しない |

## 作業項目

1. **クレート構成の分割。** 現在の `src-tauri` 単体構成から、`9.2` の責務分離に対応する構成へ分けます。少なくとも「データソース」「形式判定」「パーサー」「共通サービス」を、GUI に依存しないクレートとして切り出します。GUI 層は Tauri コマンドの薄い層に限定し、解析ロジックを置きません。
2. **TOML 設定への移行確認。** `TECH-004` により Tauri の設定と Capability を TOML にします。現状は `tauri.conf.json` と `capabilities/default.json` です。10.2 の暫定方針により、**TOML の可否は技術試作の最初の確認項目**です。
   - 使えた場合: `Tauri.toml` と TOML の Capability 定義へ移行する
   - 使えなかった場合: 判明した事実と版・ビルド構成を記録し、`TECH-004` の適用範囲を Hakutaku の利用者向け設定に限る旨の修正案を ADR として提出する。**`CFG-001`（JSON を使用しない）と衝突するため、黙って JSON を使い続けません**
3. **ビルド下限の固定。** 対象最古環境（build 17763 相当）を下限としてビルド構成を定めます。ターゲットは 64 ビットのみとし、32 ビットビルドを作らないことを構成上明確にします。
4. **依存関係の追加規則。** `VER-004` により、依存を追加するたびに下限環境で動作するかを確認する必要があります。確認手順と記録先を決め、[`docs/development/`](../docs/development/README.md) 側の正本へ追記する必要があるかを判断します。
5. **標準コマンドの整備。** ビルド、テスト、静的解析、整形のコマンドを定めます。[`docs/development/workflow.md`](../docs/development/workflow.md) は「技術スタックと CI が未決定の現在は、存在する検査と手動確認を記録する」としており、このフェーズで初めて標準コマンドが存在する状態になります。同文書の「正式リリース前と将来の自動化」節へ追記します。
6. **日本語表示の前提確認。** UI が日本語のみであること（`PROD-015`）を踏まえ、フォント指定と文字幅の扱いを共通スタイルに置きます。実際の表示確認は P04 です。

## 影響

- **セキュリティ:** Capability 定義を TOML へ移す際、権限を意図せず広げないよう差分を確認します。最小化の本実装は P01（`SEC-012`）です
  - `EXT-003` の受け入れ条件は「実行時に DLL を読み込まない」ではなく「**第三者向けの外部プラグイン機構と、実行時に発見して読み込む拡張 DLL の仕組みを持たない**」です。Tauri と Windows のランタイムは通常の動的リンクで DLL を読み込むため、前者の表現では成立しません
- **参照データ:** `PROD-003` により編集機能を持ちません。この段階では参照データを扱う経路自体がありません
- **データ:** 参照データへの影響はありません
- **性能:** クレート分割によるビルド時間の変化を記録します。実行性能への影響は想定しません
- **互換性:** ビルド下限を上げる変更は `PROD-002` と `ENV-001` に反するため行いません

## リスクと未決事項

### 確定要件に起因するもの

- **TOML 設定の可否が未確認です。** 使えなかった場合、`CFG-001`（JSON を使用しない）と `TECH-004` の整合を取り直す必要があり、ADR が必要になります。10.2 が「技術試作の最初の確認項目に含める」としているのはこのためです
- 下限 build 17763 は `ENV-001` で「相当と想定」とされており、確定は P13 の実測です。段階0では**下限を上げないこと**だけを守ります

### 暫定設計に起因するもの

- クレート分割の粒度は、P05 以降の実装で見直しになり得ます。このフェーズでは「GUI がコアに侵入しない」ことだけを固定します

### 人間判断待ち

- 版 1.10 とリポジトリ正本の整合作業（[README の「実装着手前の前提」](README.md#実装着手前の前提)）が完了していること。未完了のまま着手すると、採用済みでない要件を実装することになります
- 標準コマンドを `workflow.md` へ追記する変更は横断ファイルの変更に当たります（[`concurrent-sessions.md`](../docs/development/concurrent-sessions.md) の「ブランチと対象範囲の規則」）。統合担当を一人に決める必要があります
