# P04 最小縦断の貫通と転送契約の実測

- 状態: 草案（Draft）
- 開始条件: P01・P02・P03 の完了ゲートを満たすこと
- 前提フェーズ: P01、P02、P03
- 段階: 段階0
- 期待成果物: Rust ↔ WebView 間の範囲取得契約、フロントエンドの保持上限と破棄・再取得、転送コストと WebView2 メモリ推移の実測値、`CFG-022` の初期値
- 予定変更範囲: コア側の範囲取得 API、GUI 側の仮想スクロール、計測用のスクリプトと記録

## 目的

「起動 → 設定読み込み → 1 ファイルの解析 → 仮想スクロール表示 → クリップボードコピー」を、**最小構成で一度貫通させます**。機能の完成度ではなく、Rust コア層と WebView2 層をつなぐ契約が成立するかを確かめるフェーズです。

`VER-002` は段階0の目的を次のように定めています。

> 段階0の目的は、現行の開発環境で Rust＋Tauri 構成が動作し、主要機能の骨格が成立することの確認とする。対象は起動、日本語表示、ファイル選択、ログ読み込み、時系列統合表示、仮想スクロール、ヒープ会計、クリップボードコピーとする。

各層を作り込んでから初めて結合すると、10.2 が挙げる「Rust ↔ WebView 間の転送コスト」と「連続スクロール時の WebView2 プロセス群のメモリ推移（`PERF-012`）」が最後まで未確認のまま残ります。5.2 はこの懸念を具体的に述べています。

> ログ本文を毎回転送するため、Rust ↔ WebView 間の直列化コストがスクロール応答性を左右する。試作で不足する場合は、JSON 以外の転送経路の採用を検討する。

**転送経路の変更は、確定後に差し替えるほど影響範囲が広い判断です。** そのため機能を深掘りする前に実測します。

### 時系列統合表示を最小縦断に含めない理由

`VER-002` は段階0の確認対象に時系列統合表示を挙げていますが、これは**段階0全体の範囲**であり、最小縦断の必須要素とは扱いません。理由は次の三点です。

1. マージは Rust 側に閉じたロジックであり、**層をまたぐ契約ではありません。** 後から差し替えても影響が局所に収まります。対して転送経路と保持上限は WebView2 層をまたぐため、確定後の差し替え費用が大きく、先行させる価値があります
2. マージは複数ファイルの読み込みに依存します（`LOG-006`）。P04 に含めると P06 の一部を前倒しすることになり、最小構成という位置づけが崩れます
3. 統合表示の受け入れ条件（`LOG-024`、`LOG-025` の比較キー、同一キーの決定的順序）は、6 書式が揃っていないと意味のある検証になりません

段階0の完了時点（P12）で統合表示が確認できていれば `VER-002` を満たします。

**ただしこの除外には条件があります。** マージの実装を後回しにできるのは、範囲取得契約が最初から複数ソースを前提とした形になっている場合だけです。下記「契約に織り込む4点」を満たさないまま単一ファイル前提の契約を公開すると、P06・P09 で契約変更が波及し、除外の前提が崩れます。

## 作業項目

1. **転送契約の設計。** 5.2 の「表示データは、フロントエンドが可視範囲を指定して Rust コアへ要求し、その範囲だけを受け取る方式」を実装します。1 回の転送で渡す行数とバイト数に上限を設けます。
   - 要求: 表示集合に対する開始位置、件数
   - 応答: 各項目の日時、原文、読み込み元、位置、安定した識別子
   - 内部表現は 4.1 の暫定方針に沿った形にします（日時、読み込み元、ファイル内位置または行番号、原文、任意のログレベル）。P05 の一般化で破綻しないための備えです

   **この契約は、統合表示（P09）を後から足しても変更せずに済む形にします。** 下記「契約に織り込む4点」を満たしてください。

### 契約に織り込む4点

統合表示を P04 の範囲から外す代わりに、**契約だけは複数ソースを前提とした形で先に定義します**。単一ファイル前提の物理オフセット・ページ契約を先に公開すると、P06 で複数ソースの全順序、同一時刻の同順位解決（tie-break）、ソース別の来歴を足した際に、範囲指定、項目 ID、仮想スクロールの再取得整合性まで変更が波及します。

| # | 契約の要件 | 理由 |
| --- | --- | --- |
| 1 | 取得位置・カーソルを**単一ファイルの物理オフセットへ結合しない**。「表示集合に対する範囲取得」として定義する | 表示集合が複数ソースのマージ結果になっても、要求の形が変わらない |
| 2 | 各表示項目に**安定した識別子**と**読み込み元の来歴**を持たせ、UI とコピー経路まで保持する | `LOG-007` の「統合された各行から読み込み元を識別できる」を後付けにしない。P10 のコピーでも来歴が必要 |
| 3 | 同一日時の項目を含め、**範囲を再取得した際に同じ順序と識別子を返す** | `PERF-012` の破棄・再取得と、`LOG-007` の決定的順序が両立する条件 |
| 4 | 表示集合の再読み込み・無効化を UI が検出できる**世代（generation）または同等の仕組み**を持たせる | `LOG-023`（変更検知による索引無効化）と `LOG-028`（明示的な再読み込み）で、UI が古い範囲を掴んだままにならない |

検証には、**複数ソース相当の試験データ**（同一日時の項目を含む2ファイル分に相当する表示集合）を使います。マージの実装そのものは P06・P09 で行いますが、契約が複数ソースに耐えることはこのフェーズで確認します。

### P08 との担当境界

重複を避けるため、所有範囲を分けます。

- **P04 が所有するもの:** 範囲取得契約、保持上限、破棄・再取得の成立
- **P08 が行うこと:** **その契約を変更せず**、仮想表示の完成度と連続スクロール検証の水準を上げる

P08 で契約の変更が必要になった場合、P04 の判断が誤っていたことを意味します。その場合は P08 で黙って変えず、契約変更として扱ってください。
2. **仮想スクロールの実装。** 可視範囲と前後の一定バッファのみを保持します。上限を超えた場合、表示範囲から遠い範囲を破棄します。スクロールで戻った際は再取得します。**取得済みの行を累積しない**ことがこのフェーズの中心的な検証項目です。
3. **転送コストの実測。** 次を計測して記録します。
   - 1 回の範囲取得の所要時間（行数・バイト数を変えて）
   - 直列化・逆直列化がその内訳のどれだけを占めるか
   - 連続スクロール時のフレーム応答
   - **判定:** スクロール応答が許容できない場合、JSON 以外の転送経路（バイナリ形式など）の採用を検討し、ADR へ記録します（5.2）
4. **保持上限の内部状態による検証（機能ゲート）。** 保持行数と保持バイト数、破棄された範囲、再取得の発生を**内部状態として観測できる**ようにし、上限が守られていることを決定的に確認します。
   - `VER-005` により、段階0で `PERF-012` について確認するのは**計測手段が機能すること**までです。機能面の判定はプロセスのメモリ量ではなく**内部状態**で行います
   - プロセスのメモリ量は WebView2 やアロケータの都合で変動するため、機能不備の有無を決定的に示せません

   **対象は「フロントエンドが保持する全行データ」です。** `PERF-012` は「フロントエンド（WebView2 側）は、可視範囲と前後の一定バッファに限って行データを保持し、取得済みの行を累積しないこと」と定めており、自前のキャッシュだけを指していません。次を含めます。

   | 対象 | 計測方法 |
   | --- | --- |
   | 自前の行キャッシュ・登録表 | 直接カウント |
   | **表示ライブラリ内部の行モデル・キャッシュ** | 行モデルの**生成と解放の計数**（第三者ライブラリ内部を直接数えられない場合） |
   | **DOM が保持する行参照** | DOM ノード数の観測 |
   | **購読・イベントハンドラーが保持する行参照** | 購読解除の検証（解除されずに残っていないか） |
   | 上記で捕捉しきれない保持 | 必要に応じて heap snapshot |

   **自前のキャッシュだけを見ると、表示ライブラリや DOM による累積を見逃します。** P08 のリスク欄が挙げているとおり、これらは実際に累積の原因になります。
5. **WebView2 メモリ推移の計測手段の確認。** P02 で作った参考計測を使い、連続スクロール中の WebView2 プロセス群のプライベートコミット量の**時系列を測定・記録できること**を確認します。
   - **傾向値（単調増加しているか）の判定は段階0では行いません**（`VER-005`）。記録して P12・P13 へ渡します
   - 内部の保持上限違反がある場合は、`PERF-012` の機能不備としてブロックします。違反がないのにメモリが増える場合は、性能結果として記録するにとどめます
   - このフェーズでは 2000 万行規模のデータは不要です。規模での確認は P12、最終判定は P13
6. **`CFG-022` の初期値決定。** 実測に基づき、保持行数とバイト数の上限の初期値を決めます。決めた値と根拠を P03 の設定既定値へ反映します。
7. **日本語表示と解像度の確認。** 1920×1080 で、主要機能がスクロールやダイアログの画面外配置なしに操作できることを確認します（10.4）。日本語のフォント、文字幅、行高を確認します。
8. **層境界の確認。** GUI 層に解析ロジックが入っていないことを確認します。10.6 は「段階1で問題が判明した場合に備え、GUI 層と Rust コア層の境界を明確に保ち、GUI フレームワークの差し替えが局所的な変更で済む構造を維持する」ことを求めています。

## 影響

- **セキュリティ:** 範囲取得 API は Rust コマンド経由のファイル読み取りに限定されます（`SEC-012`）。フロントエンドへパスを渡す設計にすると `SEC-012` に反するため、ソース識別子で参照します
- **データ:** 参照ファイルを読み取り専用で開きます。転送内容にログ本文が含まれるため、`SEC-010` により `WebView2` フォルダへ残留し得ることを前提とします
- **性能:** このフェーズの実測結果が、P08 以降の設計を左右します。転送経路の変更が必要になった場合、影響は P08 全体に及びます
- **互換性:** 範囲取得 API の形は P08・P09・P10 が依存します。ここで固めます

## リスクと未決事項

### 確定要件に起因するもの

- **内部の保持上限を守れない場合、`PERF-012` を満たせません。** `PERF-013` により `PERF-008` の予算では検知できないため、内部状態の観測が唯一の歯止めです。解消できない場合は GUI フレームワークの再選定（`DEC-002` の見直し）につながり得ます
- 内部の保持上限を守れているのに WebView2 のメモリが増え続ける場合、原因は WebView2 側にあります。**段階0では判定せず記録にとどめ、P13 の実機測定で最終判定します**（`VER-005`）。ここで判定すると、環境要因を機能不備と誤認します
- `CFG-022` の初期値は開発環境の実測に基づきます。対象端末では搭載メモリを他の業務ソフトウェアと共有するため（`ENV-003`、`ENV-011`）、P13 で見直しになる可能性があります

### 暫定設計に起因するもの

- **転送コストが許容できない場合、転送経路の方針転換が必要になります。** 5.2 は「JSON 以外の転送経路の採用を検討する」としています。この判断がこのフェーズを早い位置に置いた最大の理由です。転換が必要な場合、P08 の設計が変わります
- 1 書式・UTF-8 固定で通した経路が P05 の一般化で破綻しないかは P05 の責任範囲です。内部表現を 4.1 の暫定方針に沿った形にしておくことで備えます

### 人間判断待ち

- 転送経路を変更する判断（JSON 以外を採用するか）は ADR が必要です。実測値を添えて提出してください
- スクロール応答の「許容できる」水準は `PERF-009` により一律の秒数目標がありません。段階0では**回帰の基準となる実測値を残す**ことを目的とし、合否の宣言はしません

## 完了ゲート

- 最小の縦断経路が通り、以降のフェーズが「各層を深掘りする」形に移れる状態
- 転送経路の方針が決まっている（現行方式の継続、または変更の ADR が提出済み）
- 内部状態で保持上限・破棄・再取得が確認でき、**フロントエンドが保持する全行データ**（表示ライブラリ内部の行モデル、DOM と購読が保持する行参照を含む）が上限を越えて増えない
- WebView2 メモリ推移の**計測手段が機能する**（傾向値の判定は P13）
- `CFG-022` の初期値が決まっている

## 後続 Issue / ADR 候補

- ADR: Rust ↔ WebView 間の転送経路（実測値に基づく判断）
- ADR: `PERF-012` を満たせない場合の GUI フレームワーク再選定（`DEC-002` の見直し）
- Issue: `CFG-022` の初期値を P03 の既定値へ反映
- Issue: スクロール応答の回帰基準値の記録と、以降の測定手順の整備
